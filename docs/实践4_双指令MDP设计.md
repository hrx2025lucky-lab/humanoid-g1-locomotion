# 实践 4 — 速度 + 骨盆高度双指令 MDP

> 在 mjlab（MuJoCo + NVIDIA Warp）中为 Unitree G1 设计双指令 MDP，
> 让机器人一边按速度指令行走，一边按高度指令蹲低或站高。
> 联合指令 `c = [v_x, v_y, ω_z, h_cmd]`，其中 `h_cmd ~ U(0.45, 0.80) m`。

---

## 一、核心：蹲姿行走是一条三段闭环

这是本实践唯一真正的设计要点。要让机器人"按指令蹲着走"，
**只写高度奖励是不够的**，必须打通三段：

```
① 采样高度指令        →  ② Actor 观测到指令  →  ③ 奖励高度跟踪
   TODO 1/3               TODO 4                 TODO 5/6
```

漏掉第 ② 段是助教点名的最常见错误。后果是：奖励函数在惩罚"高度不对"，
但策略的输入里根本没有目标高度这一维 —— 它不知道该蹲到哪，
只能从历史观测里瞎猜。训练目标在数学上就不成立。

**这一课的通用形式是：任何"按指令做某事"的任务，
指令必须同时出现在采样端、观测端和奖励端。三者缺一，任务就退化。**

三处的键名 `"base_height"` 必须**完全一致**。`CommandManager` 靠字符串查表，
拼错不报错，只在 `get_command()` 返回 `None` 时触发断言。

---

## 二、坐标系：本作业最容易混淆的地方

```
高度奖励  →  世界系  root_link_pos_w[:, 2]
速度奖励  →  机体系  root_link_lin_vel_b / root_link_ang_vel_b
```

**为什么高度用世界系**：高度指令的语义是"骨盆离地多高"，这是绝对概念。

**为什么速度用机体系**：速度指令 `(v_x, v_y)` 的语义是"朝机器人自己的
前方/侧方走多快"，与朝向无关。若用世界系，机器人转个身、同样的动作
就会算出完全不同的误差。

> ⚠️ 高度用世界系**只在平地成立**。本作业是平地任务，地面 z ≡ 0，
> 世界系 z 等于离地高度。实践 2 的粗糙地形上我们已经栽过一次：
> 倒金字塔楼梯和下坡的地面本身低于 0，用世界系绝对高度做判据会把
> 姿态正常的机器人误判成摔倒。那边的解法是用 `height_scanner`
> 测出脚下真实地面高度再相减。

## 三、三个跟踪奖励的结构

三者形式统一：`r = exp(-error / std²)`，但误差的构成有讲究。

```python
# TODO 6 高度
height_error  = (h_cmd - z_root)²

# TODO 7 线速度
lin_vel_error = Σ(v_xy_cmd - v_xy_actual)² + v_z_actual²
                └──── 跟踪 ────┘            └─ 惩罚 ─┘

# TODO 8 角速度
ang_vel_error = (ω_z_cmd - ω_z_actual)² + Σ(ω_xy_actual)²
                └──── 跟踪 ────┘          └─── 惩罚 ───┘
```

### 为什么把"惩罚项"并进跟踪误差，而不是单开一项

`v_z` 和 `ω_xy` 都不在指令里，期望值恒为 0。把它们并进同一个
`exp(-·/std²)` 是有意为之：二者共享同一条饱和曲线，一旦机器人开始
上下颠簸或左右摇晃，**整个跟踪奖励会一起塌下去**，策略必须同时管好
"走得准"和"走得稳"。

若拆成独立项，策略可以套利 —— 跟踪那项拿满分，颠簸那项认罚，
总分可能还更高。这与实践 2 里"站着不动白拿 `feet_clearance` 满分"
是同一类结构性漏洞。

### `weight` 和 `std` 是两回事

| | 含义 | 本作业取值 |
|---|---|---|
| `weight` | 这一项**有多重要**（决定奖励上限） | 高度 1.0，速度 2.0 |
| `std` | **多大误差算差**（决定曲线陡峭程度） | 高度 0.1，线速度 0.5 |

高度 `std` 必须比速度严得多，因为高度指令量程只有 0.35 m：

```
std=0.1  →  差 0.10 m 得 exp(-1)=0.37 分；差 0.05 m 得 exp(-0.25)=0.78 分
std=0.5  →  差 0.10 m 仍有 exp(-0.04)=0.96 分   ← 几乎没有区分度
```

高度 `weight` 反而比速度小一半，是刻意的：**行走是主任务，高度是附加任务**。
若高度权重压过速度，策略会倾向站着不动把高度稳住 —— 实践 2 刚踩过这个坑。

## 四、非对称 Actor-Critic（TODO 10）

```python
foot_contact = (sensor.data.found > 0).float()   # 只给 Critic
```

**为什么这样分**：Critic 只在训练时估计状态价值 `V(s)`，训练结束就丢弃；
Actor 才是最终部署到真机的网络。真机上"脚是否触地"需要足底力传感器，
未必可靠或存在，所以 Actor 不能依赖它。但仿真里这个信息免费且精确，
给 Critic 用能让价值估计更准 → 优势 `A = R − V` 方差更小 → 梯度更稳。

**让"打分的人"比"做事的人"看得更多**，这是特权学习的基本形态。

注意区分：**指令不是特权信息**。`height_command` 必须给 Actor
（那是任务输入），`foot_contact` 才是特权信息（只给 Critic）。

转 `float` 而非保留 `bool`：观测要拼接成连续浮点向量，`bool` 会在
`concatenate` 时报 dtype 错误。

## 五、课程学习的单位陷阱（TODO 9）

```python
{"step": 0,          "lin_vel_x": (-1.0, 1.0), "ang_vel_z": (-0.5, 0.5)},
{"step": 5000 * 24,  "lin_vel_x": (-1.5, 2.0), "ang_vel_z": (-0.7, 0.7)},
{"step": 10000 * 24, "lin_vel_x": (-2.0, 3.0)},          # ang_vel_z 沿用上阶段
```

`step` 的单位是**环境步**不是训练迭代数。`24` 是 `num_steps_per_env`
（每次迭代每个环境 rollout 的步数），所以这两阶段分别在第 5000 和
第 10000 次迭代生效。

**写成 `5000` 会让课程在第 208 次迭代就跳到 Stage 1** —— 助教点名的高频错误。

为什么要课程：直接从 `(-2.0, 3.0)` 开训，策略在还站不稳时就被要求跑到
3 m/s，绝大多数 episode 在起步瞬间摔倒，采样全是失败样本，学不到有用梯度。

## 六、日志指标不是奖励（TODO 2）

```python
metrics["error_height"] += |h_cmd - z_root| / max_command_step
```

这是**日志指标**，不进反向传播。累加除以 `max_command_step` 是本仓库
`CommandTerm` 的统一惯例，得到的是一条指令生命周期内的**时间平均误差**
而非瞬时值 —— 直接记瞬时值会被采样噪声淹没。

> 实践 2 的教训在这里再次适用：**总 reward 好看不代表任务学会了**。
> 我们上一个实践里 `reward=26.32`、`episode_length=960/1000` 都很漂亮，
> 机器人却在原地踏步。`error_height` 这类分项指标就是用来兜底的。

## 七、消融实验设计

作业 §7 明确要求 **≥2 组消融**，并给出了方向：

> 方案 A 去掉 `track_base_height`，方案 B 使用完整高度奖励；
> 或者比较"Actor 不观测 `height_command`"与"Actor 观测高度指令"。
> 重点比较 `error_height`、总回报、`h=0.5 m` 下的稳定行走时长。

两组各切断第一节那条三段闭环中的一段：

| 组别 | 任务 ID | ①指令 | ②Actor观测 | ③奖励 |
|---|---|---|---|---|
| baseline | `...-Unitree-G1` | ✅ | ✅ | w=1.0 |
| 消融 A | `...-G1-NoHeightRew` | ✅ | ✅ | **w=0** |
| 消融 B | `...-G1-BlindActor` | ✅ | **✗** | w=1.0 |

配置差异已验证（Critic 观测项三组均为 12，变量完全隔离）：

```
配置                 ①指令  ②Actor观测  Critic观测  ③奖励w  Actor项  Critic项
baseline 完整闭环      True      True       True     1.0      8       12
消融A 无高度奖励        True      True       True     0.0      8       12
消融B Actor盲视        True     False       True     1.0      7       12
```

### 消融 A —— 切断"奖励高度跟踪"

策略能"看见"目标高度却没有动机去跟踪它。预期骨盆高度会停在让**速度跟踪奖励
最大化**的姿态上，`error_height` 显著高于 baseline 且**与 `h_cmd` 无相关性**。

用 `weight = 0` 而非删除该项：`RewardManager` 不跳过零权重项，
TensorBoard 里仍会记录 `track_base_height`（恒为 0），
`error_height` 指标也照常输出，两组曲线可以直接叠图。

### 消融 B —— 切断"Actor 观测到指令"

**这组更能说明问题。** 奖励函数仍在惩罚"高度不对"，但策略输入里没有
目标高度这一维，它**无从知道该蹲到多低**。

这组有一个**可解析的理论预测**，使结论可证伪：

策略只能收敛到一个折中的固定高度 —— 让 `h_cmd` 在整个区间上的期望误差最小，
即区间中点 `(0.45+0.80)/2 = 0.625 m`。此时

```
E|h_cmd − 0.625| = (0.80 − 0.45)/4 = 0.0875 m
```

所以 `error_height` 应当收敛到 **约 0.0875 m 且不随指令变化**。
若实测值确实落在这附近，就直接证明了"策略在盲猜区间中点"。

> **只从 Actor 移除，Critic 保留。** 我们要测的是"Actor 知不知道目标"，
> 不是"系统里有没有这个信息"。Critic 保留能让价值估计质量与 baseline 一致，
> 把变量隔离在策略网络这一侧 —— 否则 critic 也变瞎，
> 优势函数的方差变化会污染对照。
>
> 这与第一节"指令不是特权信息"的论述不矛盾：
> 此处是**刻意制造的病态配置**，用于反证观测接线的必要性。

### 运行

```bash
./scripts/run_p4_ablation.sh              # 顺序跑三组
ITERS=4000 ./scripts/run_p4_ablation.sh   # 缩短迭代快速验证
```

三组共用同一份 `rl_cfg` 并显式固定 `seed=42 / num_envs=4096 / max_iterations`，
唯一变量就是上表那一处差异。

> `--agent.logger` 默认是 **wandb**，脚本里已显式改为 `tensorboard`。
