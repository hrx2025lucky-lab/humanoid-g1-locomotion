# 实践 4 — 速度 + 骨盆高度双指令 MDP

> 在 mjlab（MuJoCo + NVIDIA Warp）中为 Unitree G1 设计双指令 MDP，
> 让机器人一边按速度指令行走，一边按高度指令蹲低或站高。
> 联合指令 `c = [v_x, v_y, ω_z, h_cmd]`，其中 `h_cmd ~ U(0.45, 0.80) m`。

---

## 一、核心：蹲姿行走是一条三段闭环

这是本实践唯一真正的设计要点。要让机器人"按指令蹲着走"，
**只写高度奖励是不够的**，必须打通三段：

```
① 采样高度指令        →  ② Actor 观测到指令  →  ③ 奖励高度跟踪
   TODO 1/3               TODO 4                 TODO 5/6
```

漏掉第 ② 段是助教点名的最常见错误。后果是：奖励函数在惩罚"高度不对"，
但策略的输入里根本没有目标高度这一维 —— 它不知道该蹲到哪，
只能从历史观测里瞎猜。训练目标在数学上就不成立。

**这一课的通用形式是：任何"按指令做某事"的任务，
指令必须同时出现在采样端、观测端和奖励端。三者缺一，任务就退化。**

三处的键名 `"base_height"` 必须**完全一致**。`CommandManager` 靠字符串查表，
拼错不报错，只在 `get_command()` 返回 `None` 时触发断言。

---

## 二、坐标系：本作业最容易混淆的地方

```
高度奖励  →  世界系  root_link_pos_w[:, 2]
速度奖励  →  机体系  root_link_lin_vel_b / root_link_ang_vel_b
```

**为什么高度用世界系**：高度指令的语义是"骨盆离地多高"，这是绝对概念。

**为什么速度用机体系**：速度指令 `(v_x, v_y)` 的语义是"朝机器人自己的
前方/侧方走多快"，与朝向无关。若用世界系，机器人转个身、同样的动作
就会算出完全不同的误差。

> ⚠️ 高度用世界系**只在平地成立**。本作业是平地任务，地面 z ≡ 0，
> 世界系 z 等于离地高度。实践 2 的粗糙地形上我们已经栽过一次：
> 倒金字塔楼梯和下坡的地面本身低于 0，用世界系绝对高度做判据会把
> 姿态正常的机器人误判成摔倒。那边的解法是用 `height_scanner`
> 测出脚下真实地面高度再相减。

## 三、三个跟踪奖励的结构

三者形式统一：`r = exp(-error / std²)`，但误差的构成有讲究。

```python
# TODO 6 高度
height_error  = (h_cmd - z_root)²

# TODO 7 线速度
lin_vel_error = Σ(v_xy_cmd - v_xy_actual)² + v_z_actual²
                └──── 跟踪 ────┘            └─ 惩罚 ─┘

# TODO 8 角速度
ang_vel_error = (ω_z_cmd - ω_z_actual)² + Σ(ω_xy_actual)²
                └──── 跟踪 ────┘          └─── 惩罚 ───┘
```

### 为什么把"惩罚项"并进跟踪误差，而不是单开一项

`v_z` 和 `ω_xy` 都不在指令里，期望值恒为 0。把它们并进同一个
`exp(-·/std²)` 是有意为之：二者共享同一条饱和曲线，一旦机器人开始
上下颠簸或左右摇晃，**整个跟踪奖励会一起塌下去**，策略必须同时管好
"走得准"和"走得稳"。

若拆成独立项，策略可以套利 —— 跟踪那项拿满分，颠簸那项认罚，
总分可能还更高。这与实践 2 里"站着不动白拿 `feet_clearance` 满分"
是同一类结构性漏洞。

### `weight` 和 `std` 是两回事

| | 含义 | 本作业取值 |
|---|---|---|
| `weight` | 这一项**有多重要**（决定奖励上限） | 高度 1.0，速度 2.0 |
| `std` | **多大误差算差**（决定曲线陡峭程度） | 高度 0.1，线速度 0.5 |

高度 `std` 必须比速度严得多，因为高度指令量程只有 0.35 m：

```
std=0.1  →  差 0.10 m 得 exp(-1)=0.37 分；差 0.05 m 得 exp(-0.25)=0.78 分
std=0.5  →  差 0.10 m 仍有 exp(-0.04)=0.96 分   ← 几乎没有区分度
```

高度 `weight` 反而比速度小一半，是刻意的：**行走是主任务，高度是附加任务**。
若高度权重压过速度，策略会倾向站着不动把高度稳住 —— 实践 2 刚踩过这个坑。

## 四、非对称 Actor-Critic（TODO 10）

```python
foot_contact = (sensor.data.found > 0).float()   # 只给 Critic
```

**为什么这样分**：Critic 只在训练时估计状态价值 `V(s)`，训练结束就丢弃；
Actor 才是最终部署到真机的网络。真机上"脚是否触地"需要足底力传感器，
未必可靠或存在，所以 Actor 不能依赖它。但仿真里这个信息免费且精确，
给 Critic 用能让价值估计更准 → 优势 `A = R − V` 方差更小 → 梯度更稳。

**让"打分的人"比"做事的人"看得更多**，这是特权学习的基本形态。

注意区分：**指令不是特权信息**。`height_command` 必须给 Actor
（那是任务输入），`foot_contact` 才是特权信息（只给 Critic）。

转 `float` 而非保留 `bool`：观测要拼接成连续浮点向量，`bool` 会在
`concatenate` 时报 dtype 错误。

## 五、课程学习的单位陷阱（TODO 9）

```python
{"step": 0,          "lin_vel_x": (-1.0, 1.0), "ang_vel_z": (-0.5, 0.5)},
{"step": 5000 * 24,  "lin_vel_x": (-1.5, 2.0), "ang_vel_z": (-0.7, 0.7)},
{"step": 10000 * 24, "lin_vel_x": (-2.0, 3.0)},          # ang_vel_z 沿用上阶段
```

`step` 的单位是**环境步**不是训练迭代数。`24` 是 `num_steps_per_env`
（每次迭代每个环境 rollout 的步数），所以这两阶段分别在第 5000 和
第 10000 次迭代生效。

**写成 `5000` 会让课程在第 208 次迭代就跳到 Stage 1** —— 助教点名的高频错误。

为什么要课程：直接从 `(-2.0, 3.0)` 开训，策略在还站不稳时就被要求跑到
3 m/s，绝大多数 episode 在起步瞬间摔倒，采样全是失败样本，学不到有用梯度。

## 六、日志指标不是奖励（TODO 2）

```python
metrics["error_height"] += |h_cmd - z_root| / max_command_step
```

这是**日志指标**，不进反向传播。累加除以 `max_command_step` 是本仓库
`CommandTerm` 的统一惯例，得到的是一条指令生命周期内的**时间平均误差**
而非瞬时值 —— 直接记瞬时值会被采样噪声淹没。

> 实践 2 的教训在这里再次适用：**总 reward 好看不代表任务学会了**。
> 我们上一个实践里 `reward=26.32`、`episode_length=960/1000` 都很漂亮，
> 机器人却在原地踏步。`error_height` 这类分项指标就是用来兜底的。

## 六点五、奖励结构的四维组织与权重依据

> 补于 2026-09-04。作业 §8.2 明确要求报告「按 Task / Style / Reg / Penalty
> 四维组织」并「解释为何如此配置（即使未改代码也须分析）」。
> 此前本文档按"三个跟踪奖励""非对称 Actor-Critic"等主题组织，
> 内容不缺但没按官方维度归类，属于结构不合规。

### 四维归类（权重取自 `velocity_env_cfg.py` 实测）

| 维度 | 奖励项 | weight | 作用 |
|---|---|---|---|
| **Task** | `track_linear_velocity` | **+2.0** | 跟上 vx/vy 指令 |
| | `track_angular_velocity` | **+2.0** | 跟上 yaw 指令 |
| | `track_base_height`（TODO 6） | **+1.0** | 跟上骨盆高度指令 —— 本作业新增的第二条指令 |
| **Style** | `upright` | +1.0 | 保持躯干直立 |
| | `pose` | +1.0 | 靠近默认姿态，抑制怪异构型 |
| | `foot_clearance` | −2.0 | 摆动腿抬脚高度 |
| | `foot_swing_height` | −0.25 | 摆动轨迹形状 |
| **Reg** | `action_rate_l2` | −0.1 | 动作平滑，抑制抖动 |
| | `soft_landing` | −1e-5 | 落地冲击 |
| **Penalty** | `dof_pos_limits` | −1.0 | 关节越界 |
| | `foot_slip` | −0.1 | 支撑脚打滑 |

`body_ang_vel` / `angular_momentum` / `air_time` 的 weight 是 **0.0**，
注释写明「Override per-robot」—— 框架保留接口但 G1 未启用。
**注意零权重项不会被 RewardManager 跳过**，它仍会参与日志统计，
所以看到它们出现在指标里不等于它们在影响训练。

### 权重选择依据

**为什么高度跟踪是 1.0，只有速度跟踪的一半**

双指令 MDP 里两条指令并不对等：速度是"任务本身"，高度是"任务的姿态约束"。
若把高度提到 2.0，策略会为了压低骨盆而牺牲步幅——蹲下来但走不动。
1.0 让它足以塑形、又不至于压倒主任务。
消融数据支持这个判断：去掉高度奖励后 `error_height` 从 0.0578 劣化到 0.3304
（**5.7 倍**），而 `error_vel_xy` 几乎不动（0.5400 → 0.5396），
说明两条指令的耦合确实是弱的、可分离的。

**为什么 `std=0.1` 而不是更大**

`weight` 是重要性，`std` 是"多大误差算差"（详见 §三.3）。
骨盆高度的指令范围是 0.5~0.75 m，工作区间跨度 0.25 m。
`std=0.1` 时差 0.1 m 得 `exp(-1)=0.37` 分、差 0.05 m 得 `exp(-0.25)=0.78` 分——
梯度在 0.05~0.15 m 这个量级最陡，正好是"蹲得够不够"的判别尺度。
std 若取 1.0，整个工作区间内奖励几乎恒定，等于没有梯度
（这正是实践 5 踩过的坑：`1-tanh(d/std)` 的 std 取小了，
5~10 m 的工作范围内恒等于 0）。

**为什么 `foot_clearance` 用 −2.0 这么大的负权重**

它是唯一能阻止"拖着脚滑行"的项。蹲姿降低了骨盆高度，
摆动腿的离地裕度本来就被压缩，惩罚不够重策略就会退化成蹭地走。
配合 `foot_slip`（−0.1）形成两道防线：前者管抬脚，后者管支撑脚打滑。

### 训练曲线：三项官方要求的指标

日志里的实际指标名是 `Metrics/velocity/error_vel_xy` 与 `error_vel_yaw`
（不是 `error_lin_vel`），三组末值：

| 组 | `error_vel_xy` | `error_vel_yaw` | `error_height` | 总回报 |
|---|---|---|---|---|
| baseline | **0.5400** | **0.9947** | **0.0578** | 见 §9.6 |
| blind_actor | 0.5590 | 1.1196 | 0.2823 | 同上 |
| no_height_rew | 0.5396 | 0.9232 | 0.3304 | 同上 |

读法：

- **速度维度三组几乎一致**（xy 差 <3.6%），说明两个消融都没伤到主任务，
  对照实验是干净的
- **高度维度差异巨大**（0.0578 vs 0.2823 vs 0.3304），差异被正确隔离到了被切断的那一段
- `error_vel_yaw` 在 `blind_actor` 组偏高 12.6%：actor 看不到指令后，
  转向也受了牵连——这是预期外但可解释的，转向依赖对目标朝向的感知

## 七、消融实验设计

作业 §7 明确要求 **≥2 组消融**，并给出了方向：

> 方案 A 去掉 `track_base_height`，方案 B 使用完整高度奖励；
> 或者比较"Actor 不观测 `height_command`"与"Actor 观测高度指令"。
> 重点比较 `error_height`、总回报、`h=0.5 m` 下的稳定行走时长。

两组各切断第一节那条三段闭环中的一段：

| 组别 | 任务 ID | ①指令 | ②Actor观测 | ③奖励 |
|---|---|---|---|---|
| baseline | `...-Unitree-G1` | ✅ | ✅ | w=1.0 |
| 消融 A | `...-G1-NoHeightRew` | ✅ | ✅ | **w=0** |
| 消融 B | `...-G1-BlindActor` | ✅ | **✗** | w=1.0 |

配置差异已验证（Critic 观测项三组均为 12，变量完全隔离）：

```
配置                 ①指令  ②Actor观测  Critic观测  ③奖励w  Actor项  Critic项
baseline 完整闭环      True      True       True     1.0      8       12
消融A 无高度奖励        True      True       True     0.0      8       12
消融B Actor盲视        True     False       True     1.0      7       12
```

### 消融 A —— 切断"奖励高度跟踪"

策略能"看见"目标高度却没有动机去跟踪它。预期骨盆高度会停在让**速度跟踪奖励
最大化**的姿态上，`error_height` 显著高于 baseline 且**与 `h_cmd` 无相关性**。

用 `weight = 0` 而非删除该项：`RewardManager` 不跳过零权重项，
TensorBoard 里仍会记录 `track_base_height`（恒为 0），
`error_height` 指标也照常输出，两组曲线可以直接叠图。

### 消融 B —— 切断"Actor 观测到指令"

**这组更能说明问题。** 奖励函数仍在惩罚"高度不对"，但策略输入里没有
目标高度这一维，它**无从知道该蹲到多低**。

这组有一个**可解析的理论预测**，使结论可证伪：

策略只能收敛到一个折中的固定高度 —— 让 `h_cmd` 在整个区间上的期望误差最小，
即区间中点 `(0.45+0.80)/2 = 0.625 m`。此时

```
E|h_cmd − 0.625| = (0.80 − 0.45)/4 = 0.0875 m
```

所以 `error_height` 应当收敛到 **约 0.0875 m 且不随指令变化**。
若实测值确实落在这附近，就直接证明了"策略在盲猜区间中点"。

> **只从 Actor 移除，Critic 保留。** 我们要测的是"Actor 知不知道目标"，
> 不是"系统里有没有这个信息"。Critic 保留能让价值估计质量与 baseline 一致，
> 把变量隔离在策略网络这一侧 —— 否则 critic 也变瞎，
> 优势函数的方差变化会污染对照。
>
> 这与第一节"指令不是特权信息"的论述不矛盾：
> 此处是**刻意制造的病态配置**，用于反证观测接线的必要性。

## 九、消融实验结果

三组各跑 3000 iter × 4096 env，共用同一份 `rl_cfg` 与 `seed=42`。
训练前逐项核对过唯一变量：

| 组别 | Actor 有 `height_command` | Critic 有 | `track_base_height` 权重 |
|---|---|---|---|
| baseline | ✅ 8 项 | ✅ 12 项 | 1.0 |
| blind_actor | ❌ **7 项** | ✅ 12 项 | 1.0 |
| no_height_rew | ✅ 8 项 | ✅ 12 项 | **0.0** |

复现：`python scripts/compare_p4_ablation.py`

### 9.1 先修一个指标 bug

`Metrics/base_height/target_height_mean` 实测 **1.5579**，
但高度指令是在 `[0.45, 0.80]` 上均匀采样的，其真值必然是中点 **0.625**。

原因在 `_update_metrics`：

```python
max_command_step = self.cfg.resampling_time_range[1] / self._env.step_dt  # 8.0/0.02 = 400
self.metrics["error_height"] += torch.abs(...) / max_command_step
```

metrics 实际累积了**整个 episode**（997.7 步）而不是单条指令的生命周期，
于是所有量被同一个因子放大：`997.7 / 400 = 2.494`。
实测比值 `1.5579 / 0.625 = 2.493` —— 吻合到小数点后两位，确认了这个解释。

> **这个指标自带校准物**：`target_height_mean` 的真值可由指令分布解析地算出来，
> 所以能反推膨胀因子并校正 `error_height`。设计日志指标时顺带记一个
> "已知真值的量"，就能在事后自查数值管道是否正确。

三组 episode 长度几乎相同（997.5~997.9），膨胀因子一致，
**组间相对比较不受影响**；下面同时给出原始值与校准值。

### 9.2 主判据：高度跟踪误差

| 组别 | 原始值 | 校准后 (m) | 相对 baseline |
|---|---|---|---|
| baseline | 0.0597 | **0.0240** | 1.00× |
| blind_actor | 0.2982 | 0.1196 | **5.00×** |
| no_height_rew | 0.3352 | 0.1345 | **5.61×** |

**切断任意一段，高度跟踪误差都劣化 5 倍以上** —— 三段闭环
「① 采样指令 → ② Actor 观测到 → ③ 奖励跟踪」缺一不可得到验证。

### 9.3 blind_actor 落在可证伪的理论区间内

这一组事先给了解析预测，使结论可证伪而不只是"效果更差"。

Actor 看不到目标高度时只能输出一个固定高度 `h*`。对 `h_cmd ~ U(0.45, 0.80)`：

```
E|h_cmd − h*| = [(h*−0.45)² + (0.80−h*)²] / (2 × 0.35)
```

- 取中点 `h*=0.625` 时最小：**0.0875 m**
- 取区间端点时最大：**0.1750 m**

校准后实测 **0.1196 m**，正落在这个区间内。反推 `h* = 0.731 m`（或对称的 0.519）。

**0.731 m 比最优的 0.625 更高，这恰恰说明策略在做权衡**：
速度跟踪等其它奖励把姿态往自然站高（约 0.78 m）拉，
高度奖励把它往 0.625 拉，最终停在两者之间。
如果 Actor 真能看见指令，就不需要这种折中 —— baseline 的 0.0240 m
只有理论最优折中值 0.0875 的 **27%**，证明它确实在**按指令逐条调整**
而不是输出一个固定值。

### 9.4 对照项：速度任务未受波及
