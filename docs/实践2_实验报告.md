> 训练：10000 iter × 4096 env 已跑满。run `2026-09-02_10-58-17`（0→9000）
> 续训 `2026-09-02_20-03-39`（9000→10000），原因与注意事项见 §7.3。

## 1. 任务目标与总体思路

在平地速度跟踪任务的基础上，训练一个**带地形感知**的粗糙地形行走策略。

平地行走只依赖本体感知就够了 —— 地面高度恒为 0，是可预测的。
换到粗糙地形后这个前提消失：策略**无法提前知道脚下的高度变化**，
只能"踩到了才知道"被动响应，在台阶和斜坡上必然失稳。

因此核心改动是给策略加一双"眼睛"（局部地形高度图），
并相应调整地形、奖励与终止条件，使它们在非平地上仍然成立。

改动按四个层次组织：

```
① 地形    平地 → ROUGH_TERRAINS_CFG（六种子地形 × 10 级难度）
② 感知    启用 height_scanner，把 187 维高度图接入 policy/critic 观测
③ 判据    base_height 的奖励与终止从世界系绝对高度改为相对地形高度
④ 奖励    重设 10 项权重，打破"站着不动"的局部最优
```

## 2. 地形配置

```python
terrain_cfg = copy.deepcopy(ROUGH_TERRAINS_CFG)
self.scene.terrain.terrain_generator = terrain_cfg
self.scene.terrain.max_init_terrain_level = terrain_cfg.num_rows - 1
```

`ROUGH_TERRAINS_CFG` 包含六种程序化生成的子地形：

| 子地形 | 占比 |
|---|---|
| 金字塔楼梯 `pyramid_stairs` | 0.2 |
| 倒金字塔楼梯 `pyramid_stairs_inv` | 0.2 |
| 随机方块 `boxes` | 0.2 |
| 随机起伏 `random_rough` | 0.2 |
| 上坡 `hf_pyramid_slope` | 0.1 |
| 下坡 `hf_pyramid_slope_inv` | 0.1 |

网格为 `num_rows=10 × num_cols=20`，**行 = 难度等级**，列 = 同难度的不同随机样本。

### 两个实现细节

**`deepcopy` 是必需的。** `ROUGH_TERRAINS_CFG` 是模块级全局单例，
直接引用后再修改它的字段（父类会写 `curriculum`，play 配置会写 `num_rows`）
会污染同进程内的其他配置。

**赋值必须在 `super().__post_init__()` 之前。** 父类检测到
`curriculum.terrain_levels` 存在时才会把 `terrain_generator.curriculum` 置 `True`；
`TerrainGeneratorCfg.curriculum` 默认是 `False`，赋值晚了这行逻辑就跑空，
地形课程不会生效。

## 3. 感知设计（height_scan）

### 3.1 传感器

传感器在基线场景中已经存在，但此前**没有任何 MDP 项在使用它**：

```python
height_scanner = RayCasterCfg(
    prim_path="{ENV_REGEX_NS}/Robot/torso_link",
    offset=RayCasterCfg.OffsetCfg(pos=(0.0, 0.0, 20.0)),
    ray_alignment="yaw",
    pattern_cfg=patterns.GridPatternCfg(resolution=0.1, size=[1.6, 1.0]),
    mesh_prim_paths=["/World/ground"],
)
```

**扫描区域**：以躯干为中心的 **1.6 m（前后）× 1.0 m（左右）** 矩形，
分辨率 0.1 m。

**射线数**：`(1.6/0.1 + 1) × (1.0/0.1 + 1) = 17 × 11 = 187` 根。

**`ray_alignment="yaw"`**：扫描网格只跟随机器人的朝向旋转，
**不跟随 roll/pitch**。这样机器人身体倾斜时，采样网格仍保持水平，
读到的是"脚下这片地的真实形状"而非被姿态扭曲的投影。

**`offset=(0,0,20)`**：射线起点抬高 20 m，从高处垂直向下打，
避免被机器人自身的躯干和四肢遮挡。

### 3.2 height_scan 的语义

```python
height_scan = sensor.data.pos_w[:, 2] - sensor.data.ray_hits_w[..., 2] - offset
```

返回的**不是**地形的绝对高度，而是"传感器高度 − 命中点高度 − offset"，
即**传感器到地面的竖直距离**再减去一个参考偏移。

`offset=0.5` 是 IsaacLab 的默认值。它不是从几何推导出的物理常数，
而是训练时为统一观测分布而采用的**零点定义**：命中点落在参考平面上时输出接近 0，
地形更低时为正、更高时为负。**部署时必须保持一致**，否则策略读到的数值分布整体平移。

### 3.3 接入观测

```python
scan_obs = ObsTerm(
    func=mdp.height_scan,
    params={"sensor_cfg": SceneEntityCfg("height_scanner")},
    clip=(-1.0, 5.0),
    noise=Unoise(n_min=-0.1, n_max=0.1),
)
self.observations.policy.height_scanner = scan_obs
self.observations.critic.height_scanner = copy.deepcopy(scan_obs)
self.observations.critic.height_scanner.noise = None    # critic 不加噪
```

**policy 加噪、critic 不加噪。** 真机的高度图来自 LiDAR 或深度相机，
存在测量误差与标定漂移，±0.1 m 的均匀噪声迫使策略不去依赖单根射线的精确值。
critic 只在训练时使用，是特权网络，它的信息集必须 ⊇ policy ——
否则价值估计比策略还"瞎"，优势函数失真。

**`clip=(-1.0, 5.0)` 是双保险**：既压住异常值域，又能把射线打空时的 `inf`
截成 5.0（`torch.clip(inf, -1, 5) == 5.0`），不会污染网络输入。
奖励与终止项没有这层保护，所以第 4 节才必须自己做 `inf` 掩码。

### 3.4 观测维度

| 观测项 | 维度 |
|---|---|
| `base_ang_vel` | 3 |
| `projected_gravity` | 3 |
| `velocity_commands` | 3 |
| `joint_pos_rel` | 29 |
| `joint_vel_rel` | 29 |
| `last_action` | 29 |
| **`height_scanner`（新增）** | **187** |
| 单帧合计 | **283** |
| × `history_length = 5` | **1415** |

即 policy 网络的输入从基线的 `96 × 5 = 480` 维扩展到 **1415 维**。

> 顺序是硬约束：`ObservationManager._prepare_terms` 遍历的是**实例字典**
> （`group_cfg.__dict__.items()`），Python 3.7+ 保持插入顺序，
> 所以动态赋值的新项自动排在末尾。这一点对后续 sim2sim 是硬要求 ——
> MuJoCo 侧按同样顺序手工拼观测向量，顺序错了不报错，只会让策略读到错位的数值。

## 4. 高度判据的修正

基线的两个 height 项都拿机器人根节点的**世界系 z** 与常数比较：

```python
base_height      = base_height_l2(target_height=0.78)                 # 奖励
base_height_done = root_height_below_minimum(minimum_height=0.2)      # 终止
```

平地上地面 z ≡ 0，"世界系高度"与"离地高度"是同一个数。
换到 `ROUGH_TERRAINS_CFG` 后前提消失：**倒金字塔楼梯和下坡的地面本身低于 0**，
机器人姿态完全正常却因为"世界系 z 太低"被判摔倒。

16 环境冒烟测试实测：`Episode_Termination/base_height = 0.25`，
**四分之一的 episode 是被这条误杀的**。误杀不仅浪费采样，
还会让策略学到"不要走进低洼地形"这种完全错误的行为。

IsaacLab 官方对此是知情的，`root_height_below_minimum` 的 docstring 写着：
> This is currently only supported for flat terrains, i.e. the minimum height is in the world frame.

### 修法

判据从"机器人在世界里多高"换成"机器人相对脚下地面多高"，
地面高度由 `height_scanner` 估计：

```python
self.rewards.base_height.func = mdp_ext.base_height_l2_safe
self.terminations.base_height.func = mdp_ext.root_height_below_minimum_adaptive
```

**为什么不直接用官方的 `base_height_l2(sensor_cfg=...)`**：
官方版确实支持 `sensor_cfg`，但内部是

```python
adjusted_target = target_height + torch.mean(sensor.data.ray_hits_w[..., 2], dim=1)
```

**没有任何 `inf` 防护**。射线打空时 `ray_hits_w` 是 `inf`，
`torch.mean` 只要输入里有一个 `inf`，整个环境的结果就是 `inf`
→ 奖励 `inf` → 反传出 `NaN` → 优化器把 `NaN` 写进权重。
**它不会抛异常**，只会让 `Policy/mean_noise_std` 变成 `nan` 而训练看起来还在跑。

自实现的版本先掩掉 `inf` 再求均值（不能先 `mean` 后 `nan_to_num`，
那样 `inf` 已经污染了整个均值）：

```python
z = sensor.data.ray_hits_w[..., 2]
valid = torch.isfinite(z)
mean_valid = torch.where(valid, z, 0).sum(dim=1) / valid.sum(dim=1).clamp(min=1)
ground = torch.where(valid.sum(dim=1) > 0, mean_valid, fallback)   # 全打空则退化为 0.0
```

`fallback=0.0` 使最坏情况下行为与修改前完全一致，不引入新的失败模式。

## 5. 动作空间

**保持基线不变**，29 维关节位置控制：

```python
JointPositionAction = mdp.JointPositionActionCfg(
    asset_name="robot", joint_names=[".*"], scale=0.25, use_default_offset=True
)
```

**含义**：策略输出 29 维动作 `a`，实际的关节目标位置为

```
q_target = q_default + 0.25 · a
```

`use_default_offset=True` 表示以**默认站姿**为基准做残差，
`scale=0.25` 把网络输出（量级约 ±1）压缩到 ±0.25 rad 的关节增量。
目标角再经 PD 控制器转成力矩。

**为什么用位置控制而非力矩控制**：PD 控制器提供了一层天然的低通滤波与阻抗，
策略只需决定"关节该去哪"，不必学习完整的动力学补偿，训练难度显著降低，
且对仿真-真机的动力学差异更鲁棒。

> 对比实践 3 的 HoST 增量动作空间 `q* = q_current + 0.25a` ——
> 那里基准是**当前姿态**而非默认姿态。站起任务涉及大范围接触状态切换，
> 固定基准会产生一个持续把机器人拽向站姿的恒定拉力。
> 而行走任务姿态始终在标称站姿附近小幅摆动，用默认姿态作基准是合适的。

## 6. 奖励设计（本实践最关键的部分）

### 6.1 第一次训练的失败

第一次训练跑满 10000 iter，**常规指标全部漂亮**：

| 指标 | @2561 | @9999 |
|---|---|---|
| Mean episode length | 489.76 | **960.44** |
| `time_out` 占比 | 0.1427 | **0.9064** |
| `bad_orientation` 占比 | 0.8573 | **0.0936** |
| Mean reward | 7.14 | **26.32** |

录像却拍出完全不同的东西：**机器人原地踏步，11.98 秒净位移不到 0.3 米。**

判读方法：play 相机锁定在 0 号机器人（`viewer.origin_type="asset_root"`），
机器人恒在画面中心，因此**背景的位移就是机器人的位移**。
对比第 5 帧与第 598 帧，背景台阶只偏移约 30~40 像素；
台阶在 8 米开外，折算下来位移 < 0.3 m。

三条佐证：

```
Metrics/base_velocity/error_vel_xy   @2500=0.135 → @末=0.615    误差反而变大
Episode_Reward/track_lin_vel_xy      @4000=0.600 → @9990=0.628  4000 iter 即平台期
Curriculum/terrain_levels            全程 0                      升级判据是净位移>4m
```

### 6.2 根因：静止是奖励函数的最优解

把 `Episode_Reward/*` 全部拆开排序（单位：每秒平均）：

```
feet_clearance       +0.8228   ← 第一大正奖励
track_lin_vel_xy     +0.6355   ← 主任务，上限只有 1.0
gait                 +0.5014   ← 上限就是 0.5，等于拿满
alive                +0.1448   ← 上限 0.15，拿了 96.5%
────────────────────────────
action_rate          -0.4281   ← 以下惩罚只在动起来时才产生
joint_vel            -0.1334
joint_deviation_arms -0.1228
...
正奖励 +2.3273   惩罚 -0.9873   净 +1.3400
```

两个"站着也能拿满分"的漏洞：

**`foot_clearance_reward`**（拿了 0.8228）

```python
reward = exp(-Σ[(foot_z - target)² · tanh(k·‖foot_vel_xy‖)] / std)
                                     └──── 关键乘子 ────┘
```

设计意图是"只要求摆动腿抬够高，支撑腿不管"。副作用是
**脚不动 → `tanh(0)=0` → 整个惩罚为 0 → `exp(0)=1.0` 满分**。
静止是这一项的全局最优。

**`feet_gait`**（拿了 0.5014，上限 0.5）

按 0.8 s 固定周期判"该支撑时是否着地"。双脚长期着地时，
相位 < 0.55 的那 55% 时间照样得分，算下来静止能拿约 0.55/1.0。

**加上惩罚项的不对称性** —— `action_rate`、`joint_vel`、`joint_acc`、
`feet_slide`、`energy` 全部与运动量成正比，静止时全部接近 0 ——
策略面对的实际选择是：

| | 正奖励 | 惩罚 | 净 |
|---|---|---|---|
| 站着不动 | ≈ 2.1 | ≈ 0 | **≈ 2.1** |
| 努力行走 | track 最多再多拿 **0.36** | 付出全部动作惩罚 | 更低 |

**走路的边际收益上限只有 0.36，边际成本却是全套动作惩罚。理性策略当然站着。**

### 6.3 权重重设

依据课程《第二章作业讲解》p5/p6 的推荐表。核心不是"把奖励调大"，
而是**改变边际激励比**：

| 奖励项 | 改前 | 改后 | 理由 |
|---|---|---|---|
| `track_lin_vel_xy` | 1.0 | **3.0** | exp 型奖励的权重即上限；跟踪 60%→100% 的收益从 0.4 提到 1.2 |
| `track_ang_vel_z` | 0.5 | **2.0** | 同上 |
| `gait` | 0.5 | **0** | 固定相位在粗糙地形上是束缚；且是静止收益来源 |
| `feet_air_time` | 无 | **+0.5** | **唯一直接奖励迈步的项**，双脚同时着地得 0 |
| `stand_still` | 无 | **-1.0** | 把"停"定义为具体姿态，使走/停成为可区分的模式 |
| `joint_deviation_arms` | -0.1 | -0.5 | 抑制手臂乱摆抬高重心晃动 |
| `joint_deviation_waists` | -1.0 | -2.0 | 同上 |
| `joint_deviation_legs` | -1.0 | -2.0 | 同上 |
| `base_height` | -10 | **-20** | 防守：track 放大后策略可能弓身下蹲刷分 |
| `feet_clearance` | 世界系基准 | **相对地形基准** | 台阶上不再误罚正确抬脚 |

`feet_air_time` 是补上的关键。它只在 `single_stance`（恰好一只脚着地）时计分，
站立和跳跃都是 0，天然反"原地不动"；内部还有 `‖cmd‖>0.1` 的掩码，
零指令时不发钱，不会鼓励空踏步。

`base_height` 加倍是**放大激励时的配套防守**：
放大一个激励时必须检查它会不会打开新的作弊路径。

```
@4019  terrain_levels 0.0012
@4384  0.0122        ep_len 840   track 2.04
@4774  0.1398
@5794  1.8320        ep_len 761   track 1.77   ← 地形变难，指标回落
@6259  2.8417        ep_len 845   track 1.98   ← 适应后回升
@6519  3.2876        ep_len 859   track 2.07

```

这是教科书式的课程学习：**升级 → 变难 → 指标回落 → 适应 → 回升 → 再升级**。
`ep_len` 与 `track` 的短暂下降不是退步，而是任务本身变难了。

调参后 `Mean episode length`（908）低于调参前（960），
`time_out` 占比也更低 —— 这**恰恰是好事**：调参前机器人站在最简单地形上不动，
自然能撑满整个 episode；现在它在难度 4 的地形上主动行走，偶尔摔倒是合理代价。
`bad_orientation` 从 0.094 升到 0.186 是同一件事的另一面。

> 这印证了本实践最重要的一条教训：
> **`episode_length` 和 `reward` 上升，不等于任务学会了。**

### 7.3 训练中断与续训：一个关于 checkpoint 完整性的发现

训练在 9000 iter 时因外部原因中断，用 `--resume` 从 `model_9000.pt` 续训。
过程中暴露出一个值得记录的性质：

**`--resume` 只恢复策略与优化器，不恢复环境侧的课程进度。**

checkpoint 里只有四个键，`infos` 还是 `None`：

```python
{'iter': 9000, 'model_state_dict': ..., 'optimizer_state_dict': ..., 'infos': None}
```

而两个 curriculum 的状态都在环境侧：

| 课程 | 存放位置 | resume 后 |
|---|---|---|
| `terrain_levels` | `TerrainImporter.terrain_levels`，由 `torch.randint(0, max_init+1)` 初始化（`terrain_importer.py:347`） | 重新随机 |
| `lin_vel_cmd_levels` | `command_term.cfg.ranges`，随 env 重建复位 | 退回初始 ±0.1 |

实测续训瞬间：`lin_vel_cmd_levels` 1.0 → 0.1，`bad_orientation` 0.20 → 0.63
（机器人被扔到没挣到过的难度上）。

**当时的担心是它恢复不了**，因为命令课程的升级判据是
`reward > weight × 0.8 = 2.4`，而策略在难地形上只有 ~2.2，
且这个课程**只加不减**（`ranges` 单调放宽，没有收窄逻辑）。
原 run 之所以能爬满，是因为前 4000 iter 地形还停在 0 级、跟踪容易。

**实际结果是恢复了**：命令范围变窄后跟踪变容易，reward 越过 2.4 门槛，
课程重新逐级爬升，约 600 iter 后回到 1.0，地形等级随之回到 4.05。

```
9019  cmd_levels 0.10   ← 续训起点
9224  0.40
9364  0.70
9499  0.80
9999  1.00   terrain_levels 4.05   track 2.24   ← 完全恢复
```

> **结论**：这次续训的最终数据有效。但如果策略当时的 track reward 更低一些，
> 或剩余迭代数更少，课程就可能爬不回来 —— 那样得到的"最终指标"会是在
> **更容易的指令分布**下测出来的，看起来更好实则退化，且极难察觉。
> 长训练中断后不能直接 `--resume` 了事，**必须先确认课程指标回到中断前水平**。

配套地，`scripts/finish_p2.sh` 的指标提取改为按 step 区间自动串联续训链，
否则只会读到最后 1000 iter 那一段。

## 8. Sim2Sim 部署验证

课程要求把策略搬进 MuJoCo 验证。这一步的价值不只是"换个仿真器跑一遍"，
而是**用一套独立实现去反查训练侧的隐式约定**：训练框架里很多东西是自动完成的
（观测拼装顺序、缩放、PD 控制），部署侧必须手工复现，任何一处不一致都不会报错，
只会让行为不对。

### 8.1 MuJoCo raycaster 插件

粗糙地形的 `height_scanner` 在 MuJoCo 侧由第三方插件
`mujoco.sensor.ray_caster` 提供，必须在 MuJoCo **源码树内**编译，
且版本与 Python 运行时严格一致（否则 ABI 不兼容）。

插件（上游最后更新 2026-04）与 MuJoCo 3.12.0 之间有三处 API 断裂：

| # | 上游改动 | 处理 |
|---|---|---|
| ① | `mjtnum.h` 改名为 `mjtype.h`（12 处 include 失效） | 加转发头，插件源码零改动 |
| ② | `mjthread.h` 与整套旧线程 API 被删除 | 加串行语义兼容层，插件源码零改动 |
| ③ | `mjPLUGIN_LIB_INIT` 变成带参宏 | 无法用头文件绕开，改插件源码 1 处 |

② 值得展开：新的 `mju_threadpool` 只能设置引擎内部线程数，不再向插件暴露
任务队列，**无法 1:1 迁移**。但插件用它做的是射线分段并行——把 `[0, nray)`
切成互不相交的区间，各段之间无共享写。因此"入队时同步执行"与"并行后 join"
**语义完全等价**，只是变成串行。本项目 187 根射线，串行开销可忽略。

另外本机 gcc 11.4 对 MuJoCo 自身碰撞代码报 `-Wuninitialized` 误报，
被 `-Werror` 升级成错误，放宽为 `-Wno-error`。

全流程固化在 `scripts/build_raycaster_plugin.sh`（幂等，含版本一致性检查与加载验证）。

### 8.2 观测契约核对

跨仿真器的第一件事是确认两侧观测完全一致。MuJoCo 侧实测：

| 观测项 | 单帧 | 历史 | 小计 |
|---|---|---|---|
| `base_ang_vel` | 3 | 5 | 15 |
| `projected_gravity` | 3 | 5 | 15 |
| `velocity_commands` | 3 | 5 | 15 |
| `joint_pos_rel` | 29 | 5 | 145 |
| `joint_vel_rel` | 29 | 5 | 145 |
| `last_action` | 29 | 5 | 145 |
| `height_scanner` | 187 | 5 | 935 |
| **合计** | **283** | | **1415** |

与 §3.4 的训练侧配置逐项吻合，`height_scanner` 的 17×11=187 也对得上。

### 8.3 量化评估（而不是看录像）

课程给的 `sim2sim_raycaster.py` 只能键盘下发指令、肉眼看视频。
但**本实践已经栽过一次**：`episode_length` 和 `reward` 全线上涨，
录像里机器人却在原地踏步（§6.1）。所以部署侧也必须量化 ——
给定指令，量出实际速度、净位移与姿态。

为此另写了 `sim2sim/eval_rough_headless.py`：复用课程的观测拼装与控制链路
（第三方代码零改动），只替换掉"键盘输入 + 实时渲染"这一层。

自训策略（`model_9999` 导出的 `policy.pt`）实测：

| 指令段 | cmd vx | 实际 vx | cmd yaw | 实际 yaw | 净位移 |
|---|---|---|---|---|---|
| 站立 | 0.00 | 0.000 | 0.00 | −0.014 | 0.008 m |
| 前进 | 0.50 | **0.484** | 0.00 | −0.229 | **3.04 m** |
| 前进+转向 | 0.50 | **0.502** | 0.50 | 0.140 | **3.78 m** |
| 停止 | 0.00 | 0.079 | 0.00 | −0.008 | 0.124 m |

姿态：投影重力 z 均值 **−1.000**（直立为 −1.0），全程未摔倒。
离地高度（扫描估计）均值 0.331 m，最低 0.247 m。

与课程自带 checkpoint 的横向对照：

| | 课程 checkpoint | 自训策略 |
|---|---|---|
| 前进 vx（cmd 0.50） | 0.535 | 0.484 |
| 前进+转向 vx | 0.403 | **0.502** |
| 投影重力 z 均值 | −0.998 | **−1.000** |
| 是否摔倒 | 否 | 否 |

自训策略在纯前进段略慢，但在**前进+转向**这种复合指令下反而更稳
（0.502 vs 0.403），姿态也更直。

> 有对照基准才能判断"好不好"。只看自训策略的 0.484 无法知道它是否正常，
> 有了课程 checkpoint 的 0.535 作参照，才能说"同一量级、可接受"。

坐标系细节：实际速度是把世界系线速度按四元数转回**机体系**后再与指令比较 ——
指令本身就定义在机体系，直接比世界系速度在机器人转向后会完全对不上。
离地高度用高度扫描估计而非世界系 z，与 §4 修正终止判据踩的是同一个坑。

## 9. 结论与遗留问题

### 完成的改动

| 层次 | 内容 |
|---|---|
| 地形 | 平地 → `ROUGH_TERRAINS_CFG`，10 级难度课程 |
| 感知 | 启用 `height_scanner`，187 维高度图接入 policy（加噪）与 critic（不加噪） |
| 观测 | 单帧 96 → 283 维，×5 帧历史 → 1415 维 |
| 判据 | `base_height` 的奖励与终止改用相对地形高度，带 `inf` 防护 |
| 奖励 | 重设 10 项权重，打破"站着不动"局部最优 |
| 动作 | 保持 29 维关节位置控制不变 |
| 部署 | 编译 raycaster 插件（适配 MuJoCo 3.12 三处 API 断裂），跨仿真器量化验证通过 |

### 方法论收获

1. **诊断的决定性一步是把 `Episode_Reward/*` 全部拆开排序** ——
   总分正常时，分项能暴露策略实际在靠什么拿分。
2. **"什么都不做"是奖励函数里的隐藏强势策略**，因为几乎所有惩罚项
   都是对"做事"收费的。设计完奖励先问："如果它一动不动，能拿多少分？"
3. **exp 型奖励的权重 = 该项上限**，直接决定它能提供多大的边际激励。
4. **放大一个激励时同步检查是否打开新的作弊路径**。
5. **世界系绝对高度的判据，换到非平地一律要重新审视** ——
   本实践在 `base_height`（奖励+终止）和 `feet_clearance` 三处都栽在这上面。
6. **验收标准要跟着任务一起搬到部署侧。** 训练侧已经学会"不看 reward 看分项"，
   部署侧同样不能靠看录像——`eval_rough_headless.py` 把"能不能走"变成了
   可回归的数字，并且必须有对照基准才能判断数值是否正常。
7. **长训练中断后不能直接 `--resume` 了事。** checkpoint 只含策略与优化器，
   环境侧的课程进度会丢失；必须确认课程指标回到中断前水平，
   否则"最终指标"是在更容易的指令分布下测出来的（§7.3）。

### 遗留

- `track_ang_vel_z` 只拿到上限的 34%（`error_vel_yaw` 1.27）。根因是
  `ang_vel_z` 的 `limit_ranges` 仅 ±0.2 rad/s 而奖励权重给到 2.0，
  **权重与指令幅度不匹配**，下一轮应同步调整两者。
- `feet_air_time`（0.0170）仍低于官方参考（0.0295），步态的腾空相还可优化。
- 可视化的键盘控制 sim2sim 尚未人工试玩（量化评估已通过，属锦上添花）。
