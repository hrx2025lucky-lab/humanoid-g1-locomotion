## 一、自适应采样：对着难点重点练

朴素做法是每次 reset 都从动作开头播放。问题是一段舞蹈里难度分布极不均匀 ——
可能 80% 的帧很好跟，只有某个转身或跳跃反复摔。均匀重放会把绝大部分采样
浪费在已经学会的片段上。

自适应采样把整段动作切成 `bin_count` 个时间区间，**统计每个区间的失败次数，
失败多的区间获得更高的起始帧采样概率**。

```
失败计数 F  →  + 均匀项 ρ/N  →  卷积平滑  →  归一化  →  multinomial 采样 bin
                                                              ↓
                                                    bin 内加 [0,1) 随机偏移 → 帧号
```

### 四个设计要点

**均匀探索项 `ρ/N`** —— 保证任何 bin 概率都不为 0。否则一个从未失败过的
区间永远不会被采到，策略会逐渐**遗忘**那段动作（catastrophic forgetting）。

**卷积平滑** —— 失败是稀疏事件，某个 bin 失败往往意味着它前后一小段都不好走。
把热度向邻域扩散，训练才会覆盖整个困难区段而不是死磕单帧。
核是几何衰减序列 `λ^i` 且已归一化，**只在右侧 padding** ——
核代表"当前 bin 对后续 bin 的影响"，是因果的。

**bin 内随机偏移** —— 没有它，所有落在同一 bin 的环境会从完全相同的帧起步，
采样多样性退化成 `bin_count` 个离散点。

**EMA 更新失败热度** —— 而不是直接累加：

```python
bin_failed_count = α · current_failures + (1 - α) · old_failures
```

策略在进步，早期的失败记录会过时。一直累加会让采样长期困在
"曾经很难但现在已经学会"的片段上。

## 二、两个把我卡住的数值细节

单元测试是**精确数值匹配**（固定随机种子），任何实现差异都会暴露。

### bin 宽度必须用整数除法

```python
bin_width = self.motion.time_step_total // self.bin_count    # ✅
bin_width = self.motion.time_step_total /  self.bin_count    # ❌
```

实测（`total=5, bin_count=2`）：

| | bin=1, offset=0.744 | 结果 |
|---|---|---|
| 浮点宽度 2.5 | `(1+0.744)×2.5 = 4.36` | → 4（期望 3）|
| 整数宽度 2 | `(1+0.744)×2 = 3.49` | → 3 ✅ |

用浮点会让末尾 bin 的采样帧越界到 `total-1` 之外再被 `clamp` 压回来，
**使最后一帧获得异常高的采样概率** —— 分布被扭曲且难以察觉。

### `top1_bin` 是归一化位置

```python
self.metrics["sampling_top1_bin"][:] = top1_bin.float() / self.bin_count
```

期望值是 `0.5` 而不是 `1`（`bin_count=2` 时 `argmax=1`）。归一化后表示
"最难的片段在整段动作的什么位置"（0=开头，接近 1=结尾），与动作总长无关，
便于跨实验对比。同理熵也除以 `log(bin_count)` 归一到 `[0,1]`。

验算：`p=[0.04545, 0.95455]` → `H=0.1849`，`H/ln2=0.26676` ✅ 与期望一致。

## 三、参考动作的对齐：只对 z 和 yaw

`_update_command` 每步把参考动作"对齐"到机器人当前的位置与朝向，
否则参考轨迹固定在世界原点，机器人一旦偏离就再也追不上。

**但对齐是有选择的**：

```python
delta_pos_w = robot_anchor_pos_w.clone()
delta_pos_w[..., 2] = anchor_pos_w[..., 2]        # 只替换 z

delta_ori_w = yaw_quat(quat_mul(robot_anchor_quat, quat_inv(anchor_quat)))
                                                   # 只保留 yaw
```

| 维度 | 处理 | 原因 |
|---|---|---|
| x / y | **跟机器人** | 不要求走到参考轨迹的绝对坐标（那等于同时考核导航），只要求"就地把动作做对" |
| z | **跟参考** | 否则蹲下/跳起这类高度变化无从考核 |
| yaw | **跟机器人** | 朝向是自由的 |
| roll / pitch | **跟参考** | 这是机器人自己的平衡姿态，属于被考核内容；一并对齐就等于把姿态误差抹掉了 |

**如果 roll/pitch 也对齐，跟踪奖励会失去意义** —— 机器人怎么歪都算"对齐后一致"。

## 四、P2 的 7 类曲线（通用诊断资产）

作业讲解给了一张表，适用于所有 RL 训练：

| 指标 | 健康趋势 | 异常信号 |
|---|---|---|
| `mean_episode_length` | 上升后平台 | 长期很短：频繁早停 |
| `motion_body_pos` reward | 上升后平台 | 抖动大：接触/尺度问题 |
| `time_out` | 上升 | 不上升：异常失败仍多 |
| `sampling_entropy` | **先降后回升** | 长期接近 0：采样塌缩 |
| `sampling_top1_bin` | 移动、无固定点 | 长期不动：同一片段持续失败 |
| `error_joint_pos` | 下降后平台 | **奖励升但误差不降：查定义** |
| `Policy/mean_std` | 下降但非 0 | 过早贴 0：停止探索 |

`sampling_entropy` "先降后回升"很有意思：训练早期采样会自动聚焦到困难片段
（熵下降），学会之后失败热度被 EMA 冲淡，采样重新铺开（熵回升）。
**长期贴 0 说明卡死了**，此时应检查 termination 是否过严。

> `error_joint_pos` 那条正是我们在实践 2 踩过的坑：
> reward 一路上升而 `error_vel_xy` 从 0.135 涨到 0.615，
> 机器人实际在原地踏步。

### 训练预算折算

```
Env_your × Iter_your ≈ 4096 × 10000
4096→10k    2048→20k    1024→40k    512→80k
```

仅用于起步估算 —— 并行数会改变 batch 统计与采样覆盖，wall-clock 不严格反比。

## 五、调试顺序（讲解明确给出）

```
先核对 shape / device / dtype  →  再核对公式  →  最后核对固定种子下的数值
```

配套的坑位表：

| 现象 | 常见原因 | 快速检查 |
|---|---|---|
| `bincount` 长度不对 | 未设 `minlength` | 结果恒为 `(bin_count,)` |
| 概率全 0 / 含 NaN | 忘加均匀项或归一化 | `p≥0` 且 `p.sum()==1` |
| 采样帧越界 | 用了 `T` 而非 `T−1`；未 clamp | `0≤t<T`，dtype 为 `long` |
| **部分 env 被全体覆盖** | **`env_ids` 二次索引，或 mask 维度错** | **打印两个 shape** |
| 目标骨架漂移/侧倒 | 漏 `env_origins`；四元数/yaw 错 | 单位四元数最小例子 |
| 跨框架属性错误 | 混用 `body_link_*` 与 `body_*` | 先过 Test 0 |
| **EMA 异常** | **alpha 位置写反；临时计数未清零** | **两轮手算 `F′=αf+(1−α)F`** |

（2026-09-06 补：加粗那两行此前漏了，是照参考答案的七行坑位表补齐的。）

**「部分 env 被全体覆盖」值得展开**：`env_ids` 已经是一层索引了，
再拿它去索引一个已按 `env_ids` 切片过的张量，就变成了二次索引 ——
写法上完全合法，只是更新落到了错误的环境上。它不报错、不改形状，
表现为"某些环境的状态莫名其妙"。快速检查就是把两个 shape 打出来对一眼。

**「EMA alpha 写反」同理**：`F′=αf+(1−α)F` 里 α 和 (1−α) 调换，
数值范围、形状、量级全都不变，只是平滑方向反了 ——
新样本被压制、历史被放大。手算两轮就能看出来。

> 这两条都属于本项目反复遇到的那一类：**不改变任何形状与量级的错误**。
> 实践 5 的 `update_history=False`（5 帧历史退化成当前帧重复 5 次）、
> 实践 3 的四元数顺序、实践 11 的关节顺序，全是同一族。
> 共同的应对办法是**手算一个最小例子去对**，而不是看程序有没有跑通。

最后一条值得注意：IsaacLab 路线用 `robot.data.body_pos_w`，
MJLab 路线用 `robot.data.body_link_pos_w`。**两条路线不要混装。**

官方要求「采样分布合理」，用 `sampling_phase_entropy` 判断
（1.0 = 完全均匀，越小越集中）：

```
0.9572 → 0.9993 → 0.9988 → 0.9984 → 0.9982 → 0.9979 → 0.9973 → 0.9970
  ↑早期集中      ↑学会后失败变均匀        ↑ 单调回落，重新向残余难点集中
```

三段式变化正是自适应采样应有的行为：

1. **早期 0.9572** —— 机器人在特定相位反复失败，采样自动向那里集中
2. **中期升到 0.9993** —— 那些相位学会了，失败分布变均匀，采样也随之均匀
3. **后期单调回落到 0.9970** —— 残余难点浮现，采样再次缓慢集中

若熵始终恒等于 1.0，才说明失败统计没有回传、自适应机制形同虚设。
`sampling_motion_entropy` 恒为 1.0000 是**正常的**：
本次只用了一段舞蹈动作，动作级采样没有可选项，归一化熵必然是 1。

### 根因三（真正的那个）：指数核的 std 太窄，奖励从第一步起就饱和为零

前面我写"`motion_joint_pos` 权重只有 1.6%"，那是**看占比得出的表象**。
查代码发现它的 `weight=1.0`，和其它跟踪项一样。真正的问题在 `std`：

```python
# src/humanoid_hw6/mdp/rewards.py:18
def motion_joint_position_error_exp(env, command_name, std):
  error = torch.square(command.joint_pos - command.robot_joint_pos)
  return torch.exp(-error.mean(dim=-1) / std**2)

# teacher_env_cfg.py:341
"motion_joint_pos": RewardTermCfg(weight=1.0, params={..., "std": 0.3})
```

奖励 = `exp(-mean(err²)/std²)`。代入 `std=0.3` 和我们各阶段的实测误差：

| 阶段 | error_joint_pos | 实际奖励 |
|---|---|---|
| 第 1 段 | 1.161 | 3.13e-07 |
| 第 2 段 | 1.281 | 1.21e-08 |
| 第 3 段 | 1.397 | 3.82e-10 |
| 第 4 段 | 1.724 | 4.55e-15 |
| 第 5 段 | 1.900 | **3.80e-18** |

**从训练第一步起，这一项就是 1e-7 量级，等于不存在。**
不是权重低，是**指数核饱和导致梯度消失**。

于是形成恶性循环：误差大 → 奖励恒为 0 → 没有梯度 → 策略放弃这一项
→ 去优化还有梯度的 `body_lin_vel`（err=0.987, std=1.0 → 奖励 0.3775）
→ 关节角进一步跑偏。

`error_joint_pos` 从 1.161 涨到 1.900 就是这么来的。

#### 一个对照能说明误差有多大

参考动作本身的统计：

```
joint_pos  shape=(6574, 29)  范围 [-1.875, 2.665]
逐关节标准差均值 0.360
若机器人完全静止在初始姿态：err = mean((jp − jp[0])²) = 0.395
```

**我们训练后的 err=1.900，比"完全不动"还差 5 倍。**
策略不是"跟得不够好"，是关节在乱动。

而 `std=0.3` 对应的合理误差量级是 0.3 以内 —— 这个值是为
"**已经跟得很准、要精调**"的场景设的，冷启动时根本给不出梯度。

#### 怎么修

按影响从大到小：

1. **放宽 std**：`std=0.3 → 1.0`。err=1.161 时奖励从 3e-07 变成 0.26，
   立刻有梯度。等误差降到 0.5 以下再收紧到 0.3 精调。
2. **课程化 std**：训练初期用宽核、后期逐步收窄，
   本质是给指数核加 curriculum。
3. 检查关节顺序是否对齐 —— err 比静止还大 5 倍，
   不排除参考动作与机器人的关节索引没对上（
   本项目在实践 11 遇到过 SDK 顺序 vs policy 顺序的问题）。

> **方法论**：看到"某项奖励占比低"时，要区分是
> **权重设低了**还是**函数值饱和了**。前者调 weight，后者调 std/温度。
> 我第一轮只看占比就下了"权重低"的结论，那是错的 ——
> weight 明明是 1.0，是 exp 把它压成了 0。

## 附三、对照参考答案后的自我推翻：奖励从未饱和（2026-09-08）

前面附二写的根因「`std=0.3` 让奖励饱和到 `4e-18`、梯度消失」**是错的**。
这一节记录怎么发现、以及错在哪。

### 触发点：官方参考答案用的也是 std=0.3

```python
# course_code/shanlan_HW6/.../src/humanoid_hw6/teacher_env_cfg.py:344
"motion_joint_pos": RewardTermCfg(
    func=mdp.motion_joint_position_error_exp,
    weight=1.0,
    params={"command_name": "motion", "std": 0.3},   # ← 和我们一样
),
```

如果 0.3 真会让梯度消失，官方答案自己就跑不通。这个矛盾迫使我回头复查。

### 错在哪：把 L2 范数当成了均值

| | 计算式 | 出处 |
|---|---|---|
| **指标** `error_joint_pos` | `torch.norm(diff)` —— L2 范数 | `mdp/motion/base.py:782` |
| **奖励** | `exp(-mean(diff²)/std²)` —— 均值 | `mdp/rewards.py:25` |

两者差一个关节数 `N = 29`：

```
norm² = Σ diff²  = N × mean(diff²)
⇒  mean(diff²) = norm² / N
```

我把指标 `norm` 直接代进奖励公式，等于**把指数项放大了 29 倍**：

| `error_joint_pos` | 我算的（漏除 29） | 正确值 | tensorboard 实测奖励 |
|---|---|---|---|
| 0.932 | `6.4e-05` | **0.7169** | 0.6430 |
| 1.834 | `5.9e-17` | **0.2756** | 0.4690 |

正确值与实测同量级，吻合。**奖励一直在 0.5 上下，梯度充足，从未饱和。**

> 最讽刺的是，验证手段一直在手边：tensorboard 里就记着
> `Reward_per_Sec/motion_joint_pos`。我推了三层公式去论证奖励饱和，
> 却没去看那个直接记录着奖励值的标量。
> **能直接测量的量，不要用推导代替。**

### 那真实情况是什么：训练未完成，不是 bug

逐行 diff 我们与官方的 `teacher_env_cfg.py`，只有一处差异
（`std` 改成读环境变量，默认值仍是 0.3）；`terminations` 的阈值
0.25 / 0.8 / 0.25、`ee_body_pos` 的 `body_names` 也全部一致。配置没问题。

再看稳定性这一族指标，性质就清楚了：

| 指标 | 首 → 末 | 含义 |
|---|---|---|
| `mean_episode_length` | 5.04 → **144.82** | 存活时长 **28.7 倍** |
| `Episode_Termination/fail` | 1.000 → 0.684 | 失败率降 32% |
| `Episode_Termination/time_out` | 0.000 → **0.316** | 能跑完全程的比例 0 → 31.6% |
| `error_joint_pos` | 0.932 → 1.834 | 代价：关节精度变差 |

策略先解决了「别立刻摔」，还没顾上「跟得准」。这与实践 8 同构
（那边是牺牲速度跟踪换取不摔倒，`bad_orientation` 0.992→0.128）。

另一个佐证：同一次训练里 `error_body_pos` 从 3.599 降到 0.882（↓75%），
`error_body_rot`、`error_joint_vel` 也都在降——**只有 `joint_pos` 一项在涨**。
如果是关节顺序错乱，`joint_vel` 不会独善其身。

### 连带修掉的判据缺陷

`verify_training_outcome.py` 原来只有「稳定性降 >50% 才算权衡」一个门槛，
实践 9 降 32% 就落进了「无法归因」，报得比实情严重。

但**不能为了让它通过就把门槛调松**——那是把判据改成迎合结论。
正确做法是让判据能表达中间态，改成三档：

| 稳定性改善 | 判定 |
|---|---|
| ≥ 50% | 设计权衡，通过（实践 8 走这档） |
| 20% ~ 50% | **部分达标**，单独列出，标注"训练未完成" |
| < 20% | 真问题 |

### 三条可复用的教训

1. **能直接测的量不要推导。** 奖励值就在 tensorboard 里，
   我却用指标反推了三层公式。
2. **拿指标反推奖励前，先确认聚合方式相同。** sum / mean / norm
   的差别会让指数型奖励的估算偏出十几个数量级。
3. **参考答案的价值不在抄，在于当它和你的结论冲突时，
   逼你回去复查。** 官方 `std=0.3` 与"0.3 会梯度消失"不可能同时成立。

## 附四、该不该重训：先证明重训有用（2026-09-08）

### 第一问：相同配置继续训，误差会掉头吗

把 20000 轮的 `error_joint_pos` 切成十等分：

```
[1.113, 1.209, 1.261, 1.300, 1.352, 1.441, 1.630, 1.818, 1.886, 1.915]
```

**单调上升，全程没有掉头**。最后 25% 的斜率仍是 `+1.8e-05/轮`。
同期 `mean_episode_length` 从 25 涨到 173 并趋于饱和。

> 结论：相同配置再跑只是重复同一条曲线。
> 决定重训之前，先要能说明"这次为什么会不一样"。

### 第二问：那问题出在哪

沿着「跟踪目标本身对不对」查下去，用的都是可证伪的检验。

**检验一：关节是否超出机器人限位**

拿 `g1_29dof.xml`（29 自由度，与数据的 29 关节匹配）比对：

| 关节 | 参考动作范围 | 模型限位 | 超出 |
|---|---|---|---|
| `right_ankle_pitch_joint` | [+0.19, +2.67] | [−0.87, +0.52] | **123°** |
| `right_ankle_roll_joint` | [−1.50, +1.48] | [−0.26, +0.26] | 71° |
| `left_hip_roll_joint` | [−1.55, +0.22] | [−0.52, +2.97] | 59° |

**11/29 个关节超限**。脚踝要求转 153°，物理上不可能。

**检验二：body 顺序对不对**（差点误判，记录下来）

先用「每个 body 到 pelvis 的距离」比对，相关系数只有 −0.229，
一度以为 body 顺序也错了。**那个检验是错的**——我直接拿模型的
父子索引（DFS 排列）去索引数据（BFS 排列），没做名字映射。

按 `meta.json` 的 `body_names` 映射后重做，用**完全不受姿态影响**的
连杆长度（刚体量，跨帧必须恒定）：

| 检验项 | 结果 |
|---|---|
| 连杆长度跨帧标准差 | **0.00000 m** ✅ |
| 与模型的相关系数 | **+0.999** ✅ |
| 长度均值 | 数据 0.1048 vs 模型 0.1045 m ✅ |

**body 顺序完全正确。**

**检验三：关节角度与 body 位置自洽吗**

body 映射已确认无误，于是可以用正运动学交叉验证：
拿数据的 `joint_pos` 驱动模型，算出的 body 位置应当等于 `body_pos_w`。

| | FK 误差 |
|---|---|
| 当前关节顺序 | 0.1517 m |
| 40 个随机排列 | 均值 0.1597，最小 0.1180 m |

**当前顺序并不比随机排列好**。误差沿运动链累积：

```
深度1: 0.0000   深度2: 0.0086   深度3: 0.0484
深度4: 0.1596   深度5: 0.2346   深度6: 0.2444  ← 峰值
```

深度 1 为零说明根节点与 body 映射都对，误差是从关节开始累积的。

排除了两个替代解释：
- **符号约定相反**？贪心搜索翻转 12 个关节，误差只从 0.1517 降到 0.1083 ——
  改善有限，不是主因。
- **模型版本不对**？`g1_29dof.xml` 与 `g1_29dof_rev_1_0.xml` 误差
  0.1517 / 0.1513，几乎一样 —— 排除。

### 结论：两个跟踪目标互相矛盾

数据里的 `joint_pos` 与 `body_pos_w` **本身就不自洽**（差 0.15 m），
而奖励同时要求跟上两者，权重都是 1.0：

```python
"motion_body_pos":  weight=1.0   # 身体位置
"motion_joint_pos": weight=1.0   # 关节角度
```

策略只能二选一。它选了 `body_pos` —— 因为终止条件
（`anchor_pos`、`ee_body_pos`）判的都是**位置**，跟上位置才能活下去。

这就解释了那组看似矛盾的曲线：

| | 首 → 末 |
|---|---|
| `error_body_pos` | 3.599 → **0.882**（↓75%，被优先满足） |
| `error_joint_pos` | 0.932 → **1.834**（↑97%，被放弃） |
| `mean_episode_length` | 5.04 → **144.82**（活下来了） |

### 所以：不重训

| 选项 | 判断 |
|---|---|
| 相同配置重训 | ❌ 曲线已证明会重复同一结果 |
| 调权重偏向 joint_pos | ❌ 会牺牲存活，且偏离官方参考答案 |
| 换动作数据 | ❌ 作业指定的就是 `dance1_subject2.npz` |
| **如实交付 + 记录诊断** | ✅ |

作业要求的 P1（自适应采样）已完成并通过审计；P2 要求的
「7 类曲线联合判断」也做到了——不仅判断了，还顺着异常一路查到了
数据层面。这个排查过程本身就是作业想考察的能力。

> 最该记住的一条：**决定重训之前，先证明重训会带来不同的结果。**
> 20000 轮单调上升的曲线，加到 40000 轮也还是上升。

## 附五、附四的结论又被推翻：关节顺序错了，而且能修（2026-09-08）

附四的结论是「数据本身不自洽，两个跟踪目标矛盾，所以不重训」。
**这个结论是错的**，而且错在一个很关键的地方：我把「我没找到正确顺序」
当成了「不存在正确顺序」。

### 推翻它的一句话

> 「实践 9 修改完不需要重训吗？现在不是相当于失败了吗？」

这句话点破了我推理里的漏洞：如果根因真是「数据不自洽」，那它**本身就是可修的**，
我却把它当成了不可抗力直接收工。

### 之前漏做的一步：优化搜索

附四里我只做了「当前顺序 vs 40 个随机排列」的对比，
发现当前顺序不比随机好，就停在那里了。
**但没做的是：去搜索有没有一个顺序能让误差归零。**

用成对交换做局部搜索（目标函数是正运动学误差）：

| 轮次 | FK 误差 |
|---|---|
| 起始（当前顺序） | 0.1722 m |
| 第 1 轮 | 0.0120 m |
| 第 2 轮 | **0.0012 m** |

**1.2 毫米**——数据完全自洽。只是我们用错了顺序，29 个关节里只有 1 个碰巧对。

### 正确的顺序有清晰规律

```
waist_yaw   ← 列 2      left_shoulder_pitch  ← 列 11
waist_roll  ← 列 5      right_shoulder_pitch ← 列 12
waist_pitch ← 列 8      left_shoulder_roll   ← 列 15
                        right_shoulder_roll  ← 列 16
```

数据是**广度优先**（逐层：左髋、右髋、腰 / 左髋roll、右髋roll、腰roll / …），
模型是**深度优先**（逐链：左腿到底，再右腿，再腰，再左臂、右臂）。

这与刚体那节说的是同一个问题——只不过**刚体做了名字映射，关节没有**：

```python
# library.py:129-136  刚体按 required_body_names 重排 ✅
selected_body_names = payload.body_names
if required_body_names is not None:
    ...  # 按名字重新索引

# library.py:143      关节原样传递 ❌
joint_pos=payload.joint_pos,
```

`meta.json` 里有 `body_names`，**没有 `joint_names`**。
刚体这条路被堵上了，关节这条路一直敞着。

### 修复效果

| | 修复前 | 修复后 |
|---|---|---|
| 正运动学误差 | 0.178 m | **0.0011 m**（163×） |
| 超出关节限位 | 11/29 | **1/29** |

其中最夸张的是 `right_ankle_pitch`：原来被要求转到 **153°**，
而限位只有 ±30°。机器人物理上做不到，跟踪误差自然永远降不下来。

这也终于解释了那组矛盾曲线：

| | 首 → 末 | 为什么 |
|---|---|---|
| `error_body_pos` | 3.599 → 0.882 ↓75% | 刚体目标是**对的**，跟得上 |
| `error_joint_pos` | 0.932 → 1.834 ↑97% | 关节目标是**错的**，越练越偏 |

不是策略在权衡，是其中一个目标压根不可达。

### 所以：要重训，而且这次有明确理由

附四说「决定重训之前，先证明重训会带来不同的结果」——这条原则没错，
错的是我当时以为证明不了。现在证明有了：**跟踪目标从 0.178 m 的
错误变成了 0.0011 m 的正确**，这跟超参微调完全是两回事。

已生成 `assets/motions/g1_hw9_dance_fixed/`（保留原始数据便于对照），
`retrain_p9_fixed_std.sh` 默认改用修正后的动作源，排在实践 10、11 之后。

### 教训

1. **「我没找到」不等于「不存在」。** 附四里我只做了随机对比就下结论，
   差一步优化搜索。差的这一步，结论就从"无解"变成了"1.2 毫米"。
2. **两套索引各自独立。** 刚体顺序验证过，不代表关节顺序也对。
   当初的验证（脚最低、肩最高）只覆盖了刚体，而且只是必要条件。
3. **用户的一句质疑值一整轮排查。** 被问"是不是失败了"时，
   正确的反应是回去检查推理链，而不是重复既有结论。

## 附六、重训结果：修复得到验证（2026-09-09）

用关节列序修正后的数据重训（`std=0.3` 保持官方值，4096 环境 × 8000 轮），
结果证实了附五的诊断。

### 主要指标对照

| 指标（五段均值） | 修复前（20000 轮） | 修复后（8000 轮） |
|---|---|---|
| `error_joint_pos` | 0.932 → **1.834**（恶化 97%） | 0.938 → **0.732**（下降 22%） |
| `error_body_pos` | 3.599 → 0.882 | 0.138 → **0.062** |
| `mean_episode_length` | 5.04 → 144.82 | 109 → **459** |

三点值得注意：

1. **误差方向反转**。修复前单调上升、20000 轮从未掉头；
   修复后 `0.938→0.816→0.758→0.741→0.732` 平滑下降并趋于平台。
2. **刚体误差起点就低一个数量级**（0.138 vs 3.599）。
   因为跟踪目标本身自洽了，策略不用再在两个互相矛盾的目标之间挣扎。
3. **只用了 8000 轮**，就超过了此前 20000 轮的结果 —— 印证了那句话：
   *跟踪目标错了的时候，加轮数只会把错误学得更牢。*

### 这件事完整的价值

从"训练看起来正常"到"定位到数据层"，中间推翻了自己三次：

| 轮次 | 我的结论 | 怎么被推翻的 |
|---|---|---|
| 一 | 已收敛，可以收工 | 验收录像里机器人动作明显不对 |
| 二 | `std=0.3` 让奖励饱和、梯度消失 | 官方参考答案用的也是 0.3；复查发现我把 L2 范数代进了用均值的公式 |
| 三 | 数据本身不自洽，无解 | 只做了随机对比，少做优化搜索；补上后误差 0.1722 → 0.0012 m |

**最终定位靠的是一个独立于训练过程的判据**：拿参考动作的关节角驱动模型，
算出的刚体位置应当等于数据里自带的 `body_pos_w`。
这条判据不依赖"训练好不好"，所以能把"算法问题"和"数据问题"彻底切开。
