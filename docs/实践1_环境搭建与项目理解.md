## 一、三套仿真栈的分工

课程用了三个仿真器，各自解决不同问题：

三套栈装在**三个互相隔离的虚拟环境**里，版本各不相同（实测）：

| 环境 | 仿真器 | 版本 | 角色 | 用在哪些实践 |
|---|---|---|---|---|
| `envs/isaaclab`<br>(Py 3.11.15) | **Isaac Sim** | 5.1.0.0 | 渲染 + PhysX 物理后端 | 1、2、3、5、7、8、10、11 |
| | **Isaac Lab** | 0.54.2 | Isaac Sim 之上的 RL 环境框架（Manager-Based） | 同上 |
| | **MuJoCo** | **3.12.0** | sim2sim 部署验证 | 2、3、11 |
| | torch | 2.7.0+cu128 | | |
| `hw4_mjlab/.venv` | **MuJoCo** | 3.8.1 | mjlab 的 CPU 侧 | 4 |
| | **MuJoCo Warp** | **3.9.0.1** | GPU 物理后端 | 4 |
| | torch | 2.9.0+cu128 | | |
| `hw6_distill/.venv` | **MuJoCo** | 3.6.0 | mjlab 的 CPU 侧 | 6、9 |
| | **MuJoCo Warp** | **3.6.0** | GPU 物理后端 | 6、9 |
| | torch | 2.10.0+cu128 | | |

**三个环境的 torch 版本各不相同（2.7 / 2.9 / 2.10）**，
这正是它们必须隔离的原因 —— 也是实践 11 卡住的根源：
`instinct_rl` 要 torch 2.11 + numpy≥2，装进 `envs/isaaclab` 会毁掉实践 1~10。

**为什么需要两套**：Isaac Sim 负责大规模并行训练（4096 环境），
MuJoCo 负责验证策略离开训练器后还能不能用 —— 这就是 sim2sim。
若策略只在 Isaac Sim 里能走，说明它学到的是训练器的数值特性而非控制策略。

> mjlab（实践 4/6/9）用的是 **MuJoCo Warp**，不是 MJX。
> 本机 jax/mjx 都没装也不需要，详见 `00_实践总览.md`。

## 二、项目理解 5 问（官方 §5.2）

以 `Unitree-G1-29dof-Velocity` 为例，仓库根目录
`repos/unitree_rl_lab/`（下文路径均相对于它）。

### 1. 任务入口在哪个文件

`source/unitree_rl_lab/unitree_rl_lab/tasks/locomotion/robots/g1/29dof/__init__.py`

```python
gym.register(
    id="Unitree-G1-29dof-Velocity",
    entry_point="isaaclab.envs:ManagerBasedRLEnv",
    disable_env_checker=True,
    kwargs={
        "env_cfg_entry_point":      f"{__name__}.velocity_env_cfg:RobotEnvCfg",
        "play_env_cfg_entry_point": f"{__name__}.velocity_env_cfg:RobotPlayEnvCfg",
        "rsl_rl_cfg_entry_point":   "...agents.rsl_rl_ppo_cfg:BasePPORunnerCfg",
    },
)
```

注意 `entry_point` 是 IsaacLab 的通用 `ManagerBasedRLEnv`，
**不是**某个任务专属的类。任务的全部特性都由 `kwargs` 里的三个 cfg 决定 ——
这是 Manager-Based 架构的核心：**行为由配置组装，而非由继承定义**。

### 2. 环境配置在哪个文件

`.../g1/29dof/velocity_env_cfg.py` 里的 `RobotEnvCfg`（训练）与 `RobotPlayEnvCfg`（播放）。

粗糙地形版本在子目录 `.../29dof/rough/`，实践 2 改的就是那里。

### 3. PPO 配置在哪个文件

`.../tasks/locomotion/agents/rsl_rl_ppo_cfg.py` 里的 `BasePPORunnerCfg`。

**它和环境配置分属不同目录**：环境配置按机器人组织
（`robots/g1/29dof/`），算法配置按任务族组织（`agents/`）。
同一套 PPO 超参可以被多个机器人复用。

### 4. 训练入口在哪个文件

`scripts/rsl_rl/train.py`，同目录还有 `play.py`（回放）与 `cli_args.py`（参数解析）。

### 5. checkpoint 保存在哪类目录

`logs/rsl_rl/{experiment_name}/{时间戳}_{run_name}/model_{iter}.pt`

本机实例：

```
logs/rsl_rl/unitree_g1_29dof_velocity/2026-08-31_10-49-33/exported/policy.pt
logs/rsl_rl/unitree_g1_29dof_velocity_rough/2026-09-02_20-03-39/model_9999.pt
```

`experiment_name` 来自 PPO 配置（第 3 问那个文件），
所以**改实验名就能把 checkpoint 分开**——这正是实践 5/8 做对照实验时用的手法。

## 三、简短分析 3 问（官方 §5.3）

### 1. 从 `--task` 到实际环境创建的流程

```
python train.py --task Unitree-G1-29dof-Velocity
        │
        ├─ AppLauncher 启动 Isaac Sim（必须在任何 isaaclab 导入之前）
        │
        ├─ import unitree_rl_lab.tasks
        │     └─ 触发各 __init__.py 里的 gym.register(...)
        │
        ├─ parse_env_cfg(task) → 按 env_cfg_entry_point 取出 RobotEnvCfg
        │     └─ 用 --num_envs / --device 等命令行参数覆盖
        │
        ├─ gym.make(task, cfg=env_cfg)
        │     └─ ManagerBasedRLEnv.__init__ 依次构建：
        │          SceneCfg → 地形/机器人/传感器
        │          ObservationManager / ActionManager / RewardManager
        │          TerminationManager / CommandManager / CurriculumManager / EventManager
        │
        └─ OnPolicyRunner(env, agent_cfg) → 训练循环
```

**关键点**：`gym.register` 只登记了"配置在哪"，真正的环境对象是
`gym.make` 时由各 Manager 按配置**组装**出来的。
所以调环境行为不需要改类，只要改配置 —— 这也是为什么实践 2~11
的作业几乎都是在改 `*_env_cfg.py`。

> 踩过的坑：`AppLauncher` 必须最先执行。任何 `isaaclab` 的导入都依赖
> Isaac Sim 已启动，否则报 `ModuleNotFoundError: No module named 'pxr'`。

### 2. 训练配置与播放配置为什么要分开

两者的目标不同：

| | 训练配置 `RobotEnvCfg` | 播放配置 `RobotPlayEnvCfg` |
|---|---|---|
| 环境数 | 4096（吞吐优先） | 32~64（能看清） |
| 观测噪声 | 开（域随机化，为 sim2real） | 关（看策略真实能力） |
| 外力扰动 / 随机推 | 开 | 关 |
| 课程学习 | 开（难度递进） | 关（固定难度才可比） |
| 指令范围 | 跟随课程变化 | 固定 |

**最实际的理由**：评估必须可比。
课程会随训练进度改指令范围，若播放也用训练配置，
不同 checkpoint 之间的结果就没法对比了。

实践 8 的 FullPlay 就是这个思路的延伸：
普通 Play 只覆盖训练范围，FullPlay 把走(−0.7~1.0)和跑(1.5~2.5)的
速度区间取并集，才能验收"走跑切换"。

### 3. `play.py` 为什么能自动找到 checkpoint

`scripts/rsl_rl/play.py:91`：

```python
from isaaclab_tasks.utils import get_checkpoint_path
resume_path = get_checkpoint_path(log_root_path, agent_cfg.load_run, agent_cfg.load_checkpoint)
```

三层默认值接力：

1. `log_root_path` = `logs/rsl_rl/{experiment_name}`，
   而 `experiment_name` 来自 **PPO 配置**（与训练时同一个文件）
2. `load_run` 默认 `".*"` → 按时间戳排序取**最新**的那次运行
3. `load_checkpoint` 默认 `"model_.*.pt"` → 取该运行里**迭代数最大**的

所以「自动找到」的本质是：**play 和 train 读的是同一份 PPO 配置，
因此推导出同一个目录**，再按"最新 + 最大迭代数"选文件。

这也解释了实践 5/8 为什么必须给对照组设不同的 `experiment_name`：
同名会让 checkpoint 落进同一目录，play 时只能靠时间戳区分，极易取错。

## 四、环境搭建结果（官方 §5.1）

本机三栈均可用：

```
envs/isaaclab/     Python 3.11.15   isaacsim 5.1.0.0 / isaaclab 0.54.2
                   torch 2.7.0+cu128  mujoco 3.12.0  numpy 1.26.0
repos/IsaacLab/    IsaacLab 源码（editable 安装）
repos/unitree_rl_lab/   G1 任务与 checkpoint
shenlan_hw/hw4_mjlab/   mjlab + MuJoCo Warp 3.6.0（独立 .venv）
```

GPU：NVIDIA RTX 3090 24 GB，单卡，训练必须串行。

已验证可运行的入口：

- `scripts/rsl_rl/train.py`（实践 2 训了 10000 iter）
- `scripts/rsl_rl/play.py`（导出 `policy.pt` 并录像）
- `sim2sim/sim2sim_flat.py`（MuJoCo 侧部署，实践 2/3）
- `scripts/list_envs.py`（任务列表）

> **注意 mujoco 版本锁定在 3.12.0**：实践 2 的 raycaster 插件是按它编译的，
> 升级会立刻 ABI 不兼容（`plugin mujoco.sensor.ray_caster not found`）。
> 装任何新包前先 `pip install --dry-run` 确认不会带动它。
