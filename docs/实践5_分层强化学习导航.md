# 实践 5 — 分层强化学习导航（HRL）

> 高层导航策略输出 3 维速度指令，冻结的低层 locomotion 策略把它翻译成 29 维关节动作。
> 高层专注目标导航与避障，低层专注平衡与步态。

```
目标 + 局部地图 + 本体状态
        ↓
   高层 planner (PPO 训练)  →  [vx, vy, ωz]  →  裁剪  →  冻结低层策略  →  29 维关节动作
        ~10 Hz                                            ~50 Hz          ~200 Hz 物理步
```

---

## 一、核心：低层输入契约不可猜测

低层策略是训练完导出的 **TorchScript 静态图**。它的输入是按训练时的
term 顺序、缩放系数和 5 帧历史拼出来的一个扁平向量。

**顺序或缩放差一点，网络不会报错**，只会读到错位的物理量然后输出乱七八糟的关节角。

所以低层观测配置的唯一可靠来源是**低层自己的训练配置**：

```python
observations = copy.deepcopy(LOW_LEVEL_ENV_CFG.observations.policy)
observations.enable_corruption = False        # 推理时不加噪
observations.base_ang_vel.noise = None        # 四个本体感知项显式置空
observations.projected_gravity.noise = None
observations.joint_pos_rel.noise = None
observations.joint_vel_rel.noise = None
# history_length = 5 保持不变——改了就破坏契约
```

`deepcopy` 而非直接引用：`LOW_LEVEL_ENV_CFG` 是模块级单例，
直接改会污染同进程内其他使用它的配置。

### 两项观测要"重新接线"

低层训练时的两个输入在导航环境里已经没有对应来源，必须重定向到本 action term 的内部状态：

| 观测项 | 低层训练时来自 | 导航环境里改接到 |
|---|---|---|
| `velocity_commands` | CommandManager 的 `base_velocity` | 高层输出的 `_processed_actions` |
| `last_action` | `mdp.last_action`（返回**高层**的 3 维动作，语义和维度都不对） | 本 term 维护的 `low_level_actions`（29 维） |

改 `func` 的同时必须清空 `params`，否则原来的 `{"command_name": "base_velocity"}`
会被当多余参数传进新函数。

## 二、raw vs processed：接口契约的保护

```python
self._raw_actions[:] = actions                                        # 日志/诊断用
self._processed_actions[:] = torch.clamp(actions, lower, upper)       # 真正执行的
```

低层策略是在 `vx∈[-0.5,1.0]`、`vy/ωz∈[-0.5,0.5]` 的指令分布上训练出来的。
高层是个**没有输出限幅的高斯策略**，训练早期完全可能吐出 5.0 m/s。
把分布外的指令喂给低层，它的行为不可预测（通常直接摔倒），
高层收到一个与自身决策无关的噪声回报，学不到有效策略。

**裁剪等于给两层之间的接口加了一道契约保护。**

三处都必须用 `processed`，不能混：

1. 送给低层执行的指令
2. 低层观测里的 `velocity_commands`
3. 高层观测里的 `last_high_level_command`（TODO 1）

第 3 点尤其容易错：如果高层观测到的是裁剪前的原始动作，它会以为
"我上一步下的指令是 2.5 m/s"，而低层实际只收到 1.0 m/s —— 观测与现实脱节，
学到的因果关系是错的。**动作饱和时这个偏差最大，而饱和恰恰是训练早期的常态。**

> 注：IsaacLab 官方示例 `pre_trained_policy_action.py` 绑定的是 `_raw_actions`，
> 本作业要求绑 `processed`，是相对官方的改进。

### 一个 Python 陷阱

```python
self._processed_actions[:] = ...   # ✅ 原地写入
self._processed_actions = ...      # ❌ 重新绑定对象
```

TODO 3 里的闭包 `lambda dummy_env: self._processed_actions` 捕获的是**属性引用**，
但 `ObservationManager` 每步调用它取值。若重新绑定对象……实际上闭包读 `self.` 仍能拿到新对象，
**真正的风险在于**：预分配张量的语义（device/dtype/shape 固定）被打破，
且失去了"就地更新"带来的显存复用。统一用 `[:]` 是更安全的写法。

## 三、多时间尺度：`apply_actions()` 的位置是关键

```python
def apply_actions(self):
    if self._counter % self.cfg.low_level_decimation == 0:
        low_level_obs = self._low_level_obs_manager.compute_group("ll_policy")
        with torch.inference_mode():
            self.low_level_actions[:] = self.policy(low_level_obs)
        self._low_level_action_term.process_actions(self.low_level_actions)
        self._counter = 0
    self._low_level_action_term.apply_actions()   # ★ 在 if 之外
    self._counter += 1
```

低层网络只在计数器归零时前向一次，但它算出的**关节目标必须在随后的每个物理步
持续驱动 PD 控制器**。若把 `apply_actions()` 写进 `if` 里，关节目标只在 1/4 的
物理步被写入，其余 3 步执行器收不到指令，机器人会抽搐。

这是作业讲解点名的高频错误：
> "只在低层推理时调用 apply_actions()。正确逻辑是**低层推理按 50 Hz 更新，
> 低层动作每个 200 Hz 物理步持续执行**。"

`inference_mode` 比 `no_grad` 更彻底 —— 它连版本计数都不记录，
对这种"每步都跑、永不反传"的冻结网络能省下可观开销。

### 为什么低层必须冻结

分层 RL 的前提是**低层能力固定**，高层只学"下什么指令"。
若低层跟着一起更新，高层刚学会的"指令→行为"映射下一步就失效了，训练无法收敛。

`torch.jit.load(...).eval()` + `inference_mode()` 双重保证。

## 四、高度扫描池化：必须先还原二维

```python
flat = _height_scan(env, sensor_cfg, offset)   # (num_envs, ny*nx) 扁平
ny, nx = _height_scan_grid_shape(env, sensor_cfg)
grid = flat.view(-1, 1, ny, nx)                # 补通道维给 F.max_pool2d
pooled = F.max_pool2d(grid, kernel_size=pool_size)
return pooled.flatten(start_dim=1)
```

**不能对扁平向量直接做一维池化。** 射线在扁平向量里按 `(y, x)` 行主序排列，
相邻元素是"同一行左右相邻的两点"，但每 `nx` 个元素就跨到下一行。
一维池化会把行尾和下一行行首混在一起，空间布局完全错乱 ——
**而且不会报错**，只会让策略读到一张无意义的地形图。

**为什么取 max 而非 mean**：导航关心"前方有没有障碍物"。
最大值保留网格内最高的点（障碍），均值会把孤立的细柱子抹平。
对避障来说，漏掉一根柱子的代价远大于高估地形高度。

维度验算（V5 配置）：

```
扫描区 5.0 × 3.0 m @ 0.12 m  →  26 × 42 = 1092 根射线
2×2 最大池化                →  13 × 21 = 273 维
```

## 五、高层 376 维观测的构成

| 分组 | 观测项 | 维度 | 作用 |
|---|---|---|---|
| 本体运动 | `base_lin_vel` / `base_ang_vel` / `projected_gravity` | 3+3+3 | 当前**实际**速度与姿态 |
| 任务目标 | `pose_command` | 4 | 目标点在**机体系**下的相对位姿 |
| 控制历史 | `last_high_level_command` | 3 | 上一条**裁剪后**的指令 |
| 局部地图 | `height_scan_pooled` | 273 | 2×2 池化后的高度扫描 |
| 低层状态 | `joint_pos` / `joint_vel` / `low_level_last_action` | 29+29+29 | 低层的内部状态 |
| | **合计** | **376** | |

两个设计意图值得记：

**目标用相对位姿而非世界坐标**：导航策略应当学"朝目标偏左就右转"这种
与绝对位置无关的规律，这样才能泛化到任意起点和地图。

**实际速度 vs 期望速度的差**：`base_lin_vel`（实际）与
`last_high_level_command`（期望）之差就是低层的跟踪误差。
若关节动作已经很大而实际速度上不去，说明低层已接近能力边界，
高层应该降低指令而不是继续加码 —— `low_level_last_action` 提供的正是这个信号。

Critic 额外观测 `base_height` 与 `command_distance`（特权信息，Actor 不可见），
与实践 4 的非对称 Actor-Critic 是同一套思路。

## 六、评估不能只看 reward

作业讲解明确要求同时观察：

```
成功率 · 目标距离误差 · 跌倒率 · 超时比例 · 动作饱和 · 命令变化率
```

> "reward 上升不等于机器人真正完成避障导航。"

这与实践 2 的教训完全一致 —— 我们那次 `reward=26.32`、`episode_length=960/1000`
都很漂亮，机器人却在原地踏步。

**play 时的诊断顺序**：机器人绕障失败时，
先看**高层是否给出了正确的速度方向**，再看**低层能否执行该速度**。
这样能区分失败来自规划层、低层能力边界，还是两层接口设计。

## 七、Part 2 的公平对照原则

只改**一个**主要因素，保持相同 `seed` / `num_envs` / `iteration` /
`num_steps_per_env` / 评估 episode 数。若因显存降低了 `num_envs`，
应以**总 environment steps** 作为统一训练预算（与实践 9 的
`Env × Iter ≈ 4096 × 10000` 折算表同理）。

### ⚠️ 课程自带的 Extension 不是单因素对照

作业讲解举的例子是"baseline 使用静态地图，extension **仅增加随机障碍**"。
但课程包里 `HRL-Baseline` 与 `HRL-Extension` 实际相差**五处**：

| 项目 | Baseline (`Compact_SingleGoal`) | Extension (`MixedObstacle`) |
|---|---|---|
| 障碍布局 | 固定模板（startup 烘焙） | 每次 reset 随机 |
| 课程学习 | 无（`curriculum = None`） | 障碍数 0→120 递增 |
| **观测** | 池化 height_scan **273** 维 | 未池化 **1092** 维 |
| 目标 | 单目标 `RingPose` | arena-wide 多目标 |
| 终止 | 含 `goal_reached` success | 不同 |

**观测维度不同意味着两组的策略网络输入层都不一样** —— 已经不是同一个模型，
性能差异无法归因到任何单一因素。它们是两个难度不同的任务，不是一组消融。

### 自建的单因素对照组

新增 `Unitree-G1-29dof-Navigation-HRL-RandomArena`：
继承 Baseline，**只替换 `events`**，其余（观测/目标/终止/课程/奖励/网络/超参）
全部原样继承，并共用同一份 `PPORunnerCfg`。唯一变量是
**"障碍布局是否每个 episode 重排"**。

实现时踩到一个坑：

```python
# mdp/events/obstacle_events.py
num_active = getattr(env, "obstacle_num_active", None)
active_counts = default_num_active if num_active is None else num_active[env_ids]
```

Baseline 靠 startup 事件 `assign_fixed_mixed_arena_layout` 写入
`env.obstacle_num_active`。换掉 `events` 后没有该 startup 事件，
又没有 curriculum 去设置它，若不显式指定就会落到默认值 **0** ——
得到一个**空场地**，比较的就成了"有障碍 vs 无障碍"，与设计意图完全相反。

所以必须显式对齐障碍数：

```python
self.events.randomize_obstacles.params["default_num_active"] = V5_MAX_MIXED_OBSTACLES
```

取 120 是为了与 Baseline 对齐 —— 固定模板烘焙时
`target_count = min(layout_cfg.max_obstacles, V5_MAX_MIXED_OBSTACLES) = 120`。
两组都受同样的 `min_center_separation` / `soft_margin` 约束，
实际落位数会自然接近。

### 运行

```bash
./scripts/run_p5p6_compare.sh p5        # 顺序跑 baseline 与 random_arena
```

推荐的进一步探索路径：先增加障碍密度或窄通道 → 再加随机障碍 → 最后考虑动态障碍。
地图更难或目标更远时要同步检查 episode 时长和 curriculum，
否则策略可能因频繁超时而看似"训练失败"。

## 八、训练发散的定位过程

首次训练两组都在 ~20 iter 内崩溃：

```
RuntimeError: normal expects all elements of std >= 0.0
```

策略分布的 std 变成了 NaN。诊断脚本：`scripts/diagnose_p5_lowlevel.py`

### 8.1 三个隔离实验，推翻了三个"合理假设"

| # | 假设 | 实验 | 结果 |
|---|---|---|---|
| ① | 机器人资产从 USD 换成 URDF，导致关节顺序与预训练低层策略错位 | 底层任务 + 零指令 | ❌ 推翻。投影重力 −1.000、高度 0.797 m，站得稳。换成自训 URDF 策略后 `bad_orientation` 仍是 1.0，与策略来源无关 |
| ② | 导航环境或两层接线有问题 | 导航环境 + 恒定 vx=0.5 | ❌ 推翻。低层读到 +0.500，机器人实际走 +0.576 m/s，姿态 −0.982 |
| ③ | 环境产生 NaN/inf（实践 2 踩过 `inf` 污染） | 随机指令 400 步 × 64 env 扫描 | ❌ 推翻。观测、奖励、射线命中点全部零 NaN、零 inf |

**② 的实验设计有个容易漏掉的点**：只测零指令是不够的 ——
接线正常传 0，与接线断了永远读到 0，**表现完全相同**（都站着不动）。
而"闭包捕获旧张量导致低层永远读到零指令"恰好是第二节点名的陷阱。
必须下发非零指令并测实际速度，才能把这两种情况分开。

### 8.2 转折点：学习率已在下限

`Loss/learning_rate` 显示 **1e-5** —— 自适应调度的下限。
配合 `max_grad_norm=1.0` 的梯度裁剪，**权重不可能自己涨到 10¹²**。

于是结论只能是：**爆炸来自输入，不是来自优化器。**
而前面三个实验只查了 NaN/inf，**没有查量级**。

补测观测量级后立刻定位：

```
low_level_last_action     1.691e+06   ← 异常
joint_vel                 3.628e+01
base_ang_vel              1.365e+01
pose_command              1.161e+01
height_scan_pooled        1.500e+00   ← 因为它有 clip
projected_gravity         1.000e+00
```

### 8.3 根因与正反馈

冻结的低层 TorchScript 在机器人进入其**训练分布之外**的姿态（摔倒过程中）
会吐出极端值。这个值有两条去路，两条都会出事：

```
低层输出 1.7e6
   ├─→ low_level_last_action 进高层观测 → V(s)=W·obs 爆炸
   │      → value loss 10²⁵ → float32 溢出 → 权重 NaN → 崩溃
   └─→ PD 控制器 → 巨大力矩 → 把机器人掀翻 → 更多摔倒 ──┐
          ↑                                              │
          └──────────────── 正反馈 ─────────────────────┘
```

每次摔倒还会触发 `termination_penalty = -400`，
使 episode 回报稳定在 −400 量级（实践 2 的量级只有 ~26），
MSE 价值损失按平方放大，进一步加剧发散。

### 8.4 修复

| 措施 | 位置 | 理由 |
|---|---|---|
| 低层输出 clamp 到 ±10 | `apply_actions()` 源头 | 正常关节动作在 ±1 量级（×`action_scale`=0.25 后为 ±0.25 rad），±10 远超合理范围，不损失有效信号。在源头截断同时保护观测与 PD 两条路径 |
| `low_level_last_action` 加 `clip=(-10,10)` | 观测项 | 第二道防线，与 `height_scan_pooled` 已有的 clip 同一思路 |
| 高层指令 EMA 平滑 α=0.1 | `process_actions()` | 见下 |

**指令平滑解决的是另一个独立问题**：低层策略训练时
`resampling_time_range=(10,10)`，即指令每 **10 秒**才换一次；
而 HRL 高层每个 env step（**0.2 秒**）就重新采样，快了 **50 倍**。
实测这个分布偏移使摔倒间隔从 143 步恶化到 22.6 步。
α=0.1 在 5 Hz 下时间常数约 1.9 s。

### 8.5 效果

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 观测最大值 | 1.69×10⁶ | **37** |
| 摔倒间隔 | 22.6 步 | **143.3 步** |
| `value_function loss` | 第 2 轮 10²⁷ → NaN 崩溃 | 峰值 2721 → 降至 21 |
| 学习率 | 被钉死在下限 1e-5 | 恢复到 3.8e-4 |
| Mean episode length | 13 | **146**（上限 150） |
| Mean reward | −95 | **−3.5** |

### 8.6 方法论

1. **每个"看起来很合理"的假设都要用实验证伪，而不是靠推理接受。**
   这次前三个假设全部被推翻，真正的原因直到查了学习率才被逼出来。
2. **"lr 已在下限 + 有梯度裁剪"是一条强约束** ——
   它把问题从"优化器不稳"直接推到"输入有问题"，缩小了搜索空间。
3. **查数值污染时，NaN/inf 和量级是两件事。** 只查前者会漏掉这一类故障。
4. **冻结模块的输出必须限幅。** 它在训练分布内表现良好，
   不代表在分布外不会吐出极端值 —— 而分布外恰恰是失败时必然进入的状态。
5. 诊断实验要能**区分两种表现相同的故障**（见 8.1 的②）。

## 九、修好发散之后的第二个坑：站着不动

崩溃修复后训练恢复正常，但 200 iter 时出现了另一种失败：

| 表面指标 | 值 | |
|---|---|---|
| Mean episode length | 150.00（上限） | ✅ 看着完美 |
| `time_out` 占比 | 0.9938 | ✅ |
| `bad_orientation` 占比 | 0.0060 | ✅ |

| 真实任务指标 | 值 |
|---|---|
| `position_progress` | **−0.0003**（负） |
| `goals_reached` | **0.0000** |
| `error_pos_2d` | 7.44（不降反升） |

**机器人学会了"站着不动就不会摔"** —— 用不动来规避摔倒惩罚。
这与实践 2 的"原地踏步"是同一类局部最优。

### 9.1 用边际激励比证明这不是"再训久点就好"

按归一化单位（`Episode_Reward/*` = episode 和 ÷ `episode_length_s`=30 s）：

```
走完全程 3.5 m 的进展奖励    +0.117
到达目标的 success_bonus     +3.333
摔一次的 termination        -13.333    ← 比走完全程大 114 倍
```

诊断实测：高层输出随机指令时平均每 143 步摔一次，
而 episode 上限是 150 步 → 训练早期 **P(摔倒) ≈ 65%**。

```
E[尝试移动] = 0.117 + 3.333·P(到达) − 13.333 × 0.65
            = −8.55 + 3.333·P(到达)
E[站着不动] = 0
```

要让移动不劣于不动，需 **P(到达) > 256%** —— 数学上不可能。
**「站着不动」严格占优**，再训 3000 轮也走不出来。

> 这一步很关键：如果只看曲线"还没收敛，再等等"，就会白跑 3 小时。
> 把奖励量级、失败概率、可得收益放进同一个式子算一遍，
> 才能区分"学得慢"和"结构上学不了"。

### 9.2 为什么不能靠加强平滑解决

先试了压低指令平滑系数（让低层看到更平缓的指令）：

| α | 摔倒间隔 |
|---|---|
| 1.0（不平滑） | 22.6 步 |
| **0.1** | **143.3 步** |
| 0.05 | 75.0 步 |
| 0.02 | 66.9 步 |

α=0.1 是最优点，**再小反而更差** —— 平滑过度后指令严重滞后，
机器人需要调整时高层的意图传不过去。所以摔倒率压不到能让 −400 成立的水平
（那需要每 3000 步才摔一次，比现在好 20 倍）。

### 9.3 修法：改变边际激励比，而不是把奖励调大

沿用实践 2 §6.3 的思路。`termination_penalty` 改为环境变量可配，默认 −20：

```
termination_penalty   P(到达)=10% 时 E[移动]
    -400                  -8.217   ❌ 不动更优
    -100                  -1.717   ❌
     -50                  -0.633   ❌
     -20                  +0.017   ✅ 值得尝试
```

设 `NAV_TERMINATION_PENALTY=-400` 可复现课程原值做对照。

> **课程给的 −400 并没有错**，它隐含假设低层策略足够鲁棒、摔倒是小概率事件。
> 我们手上这套低层（hw5 自带的预训练 TorchScript）达不到那个鲁棒性，
> 于是同一份奖励在这里就变成了不可学的。
> **奖励权重从来不是孤立的数字，它与其它模块的能力共同决定激励结构。**

⚠️ 注意改的是 `NavigationV2RewardsCfg`。文件里有两处 `termination_penalty`，
Baseline 与 RandomArena 经 `NavigationV5MixedObstacleRewardsCfg` 继承的是
V2 那一处 —— 第一次改错了地方（改了 `NavigationRewardsCfg`），
必须顺着 `env_cfg_entry_point` 一路查到实际继承链才能确认。

### 9.4 配套的自动巡检

`scripts/watch_p5.sh` 每 10 分钟检查一次，三条同时成立才算健康：

1. episode length 不低于上限的 60% —— 没在频繁摔倒
2. `position_progress` > 0 —— 真的在朝目标移动
3. `error_pos_2d` 相比早期在下降 —— 距离确实缩小了

只看第 1 条会把"站着不动"误判为健康，这正是本节要防的。

## 十、真正的瓶颈：低层策略，不是奖励结构

第九节把 `termination_penalty` 从 −400 调到 −20 后，机器人确实开始移动了
（`error_pos_2d` 从 7.28 降到 6.5），但随即**在 6.5 平台化不再下降**，
`episode length` 稳定在 **16 步**。

### 10.1 一个算术让问题无所遁形

```
episode 上限 = 150 步 × 0.2 s = 30 s
机器人速度  ≈ 0.5 m/s
16 步 = 3.2 s  →  只能走 1.6 m
目标距离    = 2 ~ 5 m
```

**根本来不及走到目标就摔了。** 无论怎么调奖励都学不会导航 ——
因为"成功"这个事件在数据里从未出现过，没有任何梯度指向它。

> 这一步比继续调奖励重要：把时间、速度、距离放进同一个算式，
> 就能判断当前的 episode 长度**在物理上是否够完成任务**。
> 不够的话，问题一定在别处。

### 10.2 换低层策略：8 倍改善

其余全部不变（同一份高层配置、同一套限幅与指令平滑、同样 120 iter），
只换低层策略：

| 低层策略 | episode length | `bad_orientation` |
|---|---|---|
| 课程 `pretrained/g1_29dof_lowlevel` | 16 ~ 18 | **0.97** |
| **自训（同一套 URDF 机器人）** | **136 ~ 146** | **0.037** |

课程的 pretrained 是在原作者的 **USD** 机器人上训练的。
它在零指令下能让本机的 URDF 机器人稳稳站住（投影重力 −1.000），
观测维度也完全一致（480 → 29），
**但一旦下发持续的速度指令就频繁摔倒**。

> 这解释了为什么我早先那个「零指令站立测试」通过了却没能发现问题 ——
> **静态测试测不出动态鲁棒性。**（第八节的②已经吸取过一次类似教训：
> 零指令无法区分"接线正常传 0"与"接线断了永远读到 0"。同一个坑，两种形态。）

具体成因没有进一步隔离（USD/URDF 的物理属性差异、训练时的指令分布差异
都有可能），这里只陈述可复现的实测差距。
设 `UNITREE_G1_LOW_LEVEL_POLICY_PATH` 指向课程原策略即可复现对照。

### 10.3 一处我自己的测量偏差

诊断脚本最初用**每步独立采样的随机指令**测低层摔倒率，得到"每 143 步一摔"，
据此我一度认为低层足够鲁棒。但这个数字是错的：

```
每步独立随机 + EMA(α=0.1)  →  有效指令 std = 0.2 × √(α/(2−α)) = 0.046
策略实际输出（相关信号）    →  ‖a‖ ≈ 0.42        大 9 倍
```

EMA 对**白噪声**衰减极强，对**相关信号**几乎不衰减。
用白噪声测出来的鲁棒性因此被严重高估。

> **测一个模块对输入变化的鲁棒性时，测试信号必须有与真实输入相当的时间相关性。**
> 否则平滑环节会把测试信号吃掉，测出来的是平滑器的性能而不是模块的。

### 10.4 修改后的配置

`LOW_LEVEL_POLICY_PATH` 默认改为自训策略（文件不存在时回退到课程版本）。
`termination_penalty = −20` 保留 —— 它解决的是"敢不敢动"，
换低层解决的是"动了能不能撑住"，两者是不同的问题。

分析脚本：`scripts/compare_p5_navigation.py`
（把"表面指标"与"真实任务指标"分开列，内置「站着不动」自检）

## 十一、第三个坑：稠密奖励在工作范围内恒等于 0

换了鲁棒的低层策略后，机器人不摔了（`bad_orientation` 0.0000、
`episode length` 满值 150），但跑到 2298 iter 时：

```
error_pos_2d         7.5836 → 7.3484   （2298 iter 里几乎没动）
position_progress    恒为 0.0001~0.0002
goals_reached        恒为 0
Mean reward          -0.38 → -0.04     （收敛到"站着不动"的收益 ≈ 0）
action_magnitude     -0.0014           ← 比 position_progress 大 7 倍
```

**策略学会了输出近乎零的速度指令。**

### 11.1 病根：`std` 与目标距离不匹配

`position_tracking_fine_grained` 用的是

```python
return 1.0 - torch.tanh(distance / std)
```

课程配置 `std = 0.1`，而 Baseline 的目标在 **5~10 m** 外采样
（`ranges.distance=(5.0, 10.0)`）。代入算一下：

| 距离 | `std=0.1` 时的奖励 |
|---|---|
| 10 m | **0.000000** |
| 7.5 m | **0.000000** |
| 5 m | **0.000000** |

**这个"稠密奖励"在整个工作范围内恒等于 0**，梯度为零 ——
它只在 0.5 m 以内才醒过来，可机器人从来走不到那里。

于是策略能看到的唯一非零信号是动作惩罚（`action_magnitude` −0.0014），
梯度方向是"把动作调小"，最优解就是**不动**。

### 11.2 按真实区间重选 std

| `std` | @10m | @5m | 10m→5m 梯度 |
|---|---|---|---|
| 0.1（课程原值） | 0.000000 | 0.000000 | **0** |
| 2.0 | 0.0001 | 0.0134 | 0.013 |
| **5.0（采用）** | **0.0360** | **0.2384** | **0.202** |

改后实测：稠密奖励 0.0000 → **0.0538**，比动作惩罚（−0.0007）**大 85 倍**，
"靠近目标更好"的梯度终于压过了"少动省钱"。

### 11.3 又一次改错继承链

第一次改的是 `NavigationRewardsCfg`（`std=0.2`），
但 Baseline / RandomArena 实际继承的是 `NavigationV2RewardsCfg`，
那里的值是 **0.1**，比前者还窄。

这与第九节改 `termination_penalty` 时踩的是**同一个坑** ——
文件里同名字段有多份，必须顺着 `env_cfg_entry_point` 一路查到实际继承链：

```
Unitree-G1-29dof-Navigation-HRL-Baseline
  → NavigationV5MixedObstacleEnvCfg_Compact_SingleGoal
    → NavigationV5MixedObstacleRewardsCfg
      → NavigationV2RewardsCfg     ← 真正生效的是这里
```

> 同一个坑踩两次，说明**改配置前先确认继承链**应该变成固定动作，
> 而不是"看到同名字段就改"。

### 11.4 巡检判据也跟着收紧

原判据只要求 `position_progress > 0` 且 `error_pos_2d` 有下降。
上一跑里进展是 0.0002、误差降了 3%，**两条都"技术上满足"**，
于是被判为健康 —— 可实际是彻底的站着不动。

改为要求误差**至少下降 5%**，并在提示里指向本节的排查顺序。

### 11.5 三个坑的关系

| # | 症状 | 病根 | 修法 |
|---|---|---|---|
| 一（§八） | 训练发散 NaN | 冻结低层在分布外吐出 1.7e6 | 源头限幅 ±10 |
| 二（§九） | 站着不动 | 摔倒罚 −400 远大于移动收益 | 改为 −20 |
| 三（§十） | 移动了但走不到 | 低层不够鲁棒，16 步就摔 | 换自训低层策略 |
| 四（本节） | 不摔了但还是不动 | 稠密奖励零梯度 | `std` 0.1 → 5.0 |

**每修好一个，下一个才浮现出来。** 这是分层系统调试的常态 ——
上游的问题会掩盖下游的问题，只能一层一层剥。

## 12. 推翻前面的结论：瓶颈不在低层策略，在导航环境

> 2026-09-04。本节的结论**否定了 §10 的判断**，也否定了基于它的所有后续推断
> （包括 §11 之后我一度认为的"探索塌缩"）。诊断过程本身比结论更值得记。

### 12.1 先测上界，再谈优化

baseline 跑满 3000 iter 仍 `goals_reached = 0`。
在按"探索不足"再烧 12 GPU 小时之前，先用**不需要学习的控制器**界定问题边界：

```
oracle（脚本化"转向目标 + 前进"）
  到达率    0.0 %
  摔倒率   84.4 %
  最近距离  7.41 → 5.92 m
```

连 oracle 都到不了 —— 失败不在 RL 探索，在任务侧。
这一步花了约 10 分钟，省下 12 小时。

### 12.2 低层的安全工作区间

```
vx=0.2  摔倒率 100.0%  存活  9.3 步  有效射程 0.73 m
vx=0.3  摔倒率 100.0%  存活 15.5 步  有效射程 1.49 m
vx=0.4  摔倒率  87.5%  存活 59.5 步  有效射程 5.17 m
vx=0.5  摔倒率  92.2%  存活 47.6 步  有效射程 5.24 m
vx=0.7  摔倒率  84.4%  存活 56.2 步  有效射程 5.46 m
```

最好也只有 5.5 m 有效射程，而目标在 5~10 m。
当时的结论是"低层不够鲁棒"——**这个结论是错的**，见下。

注意一个反直觉数据：**速度越小越早摔**。这条线索后来成了突破口。

### 12.3 决定性对照：同一策略，两个环境

在**低层自己的训练环境**里下发同样的恒定速度指令：

| 环境 | 指令 | 时长 | 投影重力 z | 结果 |
|---|---|---|---|---|
| 低层自己的环境 | vx=0.5 | 200 步 / 4 s | **−0.999** | 位移 1.74 m，**0% 摔倒** |
| 低层自己的环境 | vx=0.2 | 400 步 / 8 s | **−1.000** | 位移 0.93 m，**0% 摔倒** |
| 导航环境 | vx=0.5 | 200 步 | — | **92.2% 摔倒** |
| 导航环境 | vx=0.2 | 200 步 | — | **100% 摔倒** |

**同一个 TorchScript 策略、同一个速度指令，低层环境 8 秒不摔，导航环境 1.86 秒必摔。**

策略是好的。问题 100% 在导航环境侧。

### 12.4 逐个排除（都做了实测或静态核对）

| 嫌疑 | 结论 | 依据 |
|---|---|---|
| 实践 2 的粗糙地形策略更好？ | **接口不兼容** | 读 TorchScript 首层权重：当前低层 480 维，实践 2 是 1415 维（差 935 = height_scan 187×5 帧） |
| 地形更难？ | 排除 | 导航是 `NAVIGATION_FLAT_TERRAIN_CFG` 平地，比低层训练地形还简单 |
| 出生在障碍里？ | 排除 | `exclude_origin` 保证出生点 0.8 m 内不放障碍 |
| 控制频率不同？ | 排除 | 两边低层都是 50 Hz（导航 `decimation=40`、`low_level_decimation=4`，4×0.005=0.02 s） |
| 观测重接线错？ | 静态看正确 | deepcopy 低层 obs group、保留 5 帧历史、`velocity_commands` 绑到 `_processed_actions` |

### 12.5 找到直接触发点：低层输出触顶

给诊断加了低层**输出量级**的统计（此前只统计观测）：

| 指令 | 输出 \|a\| 均值 | 峰值 | 触顶比例 | 非超时终止 |
|---|---|---|---|---|
| 零指令 | 0.185 | 1.201 | **0.0 %** | **0 次** |
| vx=0.5 | 0.359 | **10.000** | **0.2 %** | **44 次**（每 env 2.75） |

触顶与摔倒完全相关。0.2% 看着小，但 16 env × 29 关节 × 150 步 ≈ 6.96 万个动作值
里有约 139 次触顶，每次都把某个关节命令到 `10 × action_scale 0.25 = 2.5 rad`（143°）
—— 足以瞬间失衡。

**§8 加的 ±10 限幅只拦住了数值爆炸（曾出现 1.69e6），没有解决根因。**
限幅让训练不再 NaN，于是我误以为问题已经解决。

### 12.6 一个差点被写进结论的假线索

同一次诊断里出现了这个：

```
指令 vx=0.5        低层读到 0.406   （偏低 19%）
指令 (0.4,0.3,0.3) 低层读到 0.325   （偏低 19%）
```

两次都恰好 19%，看起来是系统性偏差，我一度写下"这是下一步的首要排查对象"。

**但它有平凡解释**：`--nav` 模式压根没有应用 `--smoothing` 参数
（只有 `--nan-hunt` 分支应用了），于是静默沿用了 cfg 默认的
`command_smoothing = 0.1` —— EMA 开着且尚未收敛，0.406 就是它的正常中间值。

已修掉这处不一致，让 `--nav` 与 `--nan-hunt` 用同一套设置。

**顺带得到一个有用信息**：§12.5 的触顶数据是在 **EMA 开启**下测到的，
而 §12.2 的速度扫描是在 **EMA 关闭**下测的，两者都摔 ——
说明平滑与否不是决定因素，触顶才是。

**教训**：一个数字"看起来太规整以至于像 bug"时，先检查测量配置，
再怀疑被测系统。两次 19% 完全一致，恰恰因为它是同一个确定性过程的产物。

### 12.7 我自己的诊断工具骗了我

`--nav` 模式此前只看**最后一帧**的投影重力就判定"没摔"。
但 IsaacLab 在 episode 终止时会自动重置并把机器人放回直立初始姿态，
所以"最后一帧投影重力 = −1.0"在自动重置的环境里**恒成立**，
哪怕一路上摔了几十次。

这次实测把欺骗性摆在了同一屏：

```
投影重力 z 最终   -0.999     ← 看起来完美
非超时终止次数    44         ← 实际每 env 摔 2.75 次
```

§8 那次"接线验证通过"就是被它骗的。已改为统计非超时终止次数。

**教训**：在自动重置的环境里，任何只看最终状态的判据都是无效的，
必须统计**过程中的事件**（终止次数、触顶次数），而不是**终态快照**。
这是继"用白噪声测 EMA"（§10 附注）之后，同一类错误的第二次出现：
测量方法与被测系统的动力学不匹配。

## 13. 逐项对比观测：假设被数据否定

### 13.1 先修工具：不要在一个进程里建两个 IsaacLab 环境

第一版诊断在同一进程里先后构建低层环境和导航环境，
结果**第二个环境构建到一半后 26 分钟无输出、GPU 空转 37%**，只能强杀。

这个坑我在 `probe_p5_exploration.py` 里已经踩过一次并写进了注释
（"一个进程里建两次 IsaacLab 环境非常慢，实测 >40 min 还没跑完第二组"），
但没有把教训落到新脚本上。

改法：加 `--only {low,nav}`，一次只建一个环境，结果写 JSON，
两侧分别跑完后自动汇总。外层 shell 串联并加 `timeout` 兜底。
改完后低层侧 21 秒、导航侧约 8 分钟，都正常结束。

**教训写进注释不算学到，落到代码里才算。**

### 13.2 结果

同一低层策略、同样的 vx=0.5 指令，逐项统计观测的 |值|：

| 观测项 | 低层环境（均值/最大） | 导航环境（均值/最大） | 倍数 |
|---|---|---|---|
| `base_ang_vel` | 0.034 / 0.37 | 0.061 / **1.48** | **1.81x** |
| `projected_gravity` | 0.355 / 1.05 | 0.354 / 1.00 | 1.00x |
| **`velocity_commands`** ★ | 0.164 / 0.50 | 0.163 / 0.50 | **0.99x** |
| `joint_pos_rel` | 0.047 / 0.65 | 0.061 / 1.41 | 1.31x |
| `joint_vel_rel` | 0.046 / 0.41 | 0.038 / 1.38 | 0.82x |
| **`last_action`** ★ | 0.281 / 2.87 | 0.362 / **10.00** | 1.29x |
| 低层输出 \|a\| | 0.287 / 2.87 | 0.362 / **10.00** | 1.26x |
| **非超时终止** | **0 次** | **46 次**（每 env 2.88） | — |

★ = 被 HRL 重接线的两项。

### 13.3 两个结论，一个是我的假设被否定

**① `velocity_commands` 0.99x —— 指令接线完全正确。**

这条彻底排除了我在 §12.6 一度怀疑的"19% 系统性偏差"，
也再次确认那个星号是 EMA 未收敛而非 bug。**指令通路没有问题。**

**② `last_action` 只有 1.29x，小于原生项 `base_ang_vel` 的 1.81x
—— 我的"正反馈"假设不成立。**

§12.5 发现输出触顶后，我推测是：
`输出触顶 → last_action 出现 ±10 → 观测分布外 → 输出更极端`。
若成立，`last_action` 的偏差应当**显著大于**所有原生项。
实测它排在第三，判据 `重接线项 > 3 × 原生项` 明确不满足。

需要区分**均值**与**峰值**：`last_action` 的峰值确实打到限幅 10.00
（低层环境只有 2.87），但均值只高 29%。
也就是说触顶是**偶发**的，没有形成持续的正反馈回路。

**③ `base_ang_vel` 1.81x（峰值 4 倍）更像是摔倒的结果而非原因。**

机器人翻倒时角速度必然飙升。用它来解释摔倒是倒果为因。

### 13.4 一个我一直没查的可能：撞障碍

导航环境有 8 个圆柱障碍（`V3_MAX_CYLINDER_OBSTACLES = 8`，半径 0.4 m、高 2 m），
它们是**物理刚体**。而终止项里**没有碰撞判据**：

```python
time_out      = DoneTerm(func=mdp.time_out, time_out=True)
goal_reached  = DoneTerm(...)
base_height   = DoneTerm(func=mdp.root_height_below_minimum, ...)
bad_orientation = DoneTerm(func=mdp.bad_orientation, limit_angle=0.8)
```

撞上障碍不会立刻结束 episode，而是把机器人**撞倒**后走 `bad_orientation`。
所以"撞障碍"和"自己走不稳"在指标上**长得一模一样**——
`bad_orientation` 占比升高、角速度飙升、输出触顶，两者都会产生。

我此前只验证了"出生点 0.8 m 内不放障碍"（`exclude_origin`），
但从没验证过**运动过程中**会不会撞上。而我们下发的是恒定前进指令，
机器人只会直线往前走，**撞上是大概率事件**。

已加 `NAV_MAX_OBSTACLES` 开关做隔离实验（默认 8，保持原行为）。

### 13.5 障碍隔离实验：两次都做错了，教训比结论多

想验证"机器人是撞障碍摔的，还是自己走不稳"。做了两次，**两次都翻车**。

**第一次：改错了常量。**
加了 `NAV_MAX_OBSTACLES` 开关控制 `V3_MAX_CYLINDER_OBSTACLES`（8 个圆柱），
两组结果一模一样 —— 到每一位小数。
这个"完全相同"本身就是信号：真实实验不可能给出逐位相同的结果。
一查才发现 **Baseline 用的是 `V5_MAX_MIXED_OBSTACLES = 120`**（混合障碍），
根本不走 V3 那套。开关生效了，但管的不是这套障碍。

**第二次：读到了陈旧文件。**
改对常量后重测，结果**又是逐位相同**。
这次是 `NAV_MAX_OBSTACLES=0` 让布局代码崩溃了：

```
RuntimeError: value tensor of shape [4,120,7] cannot be broadcast to [4,0,7]
```

场景里生成 0 个障碍，布局侧却仍按 120 个写位姿。
运行崩溃，没写出新 JSON，**上一轮的旧文件还在**，
我拿新数据和它对比，得到了假结论。
时间戳一看就露馅：`obstacle_test_0.json` 是 17:23（第一轮），
`obstacle_test_120.json` 是 17:34（第二轮）。

**正确做法**（已在代码注释里写明）：
不要改"物理生成多少个"，要改"激活多少个" ——
`MixedObstacleLayout.sample_layout(num_active=0)`，
课程 `V5_OBSTACLE_COUNT_LEVELS = (0, 50, 80, 100, 120)` 的第一档走的正是这条路。
我把两处常量都恢复了原值（留下会崩溃的开关比没有开关更糟）。

**已做的加固**：`diagnose_p5_obs_gap.py` 的每条结果现在都带 `_timestamp`，
读取时超过 `--max-age`（默认 1 小时）直接丢弃并告警。

### 13.7 障碍彻底排除：测摔倒现场，不做开关对照

§13.5 两次开关对照都翻车后，换了个不用改配置的办法：
**直接测摔倒那一刻机器人到最近障碍的表面距离**（`diagnose_p5_fall_distance.py`）。

```
摔倒次数         188 次（64 envs，200 步）
激活障碍数       120 个/env
平均首次摔倒步   92.3
全程平均最近距离 1.82 m

距离  最小 0.80 m   中位 2.03 m   最大 5.94 m
  < 0.0 m :   0.0%     ← 从未穿透
  < 0.3 m :   0.0%
  < 0.5 m :   0.0%     ← 从未接触
  < 1.0 m :   3.7%
  < 1.5 m :  25.0%
```

**最小距离 0.80 m，0% 低于 0.5 m —— 机器人从没碰到过任何障碍。**
75% 的摔倒发生在 1.5 m 以外。**障碍与摔倒无关，机器人是自己走不稳的。**

这个方法比开关对照好在三点：
1. 不动配置，没有"开关没生效"的风险（§13.5 栽过两次）
2. 直接测因果现场，而不是比较两组统计量
3. 给出分布，能区分"少数撞上"与"普遍自己摔"

实现上有两个坑，都写进了注释：
- `centers_xy` 是**环境局部坐标**，`root_pos_w` 是世界坐标，
  必须先减 `env_origins`。忘了减会让所有距离偏大好几米，
  直接得出"从没撞过"的假结论 —— 而这次的真结论恰好也是"没撞过"，
  两者长得一样，不减就永远发现不了错。
- 摔倒距离必须在 `env.step()` 后**立刻**取，晚一步就是重生后的位置。

### 13.10 事件配置对比：域差距指向了相反的方向

对比两个环境的 `EventCfg`：

| 事件 | 低层训练环境 | 导航环境 | 作用 |
|---|---|---|---|
| `physics_material` | ✅ 摩擦随机 (0.3, 1.6) | ❌ 无 | 域随机化 |
| `add_base_mass` | ✅ | ❌ 无 | 域随机化 |
| `add_joint_default_pos` | ✅ ±0.01 rad | ❌ 无 | 域随机化 |
| `base_com` | ✅ | ❌ 无 | 域随机化 |
| `base_external_force_torque` | ✅ | ❌ 无 | 域随机化 |
| `push_robot` | ✅ 随机推 | ❌ 无 | 域随机化 |
| `reset_base` | ✅ | ✅ | 两边一致 |
| `reset_robot_joints` | ✅ | ✅ | 两边一致 |

`NavigationSceneCfg(LowLevelRobotSceneCfg)` —— 导航场景**继承**低层场景，
只覆盖了 `terrain_generator`。所以地面材质是继承来的
`static_friction = dynamic_friction = 1.0`，
正好是低层训练随机化范围 (0.3, 1.6) 的中心值。

**这个对比的结论是反直觉的**：

导航环境比低层训练环境**扰动更少**——摩擦固定在最理想值、
没有随机推力、没有质量/质心扰动。
按"域差距"的常规推理，机器人在这里应该**表现更好**才对，
而不是从 0 摔倒变成每 env 摔 2.88 次。

**所以"低层策略遇到了分布外输入"这条思路整体上是错的。**
真正的原因一定在别处 —— 某个不属于"扰动"范畴的机制差异。

这也解释了为什么前面九项排查全部落空：我一直在找"哪里更难了"，
但导航环境处处更简单。下一步应该反过来问：
**导航环境里有什么是低层环境里没有的？**

已知的"多出来的东西"只有三类：
1. 分层调用结构（高层每 10 个低层步下发一次新指令）
2. 120 个障碍物刚体存在于场景中（虽已证明没碰到，但会影响物理求解器负载）
3. 高层动作是**每步重采样**的随机量，而低层训练时的指令是**每 10 秒才换一次**

第 3 条最值得查：低层策略从未见过"指令每 0.2 秒就变一次"的输入。
这正是 §10 加 EMA 平滑的初衷，而 §12.2 证明了关掉平滑也照样摔 ——
但那只说明平滑不是解药，不代表**指令变化率**不是病因。
下一步实验：给低层环境下发同样高频变化的指令，看它是否也开始摔。
若是，病因就锁定了；若否，剩下的只有分层调用结构本身。

### 13.11 指令变化率也被否定

§13.10 推测病因是"高层指令每 0.2 秒重采样，而低层训练时每 10 秒才换一次"。
在低层**自己的环境**里复现这种高变化率（`--resample-every 1`，每步都换）：

| 指令模式 | 非超时终止 | 位移 | 平均速度 |
|---|---|---|---|
| 恒定 vx=0.5（对照） | **0 次** | 1.86 m | 0.465 m/s |
| **每步随机重采样** | **0 次** | 0.80 m | 0.200 m/s |

**每步换指令，低层照样一次不摔。** 位移变小是正常的（指令方向来回变，
净位移自然小），但姿态始终保持 `投影重力 z = −1.000`。

指令变化率不是病因。

### 13.12 分频逻辑也是对的

```python
def apply_actions(self):
    if self._counter % self.cfg.low_level_decimation == 0:   # decimation = 4
        ...推理...
        self._counter = 0
    self._low_level_action_term.apply_actions()
    self._counter += 1
```

推理发生在 counter = 0, 4, 8, … 即**每 4 个物理步一次**。
`sim.dt = 0.005` → 4 × 0.005 = 0.02 s = **50 Hz**，与低层环境完全一致。

### 13.14 一个贯穿始终的测量缺陷（结论未变，但方法要修）

准备做"逐步对齐"实验时，发现前面所有对比都有一个单位问题：

```
低层环境  decimation=4   → step_dt = 4 × 0.005 = 0.02 s
导航环境  decimation=40  → step_dt = 40 × 0.005 = 0.2 s   ← 10 倍
```

我一直用**步数**对齐两组实验：低层 200 步、导航 150 步。
但那是 **4 秒 vs 30 秒**，时长差 **7.5 倍**。
"低层不摔"很可能只是因为没跑够时间。

重测（低层跑满 1500 步 = 30 秒，与导航侧对齐）：

| 环境 | 时长 | 非超时终止 |
|---|---|---|
| 低层 | 30 s | **0 次** |
| 导航 | 30 s | **46 次**（每 env 2.88） |

**结论没变**，低层策略确实不摔。但这个缺陷本身值得记：

- 若低层的摔倒率是"每 11 秒一次"，4 秒的测试就永远看不到，
  我会得出完全相反的结论而不自知
- 这是本轮第三次同类错误：§10 用白噪声测 EMA（信号特性不匹配）、
  §12.7 用终态快照判摔倒（自动重置抹掉过程）、
  现在是用步数对齐不同 `step_dt` 的环境（单位不匹配）

**规律**：跨环境/跨配置比较时，先问"我对齐的这个量，
在两边是同一个物理量吗"。步数不是时间，最终状态不是过程，
白噪声不是策略噪声。

顺带发现另一个指标缺陷：30 秒里位移只有 4.62 m（0.154 m/s，
而 4 秒测试是 0.465 m/s）。不是机器人变慢了，是 episode 超时重置后
被传回出生点，`root_pos_w − start_xy` 跨重置就没有意义。
`diagnose_p5_lowlevel.py` 的位移统计需要按 episode 分段，
这一点在 `probe_p5_exploration.py` 里已经修过（用逐步累加 + 掩码），
同样是"教训没落到新代码上"。
