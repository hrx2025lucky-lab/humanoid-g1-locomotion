# 实践 7 — 使用 GMR 完成人体动作到 G1 的运动重定向

> 把人体动捕数据（SMPL-X / BVH / FBX）转成 G1 能执行的关节轨迹。
> 产物会被实践 9 / 10 / 11 当作参考动作使用，所以它的正确性是下游一切的前提。

---

## 一、当前状态与一处澄清

课程包 `深蓝学院-人形运控-Project7-code(1)` 里只有两个文件：

```
B12_-_walk_turn_right_(90)_stageii.npz    ← 动作数据
vis_robot_motion_npz.py                   ← 可视化脚本
```

**这个 npz 不是原始人体数据，而是已经重定向到 G1 的结果**：

| 字段 | 形状 | 含义 |
|---|---|---|
| `dof_pos` | (232, **29**) | G1 29 个关节角 |
| `root_pos` | (232, 3) | 骨盆世界坐标 |
| `root_rot` | (232, 4) | 骨盆姿态四元数 |
| `local_body_pos` | (232, **38**, 3) | 38 个刚体相对根节点的位置 |
| `link_body_list` | (38,) | 刚体名列表 |

232 帧 @ 29.9 fps = 7.76 秒。

所以课程给的是**重定向的输出**，用来让你先看清目标格式；
要自己跑完整的 SMPL-X → G1 链路，还需要额外准备。

### 跑完整链路缺什么

`repos/GMR` 已就位，且带 `unitree_g1` 资产与 4 份 G1 的 IK 配置
（`smplx_to_g1.json` / `bvh_lafan1_to_g1.json` / `fbx_to_g1.json` / `xrobot_to_g1.json`）。

**缺 SMPL-X 人体模型**（`SMPLX_NEUTRAL.pkl` 等）。它需要在
[smpl-x.is.tue.mpg.de](https://smpl-x.is.tue.mpg.de/) 注册账号后手工下载，
无法自动获取。放到 `repos/GMR/assets/body_models/smplx/` 下即可。

### ⚠️ 安装 GMR 前必读

GMR 的 `install_requires` 包含 `mujoco` / `numpy` / `scipy`，
**直接装进 isaaclab 环境有风险**：pip 可能升级 `mujoco`，
而实践 2 的 raycaster 插件是按 **3.12.0** 编译的，版本一变立刻 ABI 不兼容
（表现为 `plugin mujoco.sensor.ray_caster not found`）。

建议二选一：

```bash
# 方案 A：独立 venv，零风险
python -m venv ~/envs/gmr && ~/envs/gmr/bin/pip install -e repos/GMR

# 方案 B：装进 isaaclab 但不动依赖，再逐个补缺失的包
pip install --no-deps -e repos/GMR
```

## 二、为什么要先验证重定向结果

重定向的错误**几乎都不会报错**：

| 错误 | 表现 |
|---|---|
| 四元数 wxyz / xyzw 读反 | 机器人整体倒置或朝向错乱 |
| 关节超出物理限位 | 仿真里被硬约束截断，动作变形 |
| 帧间跳变 | 速度尖峰，PD 控制器产生巨大力矩 |
| 脚陷进地面 / 悬空 | 接触相不对，下游的跟踪奖励失去意义 |

它们都能正常加载、正常播放，只是动作不对。
而这份数据是实践 9/10/11 的参考轨迹 —— 错了会一路传下去且极难回溯。

所以在用它之前先钉死：`sim2sim/verify_practice7_motion.py`

```bash
python sim2sim/verify_practice7_motion.py
# 22/22 项通过
```

脚本不依赖 GMR 包（原因见上），只用 numpy 与 URDF 解析。

## 三、22 项检查与实测结果

### ① 数据完整性（10 项）

各字段帧数一致、维度正确、`link_body_list` 与 `local_body_pos` 对齐、
fps 合理、四个数组均无 NaN/inf。

### ② 四元数约定（3 项）—— 本实践最容易踩的坑

```
各分量绝对值均值  [0.0240, 0.0245, 0.3778, 0.8623]
                    x       y       z       w
```

**最大分量在末位**（0.8623），且两个近零分量在前两位 —— 判定为 **xyzw**。

这与课程 vis 脚本的写法互相印证：

```python
motion_root_rot = motion_root_rot[:, [3, 0, 1, 2]]   # xyzw → wxyz
```

它把 w 从末位挪到首位，正说明**源数据是 xyzw、而 MuJoCo 需要 wxyz**。

> 这条贯穿多个实践：实践 3（MuJoCo `qpos[3:7]` 是 wxyz）、
> 实践 7（此处源数据是 xyzw）、实践 11（重力投影用 wxyz）。
> **每次跨库传递姿态都要显式确认一次顺序**，不能凭印象。

另外检查了相邻帧的四元数点积（最小 0.9987），确认没有 `q` / `−q`
符号翻转造成的假跳变 —— 这类跳变在数值上是不连续的，但表示同一个旋转，
直接对四元数做差分会得到虚假的角速度尖峰。

### ③ 关节限位（2 项）

29 个关节全部落在 URDF 限位内（含 5% 量程容差）。

容差是必要的：重定向是**优化求解**的结果，贴着限位边界很正常，
真正要抓的是大幅越界。

### ④ 时序连续性（2 项）

| 量 | 实测最大 | 门槛 |
|---|---|---|
| 关节角速度 | 6.92 rad/s | 40 rad/s |
| 根节点线速度 | 1.20 m/s | 5 m/s |

6.92 rad/s 远低于 G1 各关节 20~30 rad/s 的额定速度，轨迹是平滑的。

### ⑤ 物理合理性（4 项）

| 检查 | 实测 |
|---|---|
| 根节点高度 | 0.740 ~ 0.844 m（站立合理） |
| 脚部局部 z | 最大 −0.559（确实在根节点下方） |
| 脚到根节点距离 | 均值 0.718 m |
| 最低脚高度波动 | 0.061 m ← 说明存在支撑相 |

最后一条是判断"这是不是一段真实行走"的关键：
行走时总有一只脚踩在地上，因此**两脚中较低者**的高度应该基本不变。
波动只有 6 cm，符合行走；若这个值很大，说明动作是在跳跃或者飘着。
