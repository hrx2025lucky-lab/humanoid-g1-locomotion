> **"为什么站起来这个任务必须用增量动作空间"** 这件事，从零讲到我能对着面试官白板推演。

## 0. 一句话概括

让一台躺在地上的人形机器人自己爬起来。难点不在"训练"——策略是别人预训练好的，
我只负责在 MuJoCo 里**把它跑起来**。而"跑起来"的关键，是让策略输出的那 23 个数字，
用**正确的方式**变成关节的目标角度。这个"正确的方式"就是 HoST 的**增量动作空间**：
策略说的不是"你应该摆成什么姿势"，而是"在你现在的姿势上，往哪个方向挪一点"。

---

## 1. 问题从哪来（Why）

### 先说结论：动作空间选错了，机器人一辈子躺在地上

我先跑一个反面实验。把动作映射从增量式换成常规残差式，**其它一切不变**——
同一个预训练策略、同一份观测、同一组 PD 参数、同一个初始躺姿。结果：

| 20 秒仿真 | 增量式（HoST） | 残差式 |
|---|---|---|
| 起始骨盆高度 | 0.096 m | 0.096 m |
| **峰值高度** | **0.747 m** | **0.096 m** |
| 结束高度 | 0.741 m | 0.065 m |
| 站起判定 | ✅ 站起并维持 | ❌ 全程平躺，一次没抬起来 |

残差式的峰值高度**等于起始高度**——20 秒里它一次都没离过地，结束时甚至比开始还低
（0.065 < 0.096），把自己在原地摊得更平了。同一个策略网络，只因为最后那行"怎么把
输出变成关节目标"写法不同，一个站起来了，一个永远起不来。

这就是为什么这个作业的核心不是"训练一个会站的策略"，而是**动作空间这一个设计选择**。

### 为什么不用更简单的办法？

**"为什么不让策略直接输出关节力矩？"** 面试常问。
因为力矩和机器人当前状态强耦合：同样想让膝盖弯一点，机器人快摔倒时和站稳时需要的
力矩天差地别。让神经网络直接学"在每种状态下该出多大力"，等于让它把 PD 控制器的活
也一起干了，样本效率极低。业界几乎都用"策略出目标角 → PD 控制器出力矩"的两层结构，
把"决定去哪"和"怎么去"解耦。

**"那目标角为什么不用绝对位置 / 残差式？"** 这才是本实践真正要回答的问题——
下面第 2、3 节整段都在讲它。一句话预告：残差式把目标角永久锁在标称站姿附近的一个
小盒子里，而站起来需要走出这个盒子。

## 2. 核心概念（零基础可懂）

### 概念一：动作空间（Action Space）

**生活化类比。** 你在教一个朋友摆姿势拍照。有三种指挥方式：

1. **绝对关节角**：你直接报出每个关节的角度——"左膝 87 度，右肘 45 度……"。
   精确，但你得一次性说全，而且朋友得先忘掉现在的姿势。
2. **残差式（相对固定基准）**：你先约定一个"标准站姿"，然后说"在标准站姿的基础上，
   左膝再多弯 10 度"。你说的每一句都是相对**那个固定的标准姿势**。
3. **增量式（相对当前姿势）**：你说"在你**现在**这个姿势上，左膝再弯一点点"。
   你说的每一句都是相对**此刻的实际姿势**。

**严格定义。** 动作空间就是"策略网络那几个输出数字，被解释成什么物理量"。
本实践里策略每步输出 23 个数（记作 `a`，每一维大致落在 ±1，极端到 ±3），
这 23 个数怎么变成 23 个关节的目标角度，就是动作空间的定义。

**数学形式（三种写法）：**

```
绝对式:   q* = a                          （直接就是目标角）
残差式:   q* = q_default + α·a            基准 = 固定标称站姿
增量式:   q* = q_current + α·a            基准 = 当前实际姿态   ← HoST
```

- `q*`：这一步要送给 PD 控制器的 23 维目标关节角（弧度）
- `a`：策略网络的 23 维原始输出
- `α`：缩放系数 `action_scale`，本作业 = 0.25（来自 `configs/g1.yaml`）
- `q_default`：标称站姿，代码里的 `default_angles`
- `q_current`：**此刻真实的**关节角，从 MuJoCo 现读出来

**在本实践中的体现。** 就是 `deploy_mujoco_host_student.py` 里
`action_to_joint_targets()` 那一行：`current_joint_positions + action_scale * policy_action`。
整个作业的 TODO 4，成败就在选 `q_current` 还是 `q_default` 当基准。

### 概念二：PD 控制器（把"目标角"变成"力矩"的那层）

**生活化类比。** 目标角只是"我想让膝盖到 90 度"，但电机只认电流/力矩。
PD 控制器像一根**带阻尼的弹簧**：目标角和当前角差得越远，它拉得越用力（P 项，比例）；
关节动得越快，它越往回拽以防冲过头（D 项，微分）。

**数学形式：**

```
τ = Kp·(q* − q) + Kd·(0 − q̇)
```

- `τ`：输出力矩　`q*`：目标角　`q`：当前角　`q̇`：当前角速度
- `Kp`：刚度（本作业膝关节 = 200）　`Kd`：阻尼（膝关节 = 6）

这层在框架代码里已经写好（`pd_control()`），我不用碰。但要理解它的存在——
**正因为有 PD 这层兜底，策略只需要给"目标角"这种慢变量，控制频率 50 Hz 就够**，
不必像力矩控制那样跑到 500~1000 Hz。

### 概念三：投影重力（Projected Gravity）——机器人怎么知道"哪边是下"

**生活化类比。** 你闭着眼睛也知道自己是躺着还是站着——靠内耳的重力感。
投影重力就是给机器人装了这个"内耳"：把世界坐标系里那个永远指向地心的重力方向，
换算到机器人自己身上的坐标系，得到一个 3 维单位向量。

- 机器人**站直**时，重力在它自己看来是从头顶压到脚底，约 `(0, 0, −1)`
- 机器人**平躺**时，重力从它的胸口压向后背，z 分量接近 0

**为什么用它而不用姿态角（欧拉角）？** 两个原因，都能落到本任务：
1. 欧拉角有**万向节死锁**（gimbal lock）——某些姿态下两个轴重合，角度突变。
   站起来要翻滚过各种极端姿态，正是死锁高发区。
2. 投影重力对 **yaw（朝向）不敏感**。站起来这个任务根本不关心机器人脸朝东还是朝西，
   只关心"哪边是地面"。投影重力天然把无关的朝向信息滤掉了。

代码里 `get_gravity_orientation(base_quat_wxyz)` 从四元数算出这个向量，进观测的 `[3:6]`。

### 概念四：POMDP 与历史观测——为什么要存 6 帧

**生活化类比。** 只给你看一张照片，你说不出照片里的球是在往上飞还是往下落——
单帧丢了"趋势"。给你连续 6 张，你一眼看出运动方向。

**严格定义。** POMDP（Partially Observable Markov Decision Process，部分可观测马尔可夫
决策过程）指的是：单帧观测**不足以**推断出完整状态。站起任务就是典型——
单帧里没有"我正在往哪个方向倒""脚跟接触地面了没"这类信息。

**怎么补？** 把最近 6 帧观测拼起来喂给网络（`6 × 76 = 456` 维）。
6 帧 × 20 ms = 120 ms 的时间窗，网络能从相邻帧的**差分**里隐式恢复出加速度、
接触状态的变化这些单帧看不到的量。这就是 TODO 3 维护的历史缓冲。

### 概念五：观测缩放（Observation Scaling）——把不同量纲拉到同一个数量级

**生活化类比。** 一份体检表上"身高 175（厘米）"和"体重 0.07（吨）"放一起，
数值大的会在视觉上压过小的。神经网络也一样：输入里数值大的维度会主导梯度。

本作业三个关节量的真实范围差很多：角速度可达 ±10 rad/s，关节角只有约 ±3 rad。
所以各乘一个缩放系数压到相近范围：

```
ang_vel_scale = 0.25    dof_pos_scale = 1.0    dof_vel_scale = 0.05
```

**关键：这三个数必须和训练时一模一样。** 缩放变了，等于策略读到的是"另一个世界"
的数值，预训练学到的映射全部失效。这也是 sim2sim 部署最容易出错的地方之一。

## 3. 算法原理：为什么增量式能让"站起来"变简单

这一节是全篇的核心。我要讲透一件事：**同一个策略、同样的输出幅度 ±1，
为什么增量式能站起来、残差式不能。**

### 直觉：可达空间（Reachable Set），不是"拉力大小"

先给一个我一开始就想错、后来被数据纠正的直觉（这段本身就是面试的好素材，第 5 节
展开）。真正的原因是**可达关节空间的上界**，跟"弹簧拉力"无关。

**残差式：目标角被锁在一个固定的小盒子里。**

策略输出 `a` 典型量级 ±1，乘 `α = 0.25`，所以 `α·a` 大约在 ±0.25 rad 之间摆动。
残差式 `q* = q_default + α·a`，基准 `q_default` 是**钉死不动**的。以膝关节为例
（`default_angles` 里膝 = 0.3 rad）：

```
残差式膝关节可达范围 = [0.3 − 0.25, 0.3 + 0.25] = [0.05, 0.55] rad
```

而从仰卧把身体撑起来，膝关节要屈曲到大约 **1.5 ~ 2.0 rad**。
`0.55 < 1.5`，**差了一个数量级，而且跑多少步都到不了**——因为每一步的目标都是
相对**同一个固定基准** `q_default` 算出来的，第 1 步和第 1000 步的可达集合**完全一样**，
位移不会累积。这就是残差式 20 秒纹丝不动的根本原因。

**增量式：把基准锚在当前姿态，位移可以累积。**

增量式 `q* = q_current + α·a`，基准 `q_current` 每一步都更新成**此刻的真实关节角**。
每步最多挪 0.25 rad，但**从上一步到达的位置继续挪**。50 Hz 控制下，1 秒理论行程可达：

```
50 步/秒 × 0.25 rad/步 = 12.5 rad/秒
```

整个关节空间都能到达。膝关节从 0.3 走到 2.0 只需要 `(2.0−0.3)/0.25 ≈ 7` 步、
约 0.14 秒的理论下界。实测机器人 **约 2 秒**完成从躺到站——留了大量余量给平衡调整。

**一句话对比。**
- 残差式像是让人**每一步都从同一个原点起跳**，跳再多次也只能覆盖原点周围一圈。
- 增量式像是让人**一步接一步地走**，每步不远，但能走到任意远。

### 语义的第二个变化：`a = 0` 的含义

顺带一个常被忽略但很妙的点：

- 残差式里 `a = 0` 意味着 `q* = q_default`——**回到标称站姿**。
  也就是策略"什么都不输出"时，机器人被拉向站姿。
- 增量式里 `a = 0` 意味着 `q* = q_current`——**保持现状不动**。
  策略输出的每一维，都是一次相对此刻的**真实位移决策**。

这让增量式的搜索空间对"站起来"这种任务小得多：策略不用在每一帧都重新规划出
"完整的目标姿态"，只需要决定"在当前基础上，每个关节微调多少"。

### 为什么站起来这个任务尤其吃这一点

站起来是**接触状态频繁切换**的任务：背贴地 → 肘撑地 → 臀离地 → 深蹲 → 站直。
每个阶段的"合理姿态"相差极远，**根本不存在一个通用的标称基准**能让残差式用。
你没法找到一个 `q_default`，既适合平躺又适合深蹲。增量式绕开了这个问题——
它不需要任何全局基准，只跟"当前"比。

### 如果去掉某一项会怎样（逐项拆）

- **去掉增量、换成残差** → 上面已验证：全程平躺（峰值高度 = 起始 0.096 m）。
- **去掉历史、只喂单帧（76 维）** → POMDP 退化，策略读不到"正在往哪倒"，
  平衡阶段会失稳（这是 HoST 论文设计 6 帧历史的原因）。
- **观测缩放乱一个** → 策略读到"另一个世界"的数值，预训练映射失效，机器人乱动。
- **动作基准误用缩放后的关节角** → 目标角被整体缩放，机器人往一个错误姿态收敛
  （本作业 `dof_pos_scale=1.0` 恰好掩盖了这个 bug，换配置就暴露，见第 5 节）。

## 4. 代码走读

挑 `deploy_mujoco_host_student.py` 的四个 TODO 核心逐段讲。文件里控制主循环、
PD 控制、录像等框架代码已给好，我只写这四个函数。

### TODO 1 — 读 MuJoCo 浮动基座状态（`read_robot_state`，第 62~111 行）

```python
current_joint_positions = np.array(mj_data.qpos[7:], dtype=np.float32)   # 未缩放，留给 TODO 4
raw_joint_velocities   = np.array(mj_data.qvel[6:], dtype=np.float32)
base_quat_wxyz         = np.array(mj_data.qpos[3:7], dtype=np.float32)   # 四元数 wxyz
base_angular_velocity  = np.array(mj_data.qvel[3:6], dtype=np.float32)
```

这段在**从 MuJoCo 的状态数组里，按正确的下标切出各个物理量**。三个必须记住的点：

**(a) qpos 比 qvel 多一位。** 浮动基座（free joint）在 `qpos` 里占 7 位
（位置 3 + 四元数 4），在 `qvel` 里只占 6 位（线速度 3 + 角速度 3）。
原因是**四元数用 4 个数表示 3 个旋转自由度**（多一个约束：模长为 1）。
所以 23 个关节在 `qpos` 里从下标 **7** 开始、在 `qvel` 里从下标 **6** 开始。切错一位，
后面全体错位。

**(b) 四元数是 wxyz 不是 xyzw。** MuJoCo 的约定是 w 在前。读成 xyzw，
投影重力会算反，机器人以为自己是倒置的。（同一个坑在实践 7 会反过来咬一口——
那边的 AMP 数据要求 xyzw。所以我现在的习惯是：**每次碰四元数先查这个库的约定**。）

**(c) 为什么用 `np.array(...)` 而不是直接切片。** `mj_data.qpos` 返回的是一个
**视图（view）**不是副本——它和 MuJoCo 内部内存共享。后面主循环里 `mj_step()`
会就地改写这块内存。如果 `current_joint_positions` 只是视图，等 TODO 4 用到它时，
值可能已经被物理步更新过，不再是读取那一刻的关节角。`np.array(..., dtype=np.float32)`
强制拷贝一份，把这一刻的值"冻"住。

**缩放与不缩放的分岔**（本 TODO 最容易语义混淆的地方）：

```python
joint_positions_for_obs = current_joint_positions * dof_pos_scale   # 进观测，缩放
# 但 current_joint_positions 本身保持未缩放，专门留给 TODO 4 当动作基准
```

### TODO 2 — 拼 76 维单帧观测（`build_single_observation`，第 114~155 行）

```python
current_obs = np.concatenate([
    base_angular_velocity_obs,                   # [0:3]   基座角速度（已缩放）
    projected_gravity,                           # [3:6]   投影重力（单位向量，不缩放）
    joint_positions_for_obs,                     # [6:29]  关节角（已缩放）
    joint_velocities_for_obs,                    # [29:52] 关节角速度（已缩放）
    previous_policy_action,                      # [52:75] 上一帧动作
    np.array([action_scale], dtype=np.float32),  # [75]    动作尺度标量
]).astype(np.float32)
assert current_obs.shape == (76,)
```

维度账：`3 + 3 + 23 + 23 + 23 + 1 = 76`。三个点：

- **顺序是硬约束。** 网络第一层权重按训练时的顺序排列。顺序错了**不会报错**
  （维度还是 76），只会让每个神经元读到错误的物理量——表现为机器人乱动，
  且因为不报错而**极难 debug**。这是 sim2sim 最阴险的一类 bug。
- **`action_scale` 作为一维标量进观测。** 这是 HoST 的设计：让策略"知道"自己的输出
  会被乘以多大系数。`np.concatenate` 只接受数组，标量必须包成长度 1 的数组。
- **投影重力不缩放。** 它本身是单位向量，模长恒为 1，缩放反而破坏这个性质。

### TODO 3 — 维护 6 步 FIFO 历史（`update_observation_history`，第 158~187 行）

```python
observation_history = np.concatenate([
    observation_history[single_observation_dim:],  # 丢弃最旧的 76 维
    current_obs,                                   # 最新帧追加到末尾
]).astype(np.float32)
assert observation_history.shape == (76 * 6,)      # 456
```

这是一个**先进先出（FIFO）队列**：每来一新帧，从头部丢掉最旧的 76 维，
把新帧接到**尾部**。张量形状从 `(456,)` 出、`(456,)` 入，不变。

**顺序必须"旧 → 新"，最新帧在最高索引端。** 写反了（新帧插到最前），
策略会把未来当过去，动作方向整体反相。这也是不报错、只表现为行为异常的坑。

### TODO 4 — 增量动作映射（`action_to_joint_targets`，第 190~240 行）★核心

```python
target_joint_positions = (
    current_joint_positions + action_scale * policy_action
).astype(np.float32)
```

一行，但这一行就是整个作业的题眼。两个必须说清的点：

- **基准必须是 `current_joint_positions`（当前实际姿态），不是 `default_angles`。**
  用 `default_angles` 就退化成残差式，机器人永远躺着（第 1 节的反面实验）。
- **基准必须是"未缩放"的真实关节角。** 观测里的 `joint_positions_for_obs` 乘过
  `dof_pos_scale`，不能拿它当基准。本作业 `dof_pos_scale = 1.0` 让两者数值恰好相同，
  **但这是巧合**——换个配置（比如 0.5）立刻出错。所以我在语义上严格区分了这两个变量。

**验证这一行最直接的方法——零动作单元检查：**

```python
target = action_to_joint_targets(np.zeros(23), current_q, 0.25)
assert np.allclose(target, current_q)      # a=0 时保持现状 → 确实是增量式
assert not np.allclose(target, default_q)  # 且不等于标称姿态 → 确实不是残差式
```

这一条断言同时证明了"是增量式"和"不是残差式"。作业讲解也专门推荐这个检查。

### 运行期诊断：盯住 `‖q* − q_current‖`

主循环里我会监控这个量（目标角相对当前角的位移范数）：

- **长期为 0** → 策略输入/历史/状态读取可能返回了全零，链路某处断了。
- **数值异常大** → 优先查 `action_scale`、缩放参数、观测顺序。

## 5. 我踩过的坑

### 坑一：我用"弹簧拉力"解释残差式失败，被自己的数据打脸（最有价值的一个）

**现象。** 残差式 20 秒全程平躺。我要在文档里解释"为什么"。

**第一反应。** 我脱口而出一个听起来很顺的解释：*"残差式相当于一根指向标称站姿的
弹簧，`q_default − q_current` 产生巨大的恒定拉力，压过了策略输出的增量，
所以机器人被死死拽在站姿基准上动不了。"* 这个说法有画面感，我差点就写进去了。

**为什么这么想是错的。** 它缺了一个关键的**实测数据**：这根"弹簧"到底多用力？
我想当然地假设拉力很大，但从没量过。

**怎么找到真因。** 我在两组实验里都记录了 `‖q* − q_current‖`（目标角相对当前角的
位移范数）的均值——这正好是"弹簧拉力"的代理量。结果：

| | 增量式 | 残差式 |
|---|---|---|
| `‖q*−q_cur‖` 均值 | 0.670 rad | **0.181 rad** |
| `‖q*−q_cur‖` 最大 | 1.156 rad | 1.110 rad |

残差式的平均位移只有 **0.181 rad，不到增量式（0.670）的三分之一**。
"弹簧拉力"根本不大，反而更小——我的解释被自己的数据直接推翻了。

**根因（两层）。**
1. 数据层面：机器人**躺平时关节角本来就接近 `q_default`**。躺倒改变的是**根节点姿态**
   （四元数），不是各关节的弯曲程度——关节该多直还多直。所以 `q_default − q_current`
   本身就很小，"拉力"无从谈起。
2. 真正的限制是**可达空间的上界**：残差式目标角永远在 `q_default ± 0.25` 内，
   而站起需要膝到 1.5~2.0 rad，差一个数量级。是"够不着"，不是"被拽住"。

**教训（可迁移）。** 设计消融实验时，除了看主指标（这里是高度），一定要顺手记录
**能区分不同假设的中间量**（这里是 `‖q*−q_cur‖`）。只看高度只能知道"残差式失败了"，
加上位移量才能知道它**为什么**失败，并且能**证伪**一个听起来很顺、其实错误的解释。
一个漂亮的错误解释比"不知道"更危险，因为它会阻止你继续追问。

### 坑二：四元数读成 xyzw，机器人整个倒置

**现象。** 投影重力算出来符号不对，机器人一初始化就往错误方向翻。

**第一反应。** 以为是 `get_gravity_orientation` 的公式抄错了。

**为什么这么想是错的。** 公式没错，错的是喂给它的四元数分量顺序。
MuJoCo 用 **wxyz**，我按 xyzw 的习惯取了 `qpos[3]` 当 x，实际上它是 w。

**怎么找到真因。** 打印 `qpos[3:7]`，静止站立时应该接近 `(1, 0, 0, 0)`（单位四元数，
w≈1）。我看到第一个分量是 ~1、后三个接近 0——确认第一个是 w，wxyz 无疑。

**根因。** 不同库的四元数分量顺序约定不统一（MuJoCo/Isaac 常用 wxyz，
很多 SLAM/图形库用 xyzw）。

**教训。** 碰四元数**第一件事是查当前库的分量顺序**，别凭肌肉记忆。
我现在的自检是：静止时打印四元数，看哪个分量≈1。

### 坑三：`current_joint_positions` 是视图不是副本

**现象。** 偶发地，TODO 4 算出的目标角像是"晚了一拍"，对不上读取那一刻的姿态。

**第一反应。** 怀疑控制时序错了，policy 输出和状态没对齐。

**为什么这么想是错的。** 时序没问题。问题在 `mj_data.qpos[7:]` 返回的是和 MuJoCo
内部内存**共享的视图**，主循环每个物理步 `mj_step()` 都会就地改写它。

**怎么找到真因。** 我把读到的关节角先存一份、`mj_step` 之后再打印同一个变量，
发现值变了——它跟着内存一起被改了。

**根因。** NumPy 切片默认是视图，不是拷贝；MuJoCo 状态数组是活的。

**教训。** 从仿真器读状态，**一律显式 `np.array(...)` 拷贝**。这个坑在任何
"读状态 → 走几步物理 → 再用之前读的状态"的模式里都会出现。

### 坑四：`dof_pos_scale = 1.0` 掩盖的"缩放混用"陷阱

**现象。** 这次没出错——但我意识到它是运气。

**第一反应。** 观测里的 `joint_positions_for_obs` 和动作基准 `current_joint_positions`
数值一样，随便用哪个都行。

**为什么这么想是错的。** 两者数值相同**纯属巧合**：本作业 `dof_pos_scale` 恰好是 1.0。
观测那份是"缩放后"的、语义上属于观测；动作基准必须是"未缩放"的真实弧度。

**怎么找到真因。** 我在脑子里把 `dof_pos_scale` 换成 0.5 推演：观测那份会变成真实角的
一半，若拿它当动作基准，目标角会被整体缩到一半，机器人往一个矮一截的错误姿态收敛。

**根因。** 用一个恰好等于 1 的系数，掩盖了"观测量"和"控制量"的语义区别。

**教训。** **别让代码的正确性依赖某个参数恰好等于 1。** 语义上该分开的变量就分开，
哪怕此刻数值相同。我在代码里对这一点专门写了注释，防止后人（和三个月后的我）踩坑。

### 坑五：录像只录到 6 秒就断了

**现象。** 提交视频只有约 6 秒，机器人刚站起来就没了。

**第一反应。** 以为仿真崩了或 `simulation_duration` 设短了。

**为什么这么想是错的。** 仿真没崩，配置是 60 秒。问题在录制方式。

**怎么找到真因。** 原脚本用 `mujoco.viewer.launch_passive` 开窗口，并在每个物理步
`sleep` 到 1 ms 以实现"实时播放"。但 1280×720 的离屏渲染每帧远超 1 ms，
于是墙钟（真实世界）60 秒只推进了约 6 秒的仿真时间。

**根因。** "实时对齐"的 sleep 逻辑和"高分辨率离屏渲染"的耗时冲突了。

**教训。** 录制和实时可视化是两件事。我另写了一份 headless 录制脚本：不开 viewer、
不做实时对齐，四个核心函数直接 `import` 原文件，保证"录的就是提交的那份实现"。

## 6. 面试可能怎么问

### 概念题

**Q1：残差动作空间和增量动作空间的区别？各适合什么任务？**
残差式 `q* = q_default + α·a`，基准是固定标称姿态，`a=0` 回到站姿；适合**周期步态**
这种有明确参考姿态、只在其附近小幅摆动的任务。增量式 `q* = q_current + α·a`，
基准是当前实际姿态，`a=0` 保持不动，位移可累积；适合**大范围姿态变化**、
没有通用参考姿态的任务，比如从任意躺姿站起。

**Q2：为什么用投影重力而不是欧拉角当姿态观测？**
两点：欧拉角有万向节死锁，站起过程要翻过各种极端姿态正好是死锁高发区；
投影重力对 yaw 不敏感，而站起任务不关心朝向只关心哪边是地面，天然滤掉无关信息。

**Q3：为什么要历史观测？站起不是马尔可夫的吗？**
它是 POMDP：单帧观测推不出"我正在往哪倒""脚接触了没"这些量。拼 6 帧
（120 ms 窗口）让网络从帧间差分里隐式恢复加速度和接触变化。

### 实现题

**Q4：MuJoCo 里 23 个关节的角度从 qpos 哪个下标开始？为什么不是 6？**
从 `qpos[7]` 开始。浮动基座在 qpos 里占 7 位（位置 3 + 四元数 4），
但在 qvel 里只占 6 位（四元数用 4 个数表达 3 个旋转自由度）。
所以关节角从 `qpos[7:]`、关节角速度从 `qvel[6:]`——这俩下标故意差一位。

**Q5：你怎么单元测试 TODO 4 的动作映射写对了？**
零动作检查：喂 `a = 0`，断言 `target == current_joint_positions`（证明是增量式）
且 `target != default_angles`（证明不是残差式）。一条断言同时排除两种写错的可能。

**Q6：观测拼接顺序错了会怎样？怎么发现？**
不会报维度错误（总维度还是 76），但每个神经元读到错误物理量，机器人乱动。
发现方式是逐段打印各切片的 shape 和数值范围，和训练时的布局表逐项对照。

### 深挖题

**Q7：你说残差式站不起来，是因为它把机器人"拽"在站姿附近吗？**
（陷阱题，考你有没有真的量过。）不是。我一开始也这么以为，但数据推翻了它：
残差式的 `‖q*−q_cur‖` 均值只有 0.181 rad，比增量式的 0.670 还小，"拉力"根本不大。
真因是**可达空间上界**——残差式目标角永远在 `q_default ± 0.25 = [0.05, 0.55]` rad，
而站起需要膝到 1.5~2.0 rad，够不着，不是被拽住。

**Q8：增量式每步只挪 0.25 rad，会不会太慢站不起来？**
不会。50 Hz 下位移可累积，理论行程 `50 × 0.25 = 12.5 rad/s`，
膝关节从 0.3 走到 2.0 只需约 7 步、0.14 秒理论下界。实测约 2 秒完成，
余量都花在平衡调整上。0.25 这个值是训练时定的，部署侧不能随意改，否则和策略不匹配。

**Q9：这套部署最脆弱的环节是什么？**
sim2sim 的"隐性契约"——观测顺序、缩放系数、四元数约定、动作空间形式，
任何一项和训练时不一致都不会报错，只表现为行为异常。所以我的验证是
一套断言（16 项）+ 零动作单元检查 + 运行期 `‖q*−q_cur‖` 监控，把隐性契约显式化。

## 7. 延伸：这个技术在工业界怎么用

**HoST 本身。** 出自 Huang et al., *Learning Humanoid Standing-up Control across
Diverse Postures*, RSS 2025（Best System Paper Finalist）。解决的是"人形机器人摔倒后
能不能自己爬起来"这个非常实际的问题——一台几十万的机器人如果摔一次就得人去扶，
根本没法量产部署。增量动作空间是它能跨"多种初始姿态"站起的关键设计之一。

**"策略出目标角 + PD 兜底"是业界标配。** 从 Unitree、宇树到波士顿动力的学习型控制器，
几乎都是这个两层结构：高层策略 20~50 Hz 出关节目标（慢变量），底层 PD/阻抗控制
500~1000 Hz 出力矩（快变量）。本实践就是这套结构最小可运行的样例。

**增量 vs 残差的选择是个反复出现的设计决策。** 周期性运动（走、跑）业界多用残差式
（围绕参考步态摆动，收敛快）；大范围、多阶段、接触频繁切换的运动（站起、翻身、
爬起、跌倒恢复）倾向增量式或直接学关节位置。理解"什么任务该用哪种基准"，
比记住某一个公式更值钱。

**sim2sim / sim2real 的"契约对齐"是部署工程的日常。** 这个作业不训练、只部署，
恰恰暴露了真实工程里最耗时的部分：让部署侧的状态读取、观测拼装、坐标约定、
缩放系数和训练侧**逐位对齐**。我在这上面踩的四元数、视图、缩放三个坑，
在真机部署里会原样再来一遍。把这些隐性契约用断言显式化，是能直接迁移到 sim2real 的
工程习惯。
