## 0. 一句话概括

让宇树 G1 机器人在**高低不平的地形**（台阶、斜坡、石块）上按指令行走。要做成两件事：**给机器人装一双"眼睛"**，让它提前看到脚下地形的高低；**重新设计打分规则（奖励函数）**，让它真的迈步走出去，而不是站在原地骗分。

这个实践的价值不在"改了几行配置"，而在一次真实的**踩坑-诊断-修复**：第一次训练所有指标都很漂亮，机器人却在原地踏步——我是怎么发现、怎么定位、怎么修好的。这段经历是面试里"讲一个你遇到的最难的 bug"的标准答案。

## 1. 问题从哪来（Why）

### 1.1 平地能走，为什么换个地形就不行

先看上一个任务（平地速度跟踪）为什么简单。平地上，地面高度**永远是 0**，是完全可预测的常数。机器人只靠自己身上的传感器——知道自己的姿态、速度、关节角度——就够走了。这类"只感知自己身体状态"的信息，叫**本体感知**（proprioception，本体感觉，就像你闭着眼也知道自己手抬多高）。

换到粗糙地形，这个前提崩了。前方 0.5 米处是一级 15 厘米的台阶，还是一个下陷的坑？**光靠本体感知，机器人不知道**。它只能"踩到了才知道"——脚已经磕到台阶棱角上、身体已经开始前扑，才被动地去救。在台阶和斜坡上，这种"事后反应"必然失稳摔倒。

**结论**：粗糙地形要求机器人**提前看到脚下地形**。这就是本实践的第一个核心改动——加一个地形高度扫描（height scan）。

### 1.2 为什么不用摄像头 / 为什么用"高度扫描"

有人会问：给机器人装个摄像头看路不就行了？

不行，至少在这一步不合适。摄像头给的是一张**RGB 图像**——几十万个像素，机器人得先从像素里认出"哪是台阶哪是地面"，这是一个额外的、很难的视觉问题。而机器人走路真正需要的信息其实很简单：**脚前方那一小片地，每个点比我高多少、低多少**。

所以这里用的是**高度扫描**：在机器人身体正上方，向下打出一片规则排列的"激光测距射线"，每根射线量出"这个点的地面有多高"。最后得到的是一张小小的**高度图**（本实践是 17×11=187 个数），干净、直接、维度低。这既避开了图像识别的难题，又给了策略足够的前瞻信息。

### 1.3 眼睛装好了，为什么机器人还是不走

这是本实践真正的坑，也是最值钱的部分。装好眼睛、改好地形、跑满一万轮之后，我拿到一个**看起来完美**的策略：活得久、总分高、几乎不摔。但录像里它在**原地踏步**，11.98 秒只挪了不到 0.3 米。

问题不在感知，在**奖励函数**——机器人是"理性"的，它会找到打分规则里得分最高的做法。如果打分规则设计得让"站着不动"比"努力走路"得分还高，它当然选择站着。**§3 和 §5 会把这个陷阱彻底拆开。**

## 2. 核心概念（零基础可懂）

### 2.1 本体感知 vs 外部感知

```
本体感知 proprioception
  ├── 类比：你闭上眼，仍知道自己的手抬到了多高、身体有没有倾斜
  ├── 定义：机器人对"自己身体状态"的感知，不依赖外部环境
  ├── 本实践包含：机身角速度、重力方向、速度指令、各关节角度/角速度、上一步动作
  └── 局限：对"脚下地形长什么样"一无所知

外部感知 exteroception
  ├── 类比：你睁开眼，看到前面有台阶，提前抬脚
  ├── 定义：机器人对"外部环境"的感知
  ├── 本实践的形式：地形高度扫描（height scan），187 维高度图
  └── 作用：把"踩到才知道"的被动响应，变成"提前看到"的主动规划
```

### 2.2 height_scan 与 RayCaster——机器人的"眼睛"到底怎么工作

**RayCaster（射线投射器）** 是完成高度扫描的传感器。名字听着玄，原理很朴素：

**生活化类比**：想象你站在高处，手里拿一把梳子朝正下方的地面戳。每根梳齿都是一根竖直向下的"激光"，它会一直走到碰到地面为止。记下每根齿"戳到的那个点有多高"，你就得到了脚下这片地的高低起伏图。

**严格定义与配置**（`velocity_env_cfg.py:68`）：

```python
height_scanner = RayCasterCfg(
    prim_path="{ENV_REGEX_NS}/Robot/torso_link",              # 挂在机器人躯干上
    offset=RayCasterCfg.OffsetCfg(pos=(0.0, 0.0, 20.0)),      # 射线起点抬高 20 m
    ray_alignment="yaw",                                      # 网格只跟机器人转向，不跟晃动
    pattern_cfg=patterns.GridPatternCfg(resolution=0.1, size=[1.6, 1.0]),  # 采样网格
    mesh_prim_paths=["/World/ground"],                        # 只打地面，不打机器人自己
)
```

逐个参数解释：

- **`size=[1.6, 1.0]` + `resolution=0.1`**：以躯干为中心，铺一张前后 1.6 米、左右 1.0 米的网格，每 0.1 米一个采样点。射线根数 = `(1.6/0.1 + 1) × (1.0/0.1 + 1) = 17 × 11 = 187`。这就是那 187 个数的来历。
- **`offset=(0,0,20)`**：把射线的**起点**抬到躯干上方 20 米，从高空垂直向下打。为什么抬这么高？为了**不被机器人自己的身体挡住**——如果从躯干位置往下打，射线可能先打到自己的大腿。（这个 20 米有个大坑，见 §2.3 和 §5 坑二。）
- **`ray_alignment="yaw"`**：网格只跟随机器人的**转向**（yaw，绕竖直轴的朝向），**不跟随前倾后仰左右歪**（roll/pitch）。这样机器人身体倾斜时，采样网格仍然保持水平，读到的是"脚下这片地的真实形状"，而不是被身体姿态扭歪的投影。

**数学形式**（IsaacLab 的 `height_scan` 观测函数，`observations.py:301`）：

```
height_scan = sensor.data.pos_w[:, 2] - sensor.data.ray_hits_w[..., 2] - offset
              └──── 传感器高度 ────┘   └──── 命中点高度 ────┘        └ 0.5
```

符号逐个解释：
- `pos_w[:, 2]`：传感器原点在世界里的 **z 高度**（竖直高度）。
- `ray_hits_w[..., 2]`：每根射线**打中地面那个点**的 z 高度。
- 两者相减 = **传感器到地面的竖直距离**。
- 再减 `offset`（默认 0.5）。

**这个 offset=0.5 是什么？** 它**不是**从机器人几何量出来的物理常数，而是训练时人为约定的一个**"零点"**：当地面落在"参考平面"上时，输出正好是 0；地面比参考平面**低**，输出为**正**；比参考平面**高**，输出为**负**。它的唯一作用是把这 187 个数的分布中心挪到 0 附近，让神经网络好训练。**记住：部署时这个 0.5 必须一模一样，否则策略读到的整片高度图会整体平移，全部读错。**（见 §5 坑六。）

### 2.3 两个 offset 是两回事（高频混淆点）

配置里有个 `offset=(0,0,20)`，公式里又有个 `offset=0.5`。**它们毫无关系**，只是恰好同名：

| | `RayCasterCfg` 的 `offset=(0,0,20)` | `height_scan` 的 `offset=0.5` |
|---|---|---|
| 是什么 | 射线**起点**的位置偏移 | 观测值的**零点基准** |
| 作用在哪 | 加在射线发射点 `ray_starts` 上 | 从最终输出里减掉 |
| 目的 | 从高处往下打，避免被机身挡 | 把高度图分布中心对齐到 0 |
| 会不会进 `pos_w` | **不会** | —— |

最后一行是关键，也是我一度踩的坑：我担心 `pos_w[:,2]` 里含了那 20 米（如果含了，公式算出来会是约 19.9，被 clip 压成常数 5.0，187 维观测全部报废却不报错）。**实测否定了这个担心**：`pos_w_z - torso_z = 0.0`，说明那 20 米只加在射线起点上，不进 `pos_w`。IsaacLab 源码里那 20 米加在 `ray_starts`（`ray_caster.py:224`），RayCaster 内部另有一个同名的 `self._offset` 是"网格到刚体的相对变换"，纯属撞名。**结论：两个 offset 井水不犯河水，别混。**

### 2.4 奖励函数、权重、exp 型奖励

**奖励函数**（reward function）是强化学习的"打分规则"：机器人每走一步，环境根据它做得好不好给一个分数。机器人的唯一目标就是**让长期总分最大**。所以——**奖励函数怎么写，机器人就学成什么样**。写错了奖励，机器人会精确地学到"钻空子拿高分"而不是"完成你真正想要的任务"。

一个奖励函数通常是好多个**奖励项**加权求和。本实践有 9~10 项，比如：

- `track_lin_vel_xy`：速度跟得准不准（正奖励，越准分越高）——**这才是主任务**。
- `action_rate`：动作变化剧不剧烈（负奖励，即惩罚，动作越猛扣越多）。
- `feet_clearance`：摆动腿抬得够不够高。
- ……

每一项前面有一个**权重**（weight），决定这项有多重要。

**exp 型奖励**（指数型奖励）是一个反复出现的关键形式：

```
reward = weight × exp(−误差² / std²)
```

- 当误差 = 0（做得完美），`exp(0)=1`，拿到满分 = **weight**。
- 误差越大，`exp` 越接近 0，分数越低。

**这里有个极其重要的推论：exp 型奖励的权重，就是这一项的分数上限。** 把 `track_lin_vel_xy` 的权重从 1.0 提到 3.0，不是"多加一点分"，而是把这一项的天花板从 1.0 抬到 3.0——机器人"把速度跟准"能拿到的最高回报直接翻了三倍。§3.1 会讲这个推论如何救活了整个训练。

### 2.5 终止条件（termination）

**终止条件**决定"这一局什么时候结束、重来"。它有两种作用：一是省时间（机器人已经摔了，没必要再模拟它躺在地上的过程），二是**塑造行为**（把"绝对不能做的事"设成立即结束，机器人就会学着避开）。

本实践三个终止项：

| 终止项 | 触发条件 | 作用 |
|---|---|---|
| `time_out` | 一局到达最大步数（1000 步 = 20 秒） | 正常超时，善终 |
| `bad_orientation` | 机身倾斜超过 `limit_angle=1.0` 弧度（≈57°） | 判定摔倒 |
| `illegal_reset_contact` | 躯干 `torso_link` 接触力 >1.0，且**累计满 5 步** | 判定用非法部位撑地 |

两个数值细节值得记牢：

- **`bad_orientation` 的 57°**：知道这个具体角度，才能读懂日志。比如"`bad_orientation` 占比 0.857"不是笼统的"姿态不好"，而是精确的"**86% 的局是因为倾斜超过 57° 结束的**"。
- **`illegal_reset_contact` 的"累计 5 步"**：这是一个**去抖设计**。为什么不是"碰一下就结束"？因为刚 reset 的瞬间、或正常行走中的轻微擦碰，接触力可能瞬间超阈值。如果碰一下就重置，机器人会被反复打断，训练根本没法展开。要求"累计 5 步"才触发，就把这些偶发的瞬时碰撞滤掉了。（作业文档 Q4 专门警告过：这个阈值设太小，机器人会被不停重置。）

### 2.6 课程学习（curriculum learning）

**生活化类比**：教小孩游泳，不会一上来就扔进深水区，而是从浅水、扶板、到深水，**难度随能力逐步加大**。

**定义**：`curriculum learning` 让训练难度**随机器人能力自动递进**。本实践有两条课程：

- **`terrain_levels`（地形难度）**：地形分 10 个难度等级（0 最平、9 最崎岖）。某个机器人如果这一局**走出去超过 4 米**，说明它 hold 住了当前难度，下一局给它升一级；走得太差就降一级。
- **`lin_vel_cmd_levels`（速度指令难度）**：一开始只要求机器人跟踪很小的速度（±0.1 m/s），等它跟得够好（跟踪奖励超过某个门槛），就把要求的速度范围放宽，最终拉满到 [−0.5, 1.0] m/s。

课程学习有一个**反直觉但极其重要的后果**：**训练后期，总奖励（reward）下降，往往不是坏事，而是课程在升难度**。同一个机器人，在更难的地形、更高的速度要求下，拿到更低的分是正常的——就像同一个学生，从做小学题换成做中学题，分数下降不代表他变笨了。**§3.2 和 §5 坑四会把这件事讲透**，因为它极易被误判成"训练崩了"。

### 2.7 actor 与 critic，以及"特权 critic"

PPO（本实践用的训练算法）内部有两个神经网络：

- **actor（演员）**：机器人的"大脑"，输入观测、输出动作。**部署时只用它。**
- **critic（评论家）**：训练时的"陪练教练"，负责评估"当前局面有多好"，用来指导 actor 更新。**部署时丢掉。**

因为 critic 训练完就扔、不上真机，所以它可以"作弊"——**看一些 actor 看不到的信息**（比如真实的机身线速度，真机上没有这个传感器）。这叫**特权信息**（privileged information）。有一条硬规则：**critic 的信息必须 ⊇ actor 的信息**。教练懂的必须比学生多，否则教练的评估比学生还瞎，整个训练就跑偏了。这条规则直接决定了 §4.1 里"height_scan 要同时接进 policy 和 critic"的写法。

## 3. 算法原理

### 3.1 奖励设计的核心：先问"如果它什么都不做，能拿多少分"

这是本实践最重要的方法论，值得单独讲。

强化学习的机器人是**极端理性**的：它不理解你的意图，只会把奖励总分榨到最大。所以设计完奖励函数，第一件事不是去训练，而是**心算一遍：如果机器人杵在原地一动不动，它能拿多少分？**

我第一次训练就栽在没做这个心算。把第一次训练的各奖励项终值全部拆开排序（单位是每秒平均分）：

```
feet_clearance       +0.8228   ← 第一大正奖励，比主任务还高
track_lin_vel_xy     +0.6355   ← 主任务，但上限只有 1.0
gait                 +0.5014   ← 上限就是 0.5，等于拿满
alive                +0.1448   ← 上限 0.15，拿了 96.5%
────────────────────────────
action_rate          -0.4281   ← 以下惩罚，只在"动起来"时才产生
joint_vel            -0.1334
joint_deviation_arms -0.1228
...
正奖励合计 +2.3273    惩罚合计 -0.9873    净 +1.3400
```

看出问题了吗？**站着不动，光靠 `feet_clearance + gait + alive` 就白拿约 1.47 分，而且几乎不付任何惩罚**（因为所有惩罚项都是对"动作"收费的，不动就不扣）。

两个"站着也能拿满分"的漏洞：

**漏洞一 —— `feet_clearance`（抬脚高度奖励，拿了 0.8228）**。它的公式是：

```
reward = exp( −Σ[ (脚高 − 目标高)² × tanh(k·‖脚的水平速度‖) ] / std )
                                    └──────── 关键乘子 ────────┘
```

设计意图是"只要求**摆动中**的脚抬够高，支撑腿不管"，所以乘了一个"脚的水平速度"项。副作用是致命的：**脚不动 → 速度=0 → `tanh(0)=0` → 整个括号=0 → `exp(0)=1.0` 满分**。也就是说，**站着不动是这一项的全局最优解**。

**漏洞二 —— `gait`（步态相位奖励，拿了 0.5014，上限就是 0.5）**。它按固定 0.8 秒周期判断"这条腿现在该支撑还是该摆动"，符合就加分。双脚长期都着地时，"该支撑且确实着地"的那部分时间照样得分，算下来静止能拿约 0.55/1.0，实测 0.5014，吻合。

**加上惩罚项的不对称性**，机器人面对的实际选择变成了：

| 策略 | 能拿的正奖励 | 要付的惩罚 | 净收益 |
|---|---|---|---|
| **站着不动** | ≈ 2.1 | ≈ 0 | **≈ 2.1** |
| **努力行走** | track 顶多再多拿 0.36（0.64→1.0 上限） | 付出全套动作惩罚 | 更低 |

**走路的边际收益上限只有 0.36，边际成本却是全套动作惩罚。一个理性的策略当然选择站着。** 它不是"没学会走"，是"精确地学会了不走最划算"。

**修复的思路不是"把奖励调大"，而是"改变边际激励比"**——让"多走一点"带来的好处，明显盖过它引发的惩罚。最关键的一手是把 `track_lin_vel_xy` 的权重 **1.0 → 3.0**：

- 改之前：跟踪从 60% 提到 100%，只多拿 `1.0 × 0.4 = 0.4` 分。
- 改之后：同样的提升多拿 `3.0 × 0.4 = 1.2` 分。

这 1.2 足以盖过 `action_rate`（−0.43）等惩罚，走路第一次变得"有利可图"。**注意：改的是 weight（重要性/上限），不是 std（误差尺度）**——这两个旋钮管的是不同的事，这次要改的是"这件事有多重要"，所以动 weight。（完整的 10 项权重改动见 §4.3。）

### 3.2 课程学习：为什么 reward 下降反而说明训练是对的

这是本实践第二个反直觉的原理，也是复查训练时差点误判的地方。

用 `assess_training_budget.py` 复查时，`Train/mean_reward` 分五段的均值是：

```
13.7 → 38.9 → 37.0 → 31.4 → 28.3      末段比峰值 −11.1%
```

**孤立地看这条线，结论会是"训练退化了"**。但同一时期，两条课程指标是另一幅图景：

```
lin_vel_cmd_levels   0.21 → 0.56 → 0.85 → 1.00 → 1.00   ← 速度指令难度已拉满
terrain_levels       4.33 → 2.21 → 2.37 → 3.34 → 3.92   ← 地形难度在回升
```

真相是：**reward 下降是因为任务在变难，不是策略在变差**。

- `lin_vel_cmd_levels` 饱和到 1.00，说明速度课程已经走完——机器人现在要跟踪的是**满量程**的速度指令（最高 1.0 m/s），而不是训练初期那些温柔的小目标。目标变难，跟踪奖励自然回落。
- `terrain_levels` 从谷底 2.21 爬回 3.92，地形也在同步加难。

**同样的策略，在更难的任务上拿到更低的 reward，是课程学习的正常表现，甚至是好现象**——它证明课程在推着机器人啃更硬的骨头。

判断的正确姿势：**看到 `Curriculum/*` 在上升、同时 reward 在下降，要单独归为"课程升难度"，绝不能和"训练退化"混为一谈**。这条判据后来直接写进了评估脚本——没有它，本实践的训练会被误判成失败。

### 3.3 一个更硬的证据：terrain_levels 从 0 爬到 4

光看 reward 容易被骗，但有一个指标几乎骗不了人——**`terrain_levels`（机器人稳定停留的地形难度）**。

它的升级判据是**净位移 > 4 米**（源码里是"走出去超过地形块半长"，地形块 8 米，半长即 4 米）。这意味着：**机器人只有真的走出去了，难度才会升上去**。

- 调参前：`terrain_levels` **全程为 0**。因为机器人原地踏步，永远走不到 4 米，一路被降级到最简单地形并停在那里。这一个指标就足以戳穿"指标全绿"的假象。
- 调参后：`terrain_levels` 稳定在 **4.0** 左右。机器人**真的在走出去**。

它的完整演化过程堪称教科书：

```
@4384  terrain_levels 0.01   track 2.04   ← 刚开始能走
@5794  1.83   track 1.77             ← 地形变难，跟踪指标回落
@6259  2.84   track 1.98             ← 适应后回升
@9999  4.05   track 2.24             ← 稳定在难度 4
```

**升级 → 变难 → 指标回落 → 适应 → 回升 → 再升级**，这正是 §3.2 讲的道理在一条曲线上的完整体现。

## 4. 代码走读

### 4.1 把 height_scan 接进观测（`rough_env_cfg.py:97-110`）

```python
scan_obs = ObsTerm(
    func=mdp.height_scan,
    params={"sensor_cfg": SceneEntityCfg("height_scanner")},
    clip=(-1.0, 5.0),
    noise=Unoise(n_min=-0.1, n_max=0.1),
)
self.observations.policy.height_scanner = scan_obs                      # ① policy 加噪
self.observations.critic.height_scanner = copy.deepcopy(scan_obs)      # ② critic 不加噪
self.observations.critic.height_scanner.noise = None
```

**这段在做什么**：把 187 维高度图，作为一个新观测项，接到策略网络（policy）和评论家网络（critic）的输入里。

**几个"为什么这么写"：**

- **`clip=(-1.0, 5.0)` 是双保险**。一是压住异常值域；二是射线偶尔打空时会返回 `inf`（无穷大），而 `torch.clip(inf, -1, 5) == 5.0`，正好把 `inf` 截成一个正常数，不会污染网络输入。（记住这个 clip 只保护观测；奖励和终止项**没有**这层保护，所以 §4.2 必须自己做 inf 防护。）
- **`noise=Unoise(-0.1, 0.1)` 只加在 policy，不加在 critic**（第 ①② 行的区别）。真机的高度图来自激光雷达或深度相机，有测量误差和标定漂移，给 policy 加 ±0.1 米的均匀噪声，是逼它别去死磕单根射线的精确值，练出鲁棒性。critic 是训练时的特权教练（见 §2.7），要看**干净**的信息才能做准评估——它的信息集必须 ⊇ policy，所以也接了 height_scan，但去掉噪声。
- **为什么能直接给实例赋值**（`self.observations.policy.height_scanner = ...`）而不用重新定义一个观测类？因为 Isaac Lab 的 ObservationManager 遍历的是配置对象的**实例字典**（`__dict__`），动态加的属性会被正常收集，且 Python 3.7+ 的字典**保持插入顺序**，新项自动排在末尾。**这个顺序是 sim2sim 的硬约束**：MuJoCo 侧要按完全相同的顺序手工拼观测向量，顺序错了不报错，只会让策略读到错位的数——排查起来极其痛苦。

**观测维度的变化**（这是报告里必答的）：

| 观测项 | 维度 |
|---|---|
| base_ang_vel / projected_gravity / velocity_commands | 3 + 3 + 3 |
| joint_pos_rel / joint_vel_rel / last_action | 29 + 29 + 29 |
| **height_scanner（新增）** | **187** |
| 单帧合计 | **283** |
| × history_length = 5（拼 5 帧历史） | **1415** |

即策略网络的输入从基线的 `96 × 5 = 480` 维，扩到了 **1415** 维。

### 4.2 带 inf 防护的地面高度估计（`mdp_ext.py:75-116`）

这段是"眼睛"在奖励里的正确用法，也是一次静默崩溃的教训凝结成的代码。

先看**官方版为什么不能直接用**。IsaacLab 官方的 `base_height_l2(sensor_cfg=...)` 内部是：

```python
adjusted_target = target_height + torch.mean(sensor.data.ray_hits_w[..., 2], dim=1)
```

**没有任何 inf 防护**。射线打空时 `ray_hits_w` 是 `inf`，而 `torch.mean` 只要输入里有**一个** `inf`，整个环境的均值就是 `inf` → 奖励 `inf` → 反向传播出 `NaN` → 优化器把 `NaN` 写进网络权重 → 之后每一步输出全是 `NaN`。最阴险的是**它不抛异常**，训练看起来还在跑，只是策略已经变成一坨 `NaN`。

自实现的版本（`ground_height_from_scan`）关键是**先掩掉 inf，再求均值**：

```python
z = sensor.data.ray_hits_w[..., 2]
valid = torch.isfinite(z)                                     # 标出没打空的射线
n_valid = valid.sum(dim=1)
z_sum = torch.where(valid, z, torch.zeros_like(z)).sum(dim=1) # 只累加有效的
mean_valid = z_sum / n_valid.clamp(min=1)                     # 求有效值的均值
return torch.where(n_valid > 0, mean_valid, fallback)         # 全打空则退回 0.0
```

**顺序不能反**：不能先 `mean` 后 `nan_to_num`——那时 `inf` 已经污染了整个均值，补救时真实信息已经没了。必须先掩后算。

`fallback=0.0` 的选择也有讲究：一个环境的射线**全部**打空时退回 0.0，等于退化成基线"地面在世界原点"的假设。这是最保守的选择——最坏情况下行为和改之前完全一致，**不引入任何新的失败模式**。

### 4.3 十项权重的重设（`rough_env_cfg.py:135-197`）

依据课程《第二章作业讲解》p5/p6 的推荐表。逐项的"为什么"：

| 奖励项 | 改前 | 改后 | 为什么 |
|---|---|---|---|
| `track_lin_vel_xy` | 1.0 | **3.0** | exp 奖励权重=上限；把走路的边际收益从 0.4 抬到 1.2（见 §3.1） |
| `track_ang_vel_z` | 0.5 | **2.0** | 同理，加强转向跟踪 |
| `gait` | 0.5 | **0** | 固定步态相位在粗糙地形是束缚；且是"站着不动"的收益来源之一 |
| `feet_air_time` | 无 | **+0.5** | **唯一直接奖励"迈步"的项**，双脚同时着地得 0 |
| `stand_still` | 无 | **−1.0** | 把"停"定义成具体姿态，让走/停成为可区分的两种模式 |
| `joint_deviation_arms` | −0.1 | **−0.5** | 抑制手臂乱摆抬高重心晃动 |
| `joint_deviation_waists` | −1.0 | **−2.0** | 同上（腰） |
| `joint_deviation_legs` | −1.0 | **−2.0** | 同上（腿） |
| `base_height` | −10 | **−20** | 防守：track 放大后，防止策略靠弓身下蹲刷速度分 |
| `feet_clearance` | 世界系基准 | **相对地形基准** | 台阶上不再误罚"正确抬脚"（见 §5 坑三） |

三个最该讲的：

- **`feet_air_time`（新增 +0.5）是补上的关键一项**。它只在 `single_stance`（恰好**一只**脚着地）时计分：双脚同时着地（站立）得 0，双脚同时腾空（跳跃）也得 0，只有**交替迈步**才得分。天然反"原地不动"。内部还乘了 `‖cmd‖>0.1` 的掩码，零指令时不发钱，不会诱导原地空踏步。

- **`stand_still`（新增 −1.0）的作用容易被误解**。它是 `Σ|关节角 − 默认站姿角| × (‖cmd‖<0.1)`，配负权重 = "指令接近零时，偏离默认站姿就挨罚"。它**不是让机器人更爱站着**，恰恰相反：它把"停"**钉死成一个具体姿态**，从而让"走"和"停"成为两个**可区分**的模式。缺了它，策略完全可以用同一套"原地小幅摆动"去应付所有指令——那正是第一次训练失败的形态。

- **`base_height` 加倍（−10 → −20）是放大 track 时的配套防守**。这是调参的一个通用结构：**每当你放大一个激励，就要检查它会不会打开一条新的作弊路径**。track 权重提到 3.0 后，机器人可能发现"弓身下蹲能降重心、更容易跑快拿速度分"。加大高度惩罚，提前把这条捷径堵死。

### 4.4 sim2sim 的观测拼装（`sim2sim/sim2sim_raycaster.py`）

sim2sim 的本质是**用一套完全独立的代码，把训练侧"隐式自动完成"的事，在部署侧手工复现一遍**——任何一处不一致都不报错，只会让行为悄悄变错。观测顺序就是最典型的一处：

```python
OBSERVATION_ORDER = (
    "base_ang_vel", "projected_gravity", "velocity_commands",
    "joint_pos_rel", "joint_vel_rel", "last_action",
    "height_scanner",              # ← 必须和训练侧 §4.1 的顺序完全一致
)
```

这里 MuJoCo 侧手写的顺序，必须和训练侧 ObservationManager 收集到的顺序逐字节对齐。训练侧那个"新项自动排末尾"的行为（§4.1），在这里变成了一条必须人工保证的契约。

除观测顺序外，部署侧还要手工复现三件训练框架自动做的事：**关节顺序映射**（`deploy.yaml` 里的策略关节序 vs MuJoCo 传感器的 SDK 关节序）、**动作缩放**（`q_target = q_default + 0.25·action`）、**PD 控制**（把目标角转成力矩）。代码还硬校验了 `policy_dt` 与 `deploy.yaml` 里 `step_dt` 一致，不一致直接抛错——这类"对齐检查"就是 sim2sim 的价值所在。

## 5. 我踩过的坑（面试素材）

### 坑一：指标全绿，机器人却在原地踏步（本实践的招牌坑）

**现象**：第一次训练跑满 10000 轮，常规指标全部漂亮：Mean episode length 489→**960**（满分 1000），`time_out` 占比 0.14→**0.906**（90% 正常超时），`bad_orientation` 占比 0.86→**0.094**（几乎不摔），Mean reward 7.14→**26.32**（涨了 3.7 倍）。**任何看板都会判定"训练成功"**。

**第一反应**：成了，导出策略准备交作业。

**为什么这么想是错的**：这四个指标只回答了"活得久不久"和"总分高不高"，**没有一个回答"它在不在做我们要的事"**。录像一放，机器人在**原地踏步，11.98 秒净位移不到 0.3 米**。

**怎么找到真因**（三步）：
1. **先用录像证伪**。play 相机锁定在 0 号机器人身上，机器人恒在画面中心，所以**背景的位移就是机器人的位移**。对比第 5 帧和第 598 帧，背景台阶只挪了 30~40 像素，台阶在 8 米开外，折算净位移 < 0.3 米。
2. **再看任务本身的度量**。`error_vel_xy`（速度跟踪误差）不降反升：0.135 → 0.615；`track_lin_vel_xy` 在 4000 轮就到 0.60、之后 6000 轮只挪到 0.628，**早就平台了**；`terrain_levels` **全程为 0**（升级要净位移>4m，它做不到）。
3. **最后拆开所有奖励项排序**（§3.1 那张表），一眼看到 `feet_clearance` 是第一大正奖励、站着能白拿约 1.47 分。

**根因**：奖励函数把"站着不动"设成了最优解——`feet_clearance` 脚不动就满分、`gait` 站着也拿大半分，而所有惩罚都只对"动作"收费。走路是亏本买卖。

**教训**：`episode_length` 和 `reward` 上涨 **≠** 任务学会了。判断训练成败必须回到**任务本身的度量**（这里是 `error_vel_xy` 和净位移），并把奖励**分项拆开**看策略到底靠什么拿分。这条教训后来还救了 sim2sim——部署侧也不看录像，写了 headless 脚本量化实际速度和净位移。

### 坑二：担心 height_scan 被那 20 米污染（一次靠数据证伪的排查）

**现象**：读 RayCaster 配置，看到 `offset=(0,0,20)`，又看到 `height_scan` 公式里用 `pos_w[:,2]`。

**第一反应**：糟了，`pos_w` 里如果含了这 20 米，公式会算出约 19.9，被 `clip(-1,5)` 全压成常数 5.0——那 187 维观测就全废了，而且不报错。

**为什么这个担心不能直接下结论**：它只是一个基于同名参数的**猜测**，没有证据。同名不等于同物。

**怎么找到真因**：直接打点实测——`pos_w_z − torso_z = 0.0`，`height_scan` 的值域是 `[0.325, 0.536]`，clip 之后还有 390 个不同的值（不是常数）。**数据直接否定了猜测**。再去翻 IsaacLab 源码确认：那 20 米只加在射线**起点** `ray_starts`（`ray_caster.py:224`），不进 `data.pos_w`；RayCaster 内部另一个同名 `self._offset` 是网格到刚体的相对变换，纯撞名。

**根因**：`RayCasterCfg.offset`（射线起点偏移，20 m）与 `height_scan` 的 `offset`（观测零点，0.5 m）是两个无关的东西，只是同名（见 §2.3）。

**教训**：遇到"我担心 X 会导致 Y"，**先打一个点测出来，别靠读代码脑补**。一次 `print` 省下半天读源码。这也是为什么部署要 sim2sim——很多约定只有实测才敢确认。

### 坑三：世界系绝对高度判据，在非平地上误杀 1/4 的 episode

**现象**：16 环境冒烟测试，`Episode_Termination/base_height = 0.25`——**四分之一的局是被"机身太低"这条终止条件判摔倒的**。

**第一反应**：机器人是不是真的老是蹲太低？

**为什么这么想是错的**：机器人姿态完全正常。问题在判据本身。基线的 `base_height` 奖励和终止，都是拿机器人根节点的**世界系 z 高度**和一个常数比。平地上地面 z≡0，"世界系高度"和"离地高度"是同一个数，没问题。但换到粗糙地形，**倒金字塔楼梯和下坡的地面本身就低于 0**——机器人好端端站在一个低洼地形里，"世界系 z"确实很低，于是被误判成摔倒。

**怎么找到真因**：拆终止原因占比，发现 `base_height` 异常地高（0.25）。再去翻 IsaacLab 源码，`root_height_below_minimum` 的注释白纸黑字写着：`This is currently only supported for flat terrains`——官方自己知道这函数只支持平地。

**根因**：世界系绝对高度判据默认"地面在 z=0"，这个前提在粗糙地形上不成立。

**教训**：**任何"世界系绝对高度"的判据，一旦离开平地都要重新审视**。修法是把判据从"机器人在世界里多高"换成"机器人相对**脚下地面**多高"，地面高度由 height_scan 估计。本实践在 `base_height` 奖励、`base_height` 终止、`feet_clearance` 奖励**三处**都栽在同一个坑上，全部改成相对地形高度。

### 坑四：训练后期 reward 从 38.9 掉到 28.3，差点误判成训练退化

**现象**：复查训练预算时，`Train/mean_reward` 分五段是 13.7 → 38.9 → 37.0 → 31.4 → **28.3**，末段比峰值跌了 11%。

**第一反应**：训练退化了，是不是训崩了 / 过拟合了 / 学习率炸了。

**为什么这么想是错的**：只看了 reward 一条线。reward 是"当前难度下的得分"，而**难度本身是会变的**（课程学习）。

**怎么找到真因**：把课程指标叠上来看——同期 `lin_vel_cmd_levels` 从 0.21 一路到 **1.00 拉满**，`terrain_levels` 从谷底 2.21 爬回 3.92。速度指令和地形难度**都在同步加大**。

**根因**：reward 下降是**任务在变难**，不是策略在变差。同一个策略在更难的任务上拿更低的分，是课程学习的正常表现（见 §3.2）。

**教训**：**单一指标不足以判断训练状态**。看到 `Curriculum/*` 上升伴随 reward 下降，要单独归为"课程升难度"。这条判据写进了评估脚本——没有它，本实践会被误判成训练失败。有意思的是，这和坑一是**同一个病的两面**：坑一是"指标涨了但其实没学会"，坑四是"指标跌了但其实是好事"，共同点都是**不能只看一个数**。

### 坑五：断点续训（--resume）丢失了课程进度

**现象**：训练在 9000 轮因外部原因中断，用 `--resume` 从 `model_9000.pt` 续训。续训**瞬间**：`lin_vel_cmd_levels` 从 1.0 掉回 0.1，`bad_orientation` 占比从 0.20 飙到 0.63。

**第一反应**：checkpoint 是不是存坏了 / 续训读错了模型。

**为什么这么想是错的**：模型没坏。问题是 **`--resume` 只恢复了策略网络和优化器，没有恢复环境侧的课程进度**。翻开 checkpoint，里面只有四个键（`iter` / `model_state_dict` / `optimizer_state_dict` / `infos`），而 `infos` 是 `None`。两条课程的状态全在**环境侧**：`terrain_levels` 存在 `TerrainImporter` 里、`lin_vel_cmd_levels` 存在 command 配置里，环境一重建就复位。

**怎么找到真因**：`torch.load` 打开 checkpoint 看键；对照续训瞬间的课程指标断崖。逻辑上还有隐忧——命令课程的升级门槛是 `reward > 3.0×0.8 = 2.4`，而策略在难地形上只有 ~2.2，且这个课程**只加不减**（源码里只有 `clamp` 放宽、没有收窄逻辑）。原 run 能爬满，是因为前 4000 轮地形还停在 0 级、跟踪容易。

**根因**：checkpoint 只含策略与优化器，环境侧的课程进度不在其中，续训会丢。

**实际结局是恢复了**：命令范围变窄后跟踪变容易、reward 越过 2.4 门槛，课程重新逐级爬升，约 600 轮后回到 1.0，地形等级随之回到 4.05，最终数据有效。**但这是运气好**——如果当时 track reward 更低、或剩余轮数更少，课程可能爬不回来，得到的"最终指标"就会是在**更容易的指令分布**下测的，看着更好实则退化，且极难察觉。

**教训**：**长训练中断后不能直接 `--resume` 了事，必须先确认课程指标（terrain_levels / cmd_levels）回到中断前水平**，再采信最终数字。

### 坑六：MuJoCo raycaster 插件与运行时版本不一致

**现象**：sim2sim 里 height_scan 靠一个第三方 MuJoCo 插件提供，报 `plugin mujoco.sensor.ray_caster not found`。

**第一反应**：路径填错了，或插件没编译成功。

**为什么这么想是错的**：路径没错、插件也编出来了。真正的要求是——**编译插件时用的 MuJoCo 版本，必须和 Python 运行时加载的 MuJoCo 版本严格一致**。这类 C++ 编出来的 `.so`，和主程序之间有个二进制接口约定（ABI），版本一变约定就对不上，报的却是误导性的"插件找不到"。

**怎么找到真因**：`ldd libsensor_raycaster.so` 看它链接的 `libmujoco.so` 是哪个版本，对照 `python -c "import mujoco; print(mujoco.__version__)"`，一比就露馅。（本机锁在 3.12.0，插件也必须对 3.12.0 编。适配过程中还遇到插件源码与 MuJoCo 3.12 之间三处 API 断裂，另有处理。）

**根因**：C++ 动态库与运行时之间的 ABI 版本绑定，跨版本不兼容。

**教训**：凡"编译出来的插件/扩展"，版本一致性是硬约束。装任何新包前 `pip install --dry-run` 确认不会顺手升级 mujoco。这条和教学文档 01 的坑三是同一类问题。

## 6. 面试可能怎么问

**概念题**

1. **Q：为什么粗糙地形要加 height_scan，平地不用？**
   A：平地地面高度恒为 0，本体感知（姿态、速度、关节）就够。粗糙地形上机器人无法从本体状态推断前方是台阶还是坑，只能"踩到才知道"被动响应，必然失稳。height_scan 提供 187 维前瞻高度图，把被动响应变成主动规划。

2. **Q：height_scan 那个值到底是什么？offset 是干嘛的？**
   A：值 = 传感器高度 − 射线命中点高度 − offset，即"传感器到地面的竖直距离再减一个基准"。offset=0.5 不是物理常数，是人为约定的零点，让高度图分布中心落在 0 附近好训练。地面比基准低输出为正、高为负。部署时 offset 必须一致，否则整片高度图平移读错。（追问：配置里的 offset=(0,0,20) 是射线起点偏移，防止被机身挡，和这个 0.5 无关。）

3. **Q：critic 为什么也要接 height_scan？**
   A：critic 是训练时的评估网络（部署丢弃），它的信息集必须 ⊇ actor，否则教练比学生还瞎、优势估计失真。所以 height_scan 同时接进 policy（加噪，练鲁棒）和 critic（不加噪，看干净信息做准评估）。

**实现题**

4. **Q（招牌题）：你训练时 reward 一直在涨、机器人却不走路，怎么回事？**
   A：这是我这个实践最典型的坑。第一次训练 reward 涨了 3.7 倍、episode length 逼近满分，但录像里机器人原地踏步、11.98 秒挪不到 0.3 米。根因是奖励函数把"站着"设成了最优解——`feet_clearance` 因为乘了脚速项，脚不动就 exp(0)=1 满分；`gait` 站着也能拿大半分；而所有惩罚都只对动作收费，不动不扣。走路的边际收益上限只有 0.36，成本却是全套动作惩罚。修法是把 track 权重 1.0→3.0 改变边际激励比，再补一个只奖励交替迈步的 `feet_air_time`。教训是 reward/episode_length 上涨不等于学会了任务，必须看 `error_vel_xy` 和净位移这些任务本身的度量。

5. **Q：`feet_air_time` 和 `stand_still` 分别解决什么？**
   A：`feet_air_time` 是唯一直接奖励"迈步"的项，只在恰好一只脚着地时计分，站立和跳跃都得 0，天然反原地不动，还有零指令掩码防空踏步。`stand_still` 是低速指令下惩罚偏离默认站姿，作用是把"停"钉成一个具体姿态，让走和停成为可区分的两种模式，避免策略用同一套原地摆动应付所有指令。

6. **Q：base_height 判据为什么要从世界系高度改成相对地形高度？**
   A：基线用根节点世界系 z 和常数比，平地上等价于离地高度。但粗糙地形里倒金字塔楼梯、下坡的地面本身低于 0，机器人姿态正常却因"世界系 z 太低"被误判摔倒，实测误杀了 1/4 的 episode。改成"根节点 z − 脚下地面高度"，地面由 height_scan 估计。IsaacLab 官方注释也承认原函数只支持平地。

**深挖题**

7. **Q：训练后期 reward 下降，是不是训练退化了？**
   A：不一定，多半是课程在升难度。本实践复查时 reward 从 38.9 掉到 28.3，但同期 `lin_vel_cmd_levels` 拉满到 1.0、`terrain_levels` 从 2.21 爬回 3.92——任务在变难，同一策略拿更低分是正常的。判据是看 `Curriculum/*` 是否上升。更硬的证据是 `terrain_levels`：它升级要净位移>4m，全程为 0 说明没走出去，稳定在 4 说明真在走。

8. **Q：断点续训要注意什么？**
   A：`--resume` 只恢复策略和优化器，不恢复环境侧的课程进度（checkpoint 里 infos=None）。续训瞬间 `cmd_levels` 从 1.0 掉回 0.1。而命令课程只加不减、升级门槛是 reward>2.4，若策略在难地形上分不够就可能爬不回来，导致最终指标是在更容易的分布下测的、虚高。所以中断后必须先确认课程指标回到中断前水平再采信数据。

9. **Q：sim2sim 到底验证了什么？为什么不能只在 Isaac Sim 里看？**
   A：sim2sim 用一套独立代码把训练框架自动做的事（观测拼装顺序、关节序映射、动作缩放、PD 控制）手工复现一遍，任何不一致都不报错只会让行为悄悄变错，所以它能反查出训练侧的隐式约定。而且本实践栽过"指标全绿但原地踏步"，所以部署侧也不看录像——写了 headless 脚本量化实际速度和净位移，还对照课程自带 checkpoint 做基准。自训策略前进 vx 0.484（基准 0.535）、复合指令下 0.502 反超基准 0.403，姿态投影重力 z=−1.000 全程未摔。

**结果题**

10. **Q：训练到什么程度算够？**
    A：轮数是手段、收敛是目的。我们跑了 9999 轮（官方推荐 15000 的 67%），但主任务 `track_lin_vel_xy` 后 1/3 已在 2.0~2.28 平台震荡、不再上升，末值 2.236/3.0，是官方 15000 轮参考值 2.263 的 98%。判断顺序应是：先看核心指标是否还在单调上升（在涨就没跑够），再看是否达到参考水平，最后才看轮数。只看轮数会得出"严重不足"的错误结论。

## 7. 延伸：这个技术在工业界怎么用

**"本体感知 + 地形高度扫描"是当前足式/人形机器人越野行走的主流范式。** 苏黎世联邦理工（ETH）2022 年让 ANYmal 四足机器人走遍山地森林的工作（Miki et al., *Science Robotics 2022*），核心就是"本体感知 + 外部地形感知 + 大规模并行训练 + 地形课程"。你在本实践做的事——加 height_scan、配 `ROUGH_TERRAINS_CFG` 十级地形课程——是那套方法在人形机器人上的直接对应。区别只在真机上，那张高度图不是仿真射线打出来的，而是激光雷达或深度相机重建的——这也是为什么训练时要给 height_scan 加噪：提前适应真机传感器的误差。

**"奖励函数里站着是最优解"是这个领域最常见的失败模式之一，有正式名字叫 reward hacking（奖励作弊）。** 工业界的对策和本实践一致：设计完奖励先算"什么都不做能拿多少分"，用课程学习引导，用一个直接奖励目标行为的项（这里是 `feet_air_time`）去对冲那些"静止也能拿分"的漏洞。宇树、Agility、波士顿动力内部的运控团队，日常大量时间就花在这种"奖励塑形（reward shaping）+ 反复看分项 + sim2sim 验证"的循环里——和你这个实践做的事，是同一套工作方法。

**课程学习 + terrain_levels 这套自动难度调节，也是规模化训练的标准件。** 手工给每个机器人挑地形难度不现实，让难度跟着"净位移>4m"这类能力信号自动升降，既保证了初期不被难地形劝退、又保证了后期不断被推向极限。你在本实践观察到的"reward 下降其实是课程升难度"，正是这套机制运转正常的标志——能读懂这条曲线，是判断一次长训练成败的基本功。
