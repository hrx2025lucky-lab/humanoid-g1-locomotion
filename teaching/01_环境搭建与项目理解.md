# 教学文档 01 · 环境搭建与项目理解

> 面试复习用。配套实践文档：`docs/实践1_环境搭建与项目理解.md`。
> 本文所有路径相对 `repos/unitree_rl_lab/`，行号为本机实测。

## 0. 一句话概括

这个实践做两件事：**先在电脑上把宇树 G1 人形机器人的强化学习训练环境装起来、跑通一次完整流程**（训练 → 回放 → 换个仿真器验证），**再把这个开源项目的目录读明白**——重点是搞清楚：你在命令行敲一个 `--task Unitree-G1-29dof-Velocity`，这串字符是怎么一步步变成一个真的能训练的机器人环境的。

不涉及改算法，是后面所有实践的地基。

## 1. 问题从哪来（Why）

### 1.1 不装环境会怎样

强化学习训练机器人，本质是让机器人在一个**虚拟世界**里摔几亿次跤，从摔跤里学会走路。真机器人摔几亿次早就散架了，也没人有那个时间。所以第一步必须有一个**物理仿真器**：一个能算出「给关节施加这么大力矩、下一时刻机器人会摔向哪边」的程序。

装不好环境，后面 10 个实践一个都做不了。这就是为什么第一个实践看着最"没技术含量"，却是最容易劝退人的一关——它考的不是算法，是能不能把一堆版本互相挑剔的软件拼在一起不报错。

### 1.2 为什么要两个仿真器，不能只用一个

课程同时用了两个物理仿真器，很多人第一反应是"多此一举"。它们分工不同：

- **Isaac Sim**：英伟达出的仿真器，能用一块显卡**同时**模拟几千个机器人（本实践用 4096 个）。训练需要海量试错，靠的就是这种并行。
- **MuJoCo**：另一个仿真器，一次只跑一个机器人，但它和真机的部署代码更接近。

核心逻辑是这样的：策略（机器人的"大脑"）是在 Isaac Sim 里练出来的。但你怎么知道它学到的是**真本事**，还是只是摸清了 Isaac Sim 这个仿真器的**数值脾气**？

打个比方：一个学生只在 A 老师的题库里刷题，考了满分。换 B 老师出的题还能不能考好？如果不能，说明他背的是答案，不是会做题。把策略从 Isaac Sim 搬到 MuJoCo 里再跑一遍，就是"换个老师出题"——这个过程叫 **sim2sim**（simulation-to-simulation，仿真到仿真的迁移验证）。策略能扛过 sim2sim，才有资格谈上真机。

### 1.3 为什么推荐二进制安装而不是 pip 一键装

Isaac Sim 有两种装法：`pip install` 一行搞定，或者下载一个几十 GB 的压缩包解压（二进制安装）。作业推荐后者，理由很实在：

pip 装法会把整个 Isaac Sim **塞进每一个 Python 虚拟环境**，一个环境约占 15 GB。你有三个环境就是 45 GB 的重复。二进制装法是**全局装一份**，各个虚拟环境通过一个"快捷方式"共享它——省的不只是磁盘，还有多版本切换时的麻烦。这个"快捷方式"就是下面 §5 要讲的软链接坑。

## 2. 核心概念（零基础可懂）

### 2.1 三个仿真软件各是什么

这三个名字长得像，最容易搞混。用一句话区分：

```
Isaac Sim   —— 物理引擎 + 渲染画面。负责"算物理、画机器人"。
Isaac Lab   —— 架在 Isaac Sim 上的一层"强化学习脚手架"。
              负责把"物理世界"翻译成强化学习能用的"环境"。
MuJoCo      —— 另一个独立的物理引擎，用来做 sim2sim 验证。
```

**Isaac Sim** 就像一个游戏引擎：给它一个机器人模型和一个场景，它能算出每一帧机器人各个部件在哪、受了多大力。但它不懂"强化学习"这回事——它不知道什么叫"观测"、什么叫"奖励"。

**Isaac Lab** 补上这一层。强化学习需要环境每一步吐出三样东西：机器人现在的状态（**观测 observation**）、这一步做得好不好的分数（**奖励 reward**）、这局是不是该结束了（**终止 termination**）。Isaac Lab 就是把 Isaac Sim 算出的原始物理数据，加工成这三样东西的框架。

> 本机实测版本（`pip show`）：Isaac Sim `5.1.0.0`，Isaac Lab `0.54.2`，Python `3.11.15`，MuJoCo `3.12.0`，torch `2.7.0+cu128`。
> 注意作业文档里写的 "Isaac Lab 2.2.0/2.3.2" 是 GitHub 上的发布标签（release tag），pip 包内部版本号显示的是 `0.54.2`，两者指的是同一套代码，别被吓到。

### 2.2 什么是 Manager（管理器）——本项目的骨架

这是本实践**最该讲透**的概念，也是面试高频考点。

**先建立直觉。** 想象你要点一份定制汉堡。你不需要重新发明一个汉堡，你只填一张表：

```
面包：全麦     肉饼：牛肉     酱料：番茄     配菜：生菜
```

厨房（一个固定的流水线）拿着这张表就能给你组装出汉堡。**换汉堡不用换厨房，只换表上的选项。**

Isaac Lab 的 **Manager-Based（基于管理器的）架构**就是这个思路。它有一个通用的"环境厨房"叫 `ManagerBasedRLEnv`。你想要什么样的机器人任务，不是去改这个厨房的代码，而是**填一张配置表**，告诉每个"管理器"该干什么。

**严格定义。** 一个 Manager 是一个专门负责环境某一方面的组件，它读取你写的配置，在每一步自动完成对应的计算。Isaac Lab 把一个强化学习环境拆成了这么几个管理器：

| 管理器 | 负责什么 | 生活化理解 |
|---|---|---|
| **ObservationManager** | 每步给机器人"看"什么数据 | 机器人的眼睛和内耳 |
| **ActionManager** | 机器人的动作指令怎么变成关节控制 | 手脚 |
| **RewardManager** | 每步这一步给多少分 | 教练的打分表 |
| **TerminationManager** | 什么情况判这局结束 | 裁判的哨子 |
| **CommandManager** | 这局要机器人干嘛（比如"往前走 0.5 m/s"） | 遥控器指令 |
| **EventManager** | 什么时候随机推机器人一把、随机改地面摩擦 | 捣乱的外部干扰 |
| **CurriculumManager** | 随训练进度自动调难度 | 循序渐进的课程表 |

**关键理解**：这七个管理器加起来，就完整定义了"一个机器人任务是什么"。你改任何一项行为，都不用碰 `ManagerBasedRLEnv` 的源码，只改那张配置表。这就是为什么实践 2 到实践 11 的作业，**几乎全都是在改一个 `*_env_cfg.py` 配置文件**——你改的就是那张表。

**落到代码**：`velocity_env_cfg.py` 里你能看到七个 `@configclass` 修饰的类，一一对应上面七个管理器：

```python
class ObservationsCfg:   ...   # 喂给 ObservationManager
class ActionsCfg:        ...   # 喂给 ActionManager
class RewardsCfg:        ...   # 喂给 RewardManager
class TerminationsCfg:   ...   # 喂给 TerminationManager
class CommandsCfg:       ...   # 喂给 CommandManager
class EventCfg:          ...   # 喂给 EventManager
class CurriculumCfg:     ...   # 喂给 CurriculumManager
```

（`@configclass` 是 Isaac Lab 提供的一个装饰器，作用是把一个普通 Python 类变成"一张能嵌套、能覆盖字段的配置表"，你现在只需要知道"带这个标记的类就是配置表"即可。）

### 2.3 gym.register 与 gym.make——任务名和环境的关系

**`gym`** 指 Gymnasium，是强化学习界的通用接口标准。它规定：所有环境都要能用一个字符串 ID 来创建。

- **`gym.register`**（注册）：登记一个任务。相当于在电话簿里写一行"`Unitree-G1-29dof-Velocity` 这个名字，对应的配置在这几个文件里"。**它只登记，不干活。**
- **`gym.make`**（创建）：真正按登记的信息，把环境**造出来**。相当于照着电话簿打电话，把人叫到现场。

这个区分很重要：注册时环境还不存在，只是记下了"配方在哪"；`gym.make` 时七个管理器才真正按配方把环境组装出来。

### 2.4 训练配置 vs 播放配置——为什么要两份

`velocity_env_cfg.py` 里有两个类：`RobotEnvCfg`（训练用）和 `RobotPlayEnvCfg`（回放用）。为什么同一个任务要两份配置？

因为**训练和验收的目标不一样**：

| | 训练配置 | 播放配置 |
|---|---|---|
| 环境数 | 4096 个（要海量试错） | 32 个（够看清就行） |
| 观测噪声 | 开（模拟真机传感器误差） | 关（看策略的真实能力） |
| 随机推一把 | 开（练抗干扰） | 关 |
| 课程难度 | 开（越练越难） | 固定（才能公平对比） |

**最实际的理由是"评估必须可比"**：课程学习会随训练进度偷偷改指令范围和地形难度，如果回放也用训练配置，那不同时刻存下来的策略是在**不同难度**下测的，成绩没法横向比较。播放配置把这些变量全部固定，才能公平地说"这个 checkpoint 比那个好"。

### 2.5 checkpoint 与 experiment_name

- **checkpoint**（检查点）：训练到一半，把机器人"大脑"的当前参数存成一个文件，比如 `model_9999.pt`。断电了能从这接着练，练完了能拿它去回放。
- **experiment_name**（实验名）：一个字符串，决定 checkpoint 存到哪个文件夹。它写在 **PPO 配置**里（`rsl_rl_ppo_cfg.py`）。

记住这条链：**experiment_name 决定日志目录**。这是后面 §3.3 "play 为什么能自动找到 checkpoint" 的钥匙。

## 3. 算法原理：从 `--task` 到环境创建的完整链路

这是作业 §5.3 的第 1 问，也是面试最爱问的"你真的懂这个项目吗"。别只答一句"根据 task 找到环境"——那等于没答。完整链路分七步：

```
python scripts/rsl_rl/train.py --task Unitree-G1-29dof-Velocity --headless
   │
   │ ① 先启动 Isaac Sim（AppLauncher），必须在任何 isaaclab 导入之前
   ▼
   ② import unitree_rl_lab.tasks
        └─ 触发各个 __init__.py 里的 gym.register(...)
           —— 此刻只是"登记"了任务名，环境还没造
   ▼
   ③ @hydra_task_config 读取配置
        └─ 按注册时写的 env_cfg_entry_point 取出 RobotEnvCfg
        └─ 按 rsl_rl_cfg_entry_point 取出 PPO 配置
        └─ 用命令行参数（--num_envs 等）覆盖配置里的默认值
   ▼
   ④ gym.make(task, cfg=env_cfg)
        └─ ManagerBasedRLEnv.__init__ 依次唤醒七个管理器
           每个管理器读自己那段配置，把环境真正组装出来
   ▼
   ⑤ RslRlVecEnvWrapper(env)
        └─ 套一层"翻译头"，把 Isaac Lab 的环境接口对齐到
           训练库 rsl_rl 期望的格式
   ▼
   ⑥ OnPolicyRunner(env, agent_cfg)
        └─ PPO 训练器，拿到环境就能开跑
   ▼
   ⑦ runner.learn() —— 训练循环开始
```

**这条链最该记住的一点**：`gym.register`（第②步）只登记了"配置在哪个文件的哪个类"，真正的环境对象是 `gym.make`（第④步）时由七个管理器**按配置临时组装**出来的。

正因如此，改一个任务的行为——比如实践 2 要给机器人加"地形感知"——**根本不用改 `ManagerBasedRLEnv` 的源码，只要改那张配置表**。这句话是整个 Manager-Based 架构的精髓，也是它和"每个新机器人都写一个新环境类"的老式写法的本质区别。

**为什么 `AppLauncher` 必须最先执行（第①步）**：Isaac Lab 的很多模块（`isaaclab.envs`、`isaaclab.sensors` 等）在被 import 的那一刻，就会去调用 Isaac Sim 的底层库（一个叫 `pxr` 的 Pixar USD 库）。如果 Isaac Sim 还没启动，这个库就不存在，import 直接报 `ModuleNotFoundError: No module named 'pxr'`。所以 `train.py` 的写法是"先 `AppLauncher` 启动引擎，再 import 所有 isaaclab 东西"——这不是代码洁癖，是硬性时序。（详见 §5 踩坑一。）

## 4. 代码走读

挑三段最关键的代码，逐段拆。

### 4.1 任务注册（`.../g1/29dof/__init__.py`，全文 12 行）

```python
import gymnasium as gym

gym.register(
    id="Unitree-G1-29dof-Velocity",                          # ① 任务名
    entry_point="isaaclab.envs:ManagerBasedRLEnv",           # ② 用哪个"环境厨房"
    disable_env_checker=True,
    kwargs={
        "env_cfg_entry_point":      f"{__name__}.velocity_env_cfg:RobotEnvCfg",        # ③ 训练配置
        "play_env_cfg_entry_point": f"{__name__}.velocity_env_cfg:RobotPlayEnvCfg",    # ④ 播放配置
        "rsl_rl_cfg_entry_point":   "...agents.rsl_rl_ppo_cfg:BasePPORunnerCfg",       # ⑤ PPO 配置
    },
)
```

**逐行讲：**

- 第②行 `entry_point` 指向的是 IsaacLab **通用**的 `ManagerBasedRLEnv`，**不是**某个 G1 专属的类。这正是 Manager-Based 架构的证据：所有任务共用同一个"环境厨房"。
- 第③④⑤行的三个 `entry_point` 才是这个任务的"个性"所在——它们分别指向训练配置、播放配置、PPO 配置的**类**。任务的全部特性都由这三张配置表决定。
- **`"文件路径:类名"` 这个冒号写法**是 Gymnasium 的约定，意思是"到这个模块里去找这个类"。写成字符串而不是直接 import，是为了**延迟加载**：注册时不需要真的把配置类读进来，等 `gym.make` 用到时才去取。

一个常见扣分点：把"任务入口"（`__init__.py`，负责注册任务名）和"环境配置"（`velocity_env_cfg.py`，负责定义任务内容）搞混。用一句话记牢：

- **任务入口**回答"这个任务名是在哪登记的" → `__init__.py`
- **环境配置**回答"这个任务具体是什么" → `velocity_env_cfg.py`

### 4.2 训练入口的时序（`scripts/rsl_rl/train.py`）

只看结构，不看细节，重点是**import 的顺序**：

```python
from isaaclab.app import AppLauncher     # line 29
# ... 解析命令行参数 ...
app_launcher = AppLauncher(args_cli)     # line 61 ← 引擎在这里启动

# ↓↓↓ 下面这些 import 全部在引擎启动之后 ↓↓↓
import gymnasium as gym                   # line 88
from isaaclab.envs import ...             # line 98
import unitree_rl_lab.tasks               # line 111 ← 触发 gym.register

@hydra_task_config(args_cli.task, "rsl_rl_cfg_entry_point")   # line 120
def main(env_cfg, agent_cfg):
    env = gym.make(args_cli.task, cfg=env_cfg, ...)           # line 158 ← 环境在这里组装
    env = RslRlVecEnvWrapper(env, ...)                        # line 181
    runner = OnPolicyRunner(env, agent_cfg.to_dict(), ...)    # line 184
    runner.learn(...)
```

注意 `line 61` 和 `line 88` 之间那道分界线：所有 `isaaclab` 相关的 import 都被**故意压到 `AppLauncher` 之后**。这就是 §3 讲的硬性时序在真实代码里的样子。

### 4.3 play 如何自动找到 checkpoint（`scripts/rsl_rl/play.py`）

作业 §5.3 第 3 问。很多人答"因为有个 latest.pt"或"因为任务名没变"，都不准确。真正的机制看这两行：

```python
log_root_path = os.path.join("logs", "rsl_rl", agent_cfg.experiment_name)   # line 80
resume_path = get_checkpoint_path(log_root_path, agent_cfg.load_run, agent_cfg.load_checkpoint)  # line 91
```

三层默认值接力，逐层缩小到唯一一个文件：

1. **`log_root_path`** = `logs/rsl_rl/{experiment_name}`。而 `experiment_name` 来自 **PPO 配置**——`play.py` 和 `train.py` 读的是**同一个** PPO 配置文件，所以推导出**同一个目录**。这是"自动找到"的根。
2. **`load_run`** 默认 `".*"`（一个匹配任意字符的通配），`get_checkpoint_path` 在该目录下按**时间戳排序取最新**那次运行。
3. **`load_checkpoint`** 默认 `"model_.*.pt"`，在那次运行里取**迭代数最大**的那个 `.pt`。

所以"自动"的本质是：**play 和 train 共享同一份 PPO 配置 → 推出同一个日志目录 → 再按"最新运行 + 最大迭代"选定文件**。

一个推论：如果你想做对照实验（比如实践 5/8 对比不同奖励设计），**必须给每组设不同的 `experiment_name`**。否则它们的 checkpoint 全落进同一个目录，play 只能靠时间戳区分，极易取错。

顺带一提，`play.py` 跑完还会把策略**导出**成一个独立的 `exported/policy.pt`（line 150-151）——这个导出文件不含训练框架的任何依赖，是后面 sim2sim 和真机部署真正加载的东西。

## 5. 我踩过的坑（面试素材）

### 坑一：`ModuleNotFoundError: No module named 'isaacsim'` / `'pxr'`

**现象**：跑 `train.py` 或任何脚本，一 import 就崩，说找不到 `isaacsim` 或 `pxr` 模块。

**第一反应**：包没装好，`pip install` 重装一遍 Isaac Sim。

**为什么这么想是错的**：包其实装好了。缺的信息是——Isaac Lab 找 Isaac Sim 不是靠 pip，而是靠一个**软链接**（symbolic link，一个指向别处的"快捷方式"）。Isaac Lab 目录下必须有一个叫 `_isaac_sim` 的软链接指向 Isaac Sim 的真实安装路径；Isaac Lab 的脚本会把这个链接目录塞进 Python 的搜索路径，`import isaacsim` 才能成功。链接不存在，包装得再好也找不到。

**怎么找到真因**：
1. 到 Isaac Lab 目录 `ls -l _isaac_sim`，看软链接在不在、指向对不对；
2. 确认 `~/isaacsim/python.sh` 真实存在；
3. 确认当前在对的 conda 环境里（`conda activate env_isaaclab`）；
4. 确认跑过 `source _isaac_sim/setup_conda_env.sh`。

对于 `pxr` 这个报错还有第二种成因：**import 时序错了**——在 `AppLauncher` 启动引擎之前就 import 了 isaaclab 模块（见 §3、§4.2）。

**根因**：Isaac Lab 与 Isaac Sim 的连接靠软链接 + 启动时序，不靠 pip 依赖。

**教训**：遇到"模块找不到"，先分清是"没装"还是"没链接/没按顺序加载"。对 Isaac 这类重型仿真软件，后者远比前者常见。这个软链接机制的好处是**解耦**：Isaac Sim 装在哪都行，换版本只要重指链接，不用动 Isaac Lab 一行代码。

### 坑二：三个虚拟环境的 torch 版本互相打架

**现象**：本机有三个 conda/venv 环境，torch 版本分别是 2.7 / 2.9 / 2.10，numpy 也不同。想图省事全塞进一个环境。

**第一反应**：一个环境装全不好吗？省得来回切。

**为什么这么想是错的**：不同实践依赖的仿真栈版本是**冲突**的。实践 1~3/5/7/8/10/11 用 Isaac Sim + torch 2.7；实践 4/6/9 用另一个叫 mjlab 的框架，要更新的 MuJoCo Warp 和 torch。最典型的是实践 11 的 `instinct_rl` 要 torch 2.11 + numpy≥2——把它装进 Isaac Sim 那个环境，会把 torch 2.7 顶掉，实践 1~10 当场全废。

**怎么找到真因**：装新包前先 `pip install --dry-run <包>`，看它会**连带升级**哪些底层库。一旦发现它要动 torch / numpy / mujoco，就知道不能装进当前环境。

**根因**：仿真软件对底层数值库（torch / numpy / mujoco）的版本**极其敏感**，且各实践的要求互斥，只能物理隔离在不同虚拟环境里。

**教训**：环境隔离不是洁癖，是**必需**。判断"能不能装进来"的标准动作是 `--dry-run` 看连带升级，而不是装了再说。

### 坑三：MuJoCo 版本被锁死在 3.12.0，不能随便升

**现象**：sim2sim 用到的地形扫描是一个 MuJoCo **第三方插件**编译出来的 `.so` 动态库。某次不小心升级了 mujoco，插件立刻报 `plugin mujoco.sensor.ray_caster not found`。

**第一反应**：插件坏了，重新编译插件。

**为什么这么想是错的**：插件没坏。问题是**编译插件时用的 MuJoCo 版本**，和**运行时 Python 加载的 MuJoCo 版本**必须**严格一致**。这类 C++ 编出来的动态库和主程序之间有个"二进制接口约定"（ABI，Application Binary Interface）——版本一变，约定就对不上，库直接加载失败，报的却是"插件找不到"这种误导性错误。

**怎么找到真因**：用 `ldd libsensor_raycaster.so` 看这个插件**链接的是哪个版本**的 `libmujoco.so`，再对照 `python -c "import mujoco; print(mujoco.__version__)"`，两者一比就露馅。

**根因**：C++ 编译的动态库与运行时之间存在 ABI 版本绑定，跨版本不兼容。

**教训**：凡是"编译出来的插件 / 扩展"，版本一致性是硬约束。装任何新包前先 `pip install --dry-run` 确认不会顺手把 mujoco 带上去升级。（这条和坑二是同一类问题的两面。）

## 6. 面试可能怎么问

**概念题**

1. **Q：Isaac Sim、Isaac Lab、MuJoCo 三者什么关系？**
   A：Isaac Sim 是物理引擎+渲染，负责算物理画机器人，能一卡并行几千个环境，用于大规模训练；Isaac Lab 架在它之上，把物理世界翻译成强化学习要的"观测/奖励/终止"三件套；MuJoCo 是另一个独立引擎，一次跑一个，用来做 sim2sim——把策略换个仿真器验证，排除"只学到了训练器数值特性"的假成功。

2. **Q：什么是 Manager-Based 架构？有哪几个 Manager？**
   A：核心思想是"行为由配置组装，不由继承定义"。有一个通用的 `ManagerBasedRLEnv`，具体任务靠七个管理器（Observation / Action / Reward / Termination / Command / Event / Curriculum）各读一段配置来定义。改任务只改配置表，不碰环境源码——这就是为什么后续实践几乎都在改一个 `*_env_cfg.py`。

**实现题**

3. **Q：从 `--task` 到环境创建，中间发生了什么？**
   A：① AppLauncher 先启动 Isaac Sim；② import tasks 触发 `gym.register` 登记任务名；③ `hydra_task_config` 按注册信息取出环境配置和 PPO 配置，并用命令行参数覆盖；④ `gym.make` 让七个管理器按配置组装出环境；⑤ 套 `RslRlVecEnvWrapper` 对齐训练库接口；⑥ 交给 `OnPolicyRunner`；⑦ 开训。关键点：register 只登记配方，make 才真正组装。

4. **Q：play.py 怎么自动找到训练存的 checkpoint？**
   A：因为 play 和 train 读同一份 PPO 配置，里面的 `experiment_name` 推出同一个日志目录 `logs/rsl_rl/{experiment_name}`；再由 `get_checkpoint_path` 按"最新运行 + 最大迭代数"两级默认值定位到唯一文件。不是"因为叫 latest.pt"，是**配置共享 → 目录一致**。

5. **Q：为什么训练配置和播放配置要分开？**
   A：目标不同。训练要 4096 环境、开噪声、开随机推、开课程，追求采样效率和泛化；播放要 32 环境、关噪声、关随机、固定难度，追求可视化和**可比性**——课程会随进度改难度，播放若不固定，不同 checkpoint 的成绩就没法横向比。

**深挖题**

6. **Q：为什么 `train.py` 里 isaaclab 的 import 全压在 `AppLauncher` 后面？**
   A：isaaclab 模块 import 时就会调用 Isaac Sim 底层的 USD 库（`pxr`）。引擎没启动，这个库不存在，import 直接报 `No module named 'pxr'`。所以必须先 `AppLauncher` 启动引擎再 import——是硬性时序，不是风格问题。

7. **Q：为什么推荐二进制装 Isaac Sim 而不是 pip？软链接的作用是什么？**
   A：pip 会把 Isaac Sim 塞进每个虚拟环境（约 15 GB/个），二进制是全局装一份共享。共享靠 Isaac Lab 目录下的 `_isaac_sim` 软链接指向真实安装路径——它统一了模块导入路径、解耦了安装位置、换版本只需重指链接。缺链接就报 `No module named 'isaacsim'`。

## 7. 延伸：这个技术在工业界怎么用

**训练-验证的两级仿真是行业标配。** 波士顿动力、宇树、Agility 这些做人形/足式机器人的公司，内部流程和这个实践是同构的：先在 GPU 并行仿真器里大规模训练（Isaac Sim / MuJoCo MJX / Genesis 等），再在一个更"接近真机"的仿真器里做迁移验证，最后才上真机。中间这道 sim2sim，本质是在花几分钟排除掉那些"只在训练器里成立"的假策略，避免直接上真机摔坏几十万的硬件。

**Manager-Based 这种"配置驱动"的设计，是为了规模化。** 一家公司可能同时维护十几种机器人、几十种任务。如果每个任务都手写一个环境类，代码会爆炸且没法复用。把环境拆成一组管理器、任务写成配置表之后，一套 PPO 超参可以喂给所有机器人，一个奖励项可以在多个任务间复用——这正是 `rsl_rl_ppo_cfg.py`（算法配置，按任务族组织）和 `velocity_env_cfg.py`（环境配置，按机器人组织）**分在两个目录**的原因。

**这套栈直接脱胎于学术界的开源工作。** rsl_rl 训练库来自苏黎世联邦理工（ETH Zürich）足式机器人实验室，他们 2022 年那篇让 ANYmal 机器人靠强化学习走遍山野的工作（Miki et al., *Science Robotics*），用的就是"并行仿真 + 地形课程 + 本体感知"的组合——和你在实践 2 里要做的事情是一条技术脉络。你现在搭的这个环境，就是复现那类工作的起点。
